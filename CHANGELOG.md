# Changelog

## 0.13 (unreleased)

In short: a change to a check's code is now reviewed by two reviewers from two model families other than the author's, a clause of the experimental rule `ratchet.review-by-risk`, text only. This repo's own required job `checks` now also runs the base branch's checks against every pull request, so six entries of its register are "built" again. For a project that adopted by reference, five frictions from an adoption report on 0.12 are fixed: `upgrade.py` prints the new runner commands in place of a workflow pin, the line for a local check script stops the script without `set -e`, and `run_pinned.py` runs in well under a second where it took seven to nine. If you keep `REGISTER.md` with rows by reference, print it again: the label of those rows changed one word. A new page, TRYING.md, says how to try Ratchet on a repo of your own. No form changes.

- `ratchet.review-by-risk` gets a clause: a PR that changes a check's code, in the paths the project lists as its checks, is reviewed by two reviewers from two model families other than the author's, each at the same head, and merges only when both have passed it. It takes no place under the cap ([D-2026-11-23-two-reviewers-for-check-code](decisions/D-2026-11-23-two-reviewers-for-check-code.md), [#139](https://github.com/fabian-von-tiedemann/ratchet/pull/139)).
- This repo's register adopts the new text, and its own rule `repo.review-classes` names its checks: `checks/` and `.github/workflows/` ([#139](https://github.com/fabian-von-tiedemann/ratchet/pull/139)).
- This repo's `.github/workflows/checks.yml` has three jobs. `own` runs the pull request's own checks, as before. `base`, on a pull request only, takes `checks/from_base.py` from the base commit and runs the base branch's scripts on the pull request's data, and the base branch's tests and runner on the pull request's checks. `checks`, the status the ruleset on `main` requires, passes only when both did ([#121](https://github.com/fabian-von-tiedemann/ratchet/pull/121)).
- A pull request that the base branch cannot judge fails closed and says why: one that changes the workflow or the runner of the suite, one whose base lacks a script the job runs, or one that changes a check or the form of a data file in a way the base's checks reject. The maintainer reads it and merges it as an administrator. The pull request that adds the job is the first ([#121](https://github.com/fabian-von-tiedemann/ratchet/pull/121)).
- `ratchet.register-on-top`, `ratchet.expected-tests-ran`, `repo.rules-as-data`, `repo.checks-fail-on-fixtures`, `repo.version` and `repo.new-rule-used` are "built" in this repo's register, each `where` naming the job and the point where it is enforced. `checks/test_budget.py` fails on a "built" entry that the workflow and `checks/from_base.py` do not show ([D-2026-11-22-second-redraw](decisions/D-2026-11-22-second-redraw.md), [#121](https://github.com/fabian-von-tiedemann/ratchet/pull/121)).
- `upgrade.py`, for a register with rows by reference in a project with no `.github/workflows/ratchet.yml`, which adopt mode never writes, no longer ends with "Then pin .github/workflows/ratchet.yml". It prints what `init.py` prints for such a project, with the new commit: the command that copies `checks/run_pinned.py` again, the line for the local check script and the line for the CI step ([#140](https://github.com/fabian-von-tiedemann/ratchet/pull/140)).
- To do, if your local check script runs the line adopt mode printed in 0.12: replace it with the one `init.py` or `upgrade.py` prints now, `( ... ) || exit 1`. The old line went on after a failing check in a script without `set -e` ([#140](https://github.com/fabian-von-tiedemann/ratchet/pull/140)).
- `upgrade.py` no longer prints `--markdown REGISTER.md` in the command that checks a register that has rows by reference and no `REGISTER.md` ([#140](https://github.com/fabian-von-tiedemann/ratchet/pull/140)).
- The label of a row by reference says "The wording is not guarded against softening", or "guarded", where it said "Protection against a softened wording: not built". "built" now means only a rule's enforcement ([D-2026-11-23-new-rules-first](decisions/D-2026-11-23-new-rules-first.md), [#140](https://github.com/fabian-von-tiedemann/ratchet/pull/140)).
- `run_pinned.py` fetches only the pinned commit when it has to make the store, shallow and by its id, and fetches the whole repository, as a clone does, only when the host does not give a commit by its id. It reads the tree one level at a time, so a run takes about 0.5 seconds in place of 7 to 9. It still hashes every object it uses, and never passes when Ratchet cannot be reached ([#140](https://github.com/fabian-von-tiedemann/ratchet/pull/140)).
- [STARTING.md](STARTING.md) says that the pinned step may run in a job that is not required, and that it fails, never passes, when Ratchet cannot be reached ([#140](https://github.com/fabian-von-tiedemann/ratchet/pull/140)).
- For a rule adopted in part, list the whole sentence when any part of it is not stated, and put a marker line outside a Markdown list, since one between list items ends the list. The form of `register.json` does not change ([#140](https://github.com/fabian-von-tiedemann/ratchet/pull/140)).
- `upgrade.py` takes the register named alone, from the folder that holds it, as `python3 .ratchet/checks/upgrade.py register.json`, and refuses a path in another folder before it does anything, so the commands it prints always name the register that was upgraded ([#140](https://github.com/fabian-von-tiedemann/ratchet/pull/140)).
- New: [TRYING.md](TRYING.md), for trying Ratchet on a repo of your own, with an issue form for the report. A repo that already has its own rules and checks reads the rules against itself and adopts nothing yet ([#141](https://github.com/fabian-von-tiedemann/ratchet/pull/141)).

## 0.12 (2026-11-23)

- Every script in `checks/` runs under `python3 -I` ([#135](https://github.com/fabian-von-tiedemann/ratchet/pull/135)).

This version is the second redraw of Ratchet, steps 1 to 11 of the migration in the decision `D-2026-11-22-second-redraw`. The eleven principles become seven, and every rule stands under one of them. The core goes from 35 rules to 19, of which 13 name a check and 6 are text only, and the experimental rules go from 19 to 10, under a cap of 17 in place of 23. The tag `v0.2` was already published when this work was finished, so it is released as 0.3: see [D-2026-11-16-renumber](decisions/D-2026-11-16-renumber.md).

**The format of a register changes.** In 0.2 a register was a Markdown file, checked by a few lines of shell. From 0.3 it is a data file, `register.json`, and `REGISTER.md` is generated from it. A register written for 0.2 has to be moved by hand: see [MIGRATING.md](MIGRATING.md). Ratchet ships no reference check for decision files or for the glossary. Two attempts were reviewed and set aside, and how to check them is an open question.

The reason for the new format is that two reviews in a row found new ways to hide a changed row from a check that read Markdown. A data file has one form, and the generated file is compared with it byte for byte.

Added:

- `ratchet.json`: every rule as data, with its part, its status (`core` or `experimental`) and its enforcement (`enforced` or `text-only`). The rule tables are generated from it.
- A reference check for `ratchet.register-on-top`, `checks/check_register.py`. It reads a project's `register.json`, compares it with Ratchet at the version it states, and fails unless `REGISTER.md` is exactly what the data generates. A value in a data file is text, never Markdown: it is written into a generated file with a backslash before every punctuation mark, so that data cannot become a link, HTML or hidden text. The one other form is code, between a pair of backticks. A value is written in Latin script: its characters come from one fixed list of Latin letters, digits, the plain space and marks, written out as code points in the check, so that a value is valid or not the same on every supported version of Python. No character on the list is written right to left or changes the order a line is shown in. No character on the list is a compatibility form, which is not a protection against characters that look alike. A name between two colons is refused, so that a site cannot show it as a picture. A person named with `@`, an issue named with `#` and the id of a commit are accepted and written as text, and what a site makes of them is not covered. Every file a check reads is strict UTF-8, and bytes that are not UTF-8 fail the check. See [checks/README.md](checks/README.md) and [D-2026-11-17-latin-strict-utf8](decisions/D-2026-11-17-latin-strict-utf8.md). It has a clean project copy it passes on and one copy for each fault it fails on, including every way of hiding a row that the reviews found. It runs in this repo's CI, together with a check that the generated text matches the data files.
