Working rules, templates and checks for long-lived code projects built by AI agents

Your AI agents read the rules, then say “done” without running the tests.

When something breaks, the fix is one more line in a prompt that is also ignored. Ratchet turns each rule into a check that fails when the rule is broken, and each failure into a check with a fixture it must fail on, so a case that is tested cannot quietly come back. Where no check can see a rule, Ratchet says so.

01 The mechanism

How the ratchet turns

A ratchet turns one way. Each failure leaves a ratchet behind, a check wherever a check can see it, and the next failure adds another.

Fig. 3 One turn. The steps are the five on this page, in order.

  1. A failure happens. A review rejects a change, a run fails, or a bug reaches the main branch. The loop
  2. It becomes a lesson. What happened, the failure class, the ratchet, and whether it would apply in other projects. templates/LESSON.md
  3. The lesson becomes a check, with a fixture it must fail on, so the check is known to see the failure. Where no check can see it, the rule says “text only” and why. checks/ · the fixtures
  4. The register says what is built. Every rule in force, copied verbatim, and whether its check is built. A check in every PR fails when a rule was softened. REGISTER.md
  5. The next release carries it. Changes are collected under the unreleased entry of the changelog and released together, and each project upgrades in a PR of its own. CHANGELOG.md · UPGRADING.md

And round again: the next failure becomes the next check. A check may be tightened at any time, and loosening one is the owner's decision, written down. A lesson that would apply in other projects is sent back to Ratchet.

One turn, as an illustration. It is not a report from a real project. README.md

  • What happened
    An agent writes “all tests pass” on a PR. The tests were never run, and the bug reaches the main branch.
  • The failure class
    A claim of completion without a run.
  • The ratchet
    A required check that runs the tests on the PR head, so the claim no longer matters.

Fig. 4 One click, as a cartoon. The first run fails, and the failure becomes a check: a dial that catches that fault the next time, and only that fault. The rules that no check can see yet stay bows, and Ratchet lists them as text only.

02 Why it exists

Why Ratchet exists

The maintainer had more than 100 repos and no longer knew what governed the agents in them. Each new practice from the field went into one repo at a time. So for a new project that had to be tight from the start, the rules were built outside any one repo for the first time: one set, kept up with lessons from every project and from the field.

  • The field is followed once, upstream, instead of once per repo. Ratchet credits four public sources on agentic coding, each pinned at a commit. A scheduled workflow opens an issue when a source moves, and the maintainer judges each move before the pin follows. The maintainer also reads more widely, and what holds up comes in as a proposal. sources.json · What Ratchet builds on
  • A new rule has one way in. It starts as a proposal, enters by the maintainer's decision as an experimental rule, outside the core and under a cap, and moves into the frozen core only by another decision of the maintainer. The core is frozen
  • Each project owns its set. It adopts the rules that matter to it, copied verbatim, and adds its own. Nothing arrives by itself: a new or changed rule reaches a project only when it upgrades, and which new rules to adopt is the project's choice. UPGRADING.md
  • Skills stay out of your repos until you choose one. Ratchet cites the sources and does not ship or install any skill from them. A project that wants one copies it at a pinned commit, tied to a named situation. RATCHET.md

Ratchet does not yet help you clean up an agent layer you already have. That clean-up is what it grew out of, and it comes next.

Tell us where it does not fit. A project that tries Ratchet and meets a rule that does not fit is the input Ratchet improves from. Open an issue, with the proposal form for a change to a rule. Feedback from one project, issue #89, has already led to a decided change of form: a project may keep the rules it adopts in a block generated into its own instruction file. It is part of 0.10. A proposal takes the same way in as any rule, and nothing is promised in advance. To try it, go to Start here.

03 The form of a rule

What Ratchet does

Ratchet is a set of working rules, templates and reference checks for long-lived code projects built by AI agents.

Each rule carries a ratchet: the check that fails when the rule is broken, or the words “text only” and the reason no check can see it. Two rows from RATCHET.md, shortened:

  • ratchet.no-secrets
    No secrets, tokens or real personal data in the repo or in the chat.
    Check a secret scan in every PR and every night
  • ratchet.ask-the-owner
    The agent looks up facts itself. Decisions belong to the owner.
    Text only a check cannot tell a fact from a decision
  • The register says honestly what is built. Your project keeps a register with the rules it adopts, copied verbatim, and for each check whether it is built. The register that people read is generated from it, and a check in every PR fails when a rule was softened. Ratchet's own register
  • It runs on itself. Ratchet follows its own rules, and its repo is where they are tried first. Its working rules, its register, its handover and its decisions are Ratchet's own. AGENTS.md · decisions/

04 The machine around it

How this repo is run

Several agents work on this repo at once, in the way CONTROL-ROOM.md describes. It is how this repo works, not something a project must adopt: the control room is experimental.

Fig. 5 From the control room to a release. The review, the approval and the merge hold only for the same head.

  1. A control room plans. One long-running agent session keeps the handover, starts the work, and brings the maintainer at most five decisions at a time, each with a recommendation. The control room · HANDOVER.md
  2. Short-lived workspaces build. Each task gets a workspace with its own branch and worktree, which reports back with a PR and its head. Here the workspaces' shell commands run in a sandbox. That is an observation from a trial in this repo, not a rule. issue #49 · the decision
  3. Each change is a pull request, from the agents' own account. An approval from that account does not count as the code owner's. The main branch
  4. A model from another family reviews the exact head, and the verdict is posted on the PR. A PR that changes only decisions and the handover is exempt. This is an instruction the agents follow, not a lock. The decision · the exception
  5. The maintainer approves that head, with a click on GitHub, or the control room submits the approval on the maintainer's word in its chat. A new push dismisses it. The decision
  6. The merge. The ruleset on main refuses it until the job checks is green and the code owner has approved the latest push. The agent merges with a squash, pinned to the approved head. On main, the release workflow runs the checks again and, when the version has a date, tags and releases it. Release on merge · the workflow

Then back to the control room, which replaces the handover and takes the next task.

06 Tighter, not heavier

How it stays tight

Tighter does not mean more rules. It means more of the rules are enforced by a check, and fewer failure classes come back (what tighter means).

10 experimental rules, with a cap of 17. The core holds 28 rules and is frozen: 15 name a check and 13 are text only. Counted by checks/generate.py from ratchet.json.

  • The core is frozen. No rule is added to it or removed from it without the maintainer's decision. A new rule starts as experimental, outside the core. The core is frozen
  • The experimental rules have a cap. A new one replaces, merges or removes one, or a decision raises the cap, and Ratchet uses it itself or says why it cannot. Over the cap, generate.py --check is red and nothing is generated. The budget · the decision
  • Releases are batched. Changes are collected under the unreleased entry of the changelog, and released at most once a week or when the maintainer asks. A fix for a security fault is released at once. The decision
  • The sources are watched every day. A scheduled run compares each pin with the head of its source and opens an issue when one has moved, so a rule does not go on crediting a source that now says something else. The workflow · watch_sources.py
  • Every change is reviewed before it is merged. A model from another family reviews its exact head, except for a PR that changes only decisions and the handover, and the maintainer then approves that same head. A change to a check, a rule or a decision is read by the maintainer. How to change a check
  • Rules leave, too. A core rule leaves when a check covers it, or when a stronger or simpler rule replaces it. An experimental rule that has stood through three releases and 60 days with no decision stops the checks at the next release, until the maintainer moves it into the core, merges it, removes it, or keeps it once more by a decision. The rest of the clean-out, a pass at every release over what no longer earns its place, is planned and not built yet. The age of a rule · the decision

07 What the repo shows

Evidence from this repo

  • A hook that could not be a lock was replaced by locks. A review from another model family rejected a hook meant to stop the steps that cannot be undone, twice, and it was closed unmerged (PR #42). It came back as a tripwire that says it does not catch every spelling, and the locks moved to a ruleset at GitHub and the role of the agents' account (the decision).
  • Tags are locked by a ruleset. No one but a repository admin can move or delete a tag (the ruleset, the decision).
  • A release is published by the merge that dates it. The release workflow tags it after the merge, and every PR compares released text with its tag (released_text.py), because the generator once rewrote a released entry (PR #12).
  • A change to a rule or a check is merged only after a model from another family has passed its exact head. The reviews are comments on the PRs, such as the two rounds on PR #50. This is an instruction the agents follow, not a lock (the decision).
  • The register says honestly which checks are built. Every rule this repo adopts that names a check stands as “text only for now” (REGISTER.md).

08 Read this before you start

The honest limits

  • Most of the core is still text. The share is stated with every version in the changelog, and the work between versions is to bring it down. For a rule without a reference check, the ratchet says what a check must do, and your project builds it. Until it does, the rule is text only in your project, and your register says so.
  • It is built for one person who decides, several coding agents, and a repo that has to last. For a single agent on a short project it is more than you need: take the ten rules to start with and stop.
  • Some of what holds here is an instruction, not a lock. The review from another family is one. The register and AGENTS.md say which.
  • The form may still change. Before 1.0, a minor version may change the form of the data files, and the changelog lists every such change.

09 Two commands and a dry run, in the root of your own git repo

Start here

  1. Fetch Ratchet at the latest release into .ratchet. 
    git clone --branch v0.10 https://github.com/fabian-von-tiedemann/ratchet .ratchet
  2. See what it would write. This writes nothing. 
    python3 .ratchet/checks/init.py --check
  3. Write it. 
    python3 .ratchet/checks/init.py
    It writes AGENTS.md, register.json with ten rules to start with, the generated REGISTER.md, and a workflow that runs the register check on every PR. It never overwrites a file.

The next steps are in the README.
