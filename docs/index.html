Ratchet

AI agents read your instructions and still don't follow them. They say "done" without running the tests, and when something breaks, the fix is another line in a prompt that is also ignored.

Ratchet turns each rule into a check that fails when the rule is broken, or says plainly that no check can see it. Each failure becomes a check with a fixture it must fail on, so the cases that are tested cannot quietly come back.

What Ratchet does

Ratchet is a set of working rules, templates and reference checks for long-lived code projects built by AI agents.

  • A rule names the check that enforces it, or says text only and why. Each rule carries a ratchet: the check that fails when the rule is broken, or the words "text only" and the reason no check can see it. The rules
  • Every failure becomes a check with a fixture. When something breaks, its failure class gets a ratchet: a check that fails on it, run on a fixture it must fail on. A lesson that would apply in other projects is sent back to Ratchet. The reference checks
  • The register says honestly what is built. Your project keeps a register with the rules it adopts, copied verbatim, and for each check whether it is built. The register that people read is generated from it, and a check in every PR fails when a rule was softened. Ratchet's own register
  • It runs on itself. Ratchet follows its own rules, and its repo is where they are tried first. Its working rules, its register, its handover and its decisions are Ratchet's own. AGENTS.md, decisions

Evidence from this repo

  • A hook that could not be a lock was replaced by locks. A review from another model family rejected a hook meant to stop the steps that cannot be undone, twice, and it was closed unmerged (PR #42). It came back as a tripwire that says it does not catch every spelling, and the locks moved to a ruleset at GitHub and the role of the agents' account (the decision).
  • Tags are locked by a ruleset. No one but a repository admin can move or delete a tag (the ruleset, the decision).
  • A release is published by the merge that dates it. The release workflow tags it after the merge, and every PR compares released text with its tag (released_text.py), because the generator once rewrote a released entry (PR #12).
  • A change to a rule or a check is merged only after a model from another family has passed its exact head (the decision). The reviews are comments on the PRs, such as the two rounds on PR #50. This is an instruction the agents follow, not a lock.
  • The register says honestly which checks are built. Most of the rules this repo adopts that name a check stand as "text only for now" (REGISTER.md).

The honest limits

  • Most of the core is still text. The share is stated with every version in the changelog, and the work between versions is to bring it down. For a rule without a reference check, the ratchet says what a check must do, and your project builds it. Until it does, the rule is text only in your project, and your register says so.
  • It is built for one person who decides, several coding agents, and a repo that has to last. For a single agent on a short project it is more than you need: take the nine rules to start with and stop.
  • Some of what holds here is an instruction, not a lock, such as the review from another family. The register and AGENTS.md say which.
  • The form may still change. Before 1.0, a minor version may change the form of the data files, and the changelog lists every such change.

Start here

Run these in the root of your own git repo.

  1. Fetch Ratchet at the latest release into .ratchet. 
    git clone --branch v0.9 https://github.com/fabian-von-tiedemann/ratchet .ratchet
  2. See what it would write. This writes nothing. 
    python3 .ratchet/checks/init.py --check
  3. Write it. 
    python3 .ratchet/checks/init.py
    It writes AGENTS.md, register.json with nine rules to start with, the generated REGISTER.md, and a workflow that runs the register check on every PR. It never overwrites a file.
