## The threat model

One text for every check here, by [D-2026-11-22-second-redraw](../decisions/D-2026-11-22-second-redraw.md). A review brief cites it.

**What every check here is for.** Ratchet's checks catch mistakes and drift: a rule copied wrong, a test that was dropped, a step taken the usual way without its approval, a job that stopped reporting.

**What no check here is for.** They are not written to stop someone who means to get past them. An agent or a person with write access can soften a rule, reword a check or take a step another way, and a check in the repo will often not see it. What stands against that is a lock at the host: the owner's required review of the paths that hold the rules and the checks, from an account the agents cannot approve with. Where that lock is not built, nothing stands against it, and the register says so. No check guards against someone who controls the owner's account, the host, or the machine a session runs on.

**Tripwires.** A script that runs only on an agent's machine, with no lock at the host behind it, is a tripwire. It catches the usual way and no other.

**Each check's own limits.** This shared text sets the threat model for every check. Each check states its own, narrower claim, under "What it claims" and "What it does not claim", and that claim sets what the check covers.

**When a review finds something the check does not cover.** A finding that the check's own claim does not cover starts no new round of hardening. It becomes one question to the owner: widen the claim by a decision, or record the finding as outside it. A finding inside the check's own claim is fixed as before, and `ratchet.two-rounds` still applies.

## Data files and strict forms

No check here looks for rules in free Markdown. A check that does can be shown a file in which a reader sees a row and the check does not: an indented row, a row in a comment, a row under a heading that is not a heading. Each way that was found is closed the same way:

- **What a check needs to read is data.** The register is `register.json`. A data file is read strictly: valid JSON in UTF-8, no field twice in one object, no field the check does not know, every value of the kind it must be. `registry.load_json` opens it without blocking and reads it only when it is a regular file, so a FIFO, a device or a folder in its place is refused, not waited on, and a link is followed as before.
- **Every file is strict UTF-8.** A check decodes every file it reads as UTF-8 and fails on bytes that are not, with the file and the byte named. No byte is read as some other character, so a file with a wrong byte never compares equal to a file without it.
- **What people read is generated.** `REGISTER.md` is written from the data file and compared with it byte for byte. Nothing can be added to the generated file, hidden in it or changed in it without failing the check.
- **A value is text, never Markdown.** When a value from a data file is written into a generated file, every ASCII punctuation mark in it gets a backslash, so Markdown reads none of it as markup. A value cannot become a link, an image, emphasis, HTML or a comment. The generator does not try to work out what Markdown would make of a value.
- **Code is the one other form.** A part of a value between a pair of backticks is code. That is the data's own way to mark it, and the generator writes it as a code span. Two such parts have text between them, and code has no spaces at its ends.
- **Characters from one fixed list.** A value is one line. Every character in it is a Latin letter, a digit, a plain space or one of the marks listed under [The characters a value may hold](#the-characters-a-value-may-hold). Everything else is refused, with the character named: other scripts, combining marks, control and format characters, other kinds of space, line and paragraph separators, fillers that show as nothing, lone surrogates, the replacement characters, characters that are written right to left, controls that change the order a line is shown in, and compatibility forms such as full-width letters. An `@` between two characters is refused outside code, because it is read as a mail address whatever is escaped.
- **The list is code points in the check.** It stands in [registry.py](registry.py) as ranges of code points. The check does not ask the interpreter what kind of character it has, because the answer depends on the version of Unicode the interpreter carries. A value is valid or not by the list alone, the same on every supported version of Python.
- **No name between two colons.** A colon, then one or more letters, digits, `_`, `+` or `-`, then a colon is refused, in text and in code. A site that renders the file may replace such a name with a picture after Markdown is done, and no backslash stops that.
- **What that costs.** A value is written in Latin script: no other script, no symbol that is not on the list, and an accented letter only in its one-character form. A time with seconds, or anything else with a word between two colons, is written another way. A link in a value is shown as its text.
- **Keys, statuses and versions are not free text.** Each has its own exact form and is written as it stands.
- **One policy for line endings.** CRLF is read as LF, by every check and by the generator. Generated files are written with LF. A carriage return alone counts as a difference. One exception: the block that `check_register.py` generates into a project's instruction file is compared as it stands, so a line of the block or a marker that ends in CRLF fails, and the rest of that file, which is never read, may keep its CRLF. See [check_register.py](#check_registerpy).
- **A file that failed once fails forever.** Every way that has been found to hide something from a check is a copy under [fixtures/](fixtures/) that must fail, with a test that names the message.

## The characters a value may hold

741 characters, and no other:

- **Latin letters.** `A` to `Z` and `a` to `z`. U+00C0 to U+00FF without the two signs U+00D7 and U+00F7. U+0100 to U+024F. U+1E00 to U+1EFF. Left out of those ranges: the compatibility forms U+0132, U+0133, U+013F, U+0140, U+0149, U+017F, U+01C4 to U+01CC, U+01F1 to U+01F3, U+1E9A and U+1E9B, and the click letters U+01C0 to U+01C3, which look like a pipe and an exclamation mark.
- **Digits.** `0` to `9`.
- **The plain space.** U+0020.
- **The ASCII marks.** All 32, from `!` to `~`. Two have a meaning of their own: a pipe is refused because it would break the table, and a backtick marks code.
- **Sixteen marks outside ASCII.** ¡ U+00A1, £ U+00A3, § U+00A7, « U+00AB, ° U+00B0, · U+00B7, » U+00BB, ¿ U+00BF, – U+2013, — U+2014, ‘ U+2018, ’ U+2019, “ U+201C, ” U+201D, „ U+201E and € U+20AC.

What the list is chosen to give, and how far that goes:

- **The order of a line.** No character on the list is written right to left, is a digit of a right-to-left script or is a control for direction. By the Unicode rules for mixing directions, a line made only of such characters is shown in the order it is stored. A test reads the direction class of every character on the list from the interpreter's own tables, on every supported version. It has not been tried in a browser.
- **Compatibility forms, not look-alikes.** No character on the list is a compatibility form: a test compares each with its normal form NFKC, and no two of them join into another, so a value is in the normal forms NFC and NFKC as it stands. That shuts out full-width letters, ligatures, the long s and the like. It is not a protection against characters that look like one another. Some on the list do in some fonts: the capital `I` and the small `l`, the digit `0` and the capital `O`, a dash and a hyphen, a curved quotation mark and a straight one, and letters that differ by a small accent. The division slash, the minus sign and the ratio sign are refused because they are not on the list, not because the check knows what they look like.
- **Adding a character.** A character is added to the list only by a decision, because that loosens the check.

## check_register.py

```sh
python3 checks/check_register.py register.json
python3 checks/check_register.py register.json --markdown REGISTER.md
python3 checks/check_register.py register.json --markdown REGISTER.md --agents AGENTS.md
python3 checks/check_register.py register.json --print-markdown
python3 checks/check_register.py register.json --print-instructions
python3 checks/check_register.py --entries ratchet.no-secrets ratchet.root-cause
```

`--entries` prints the rules it names, from Ratchet's `ratchet.json` or the one `--source` gives, as entries to paste into a `register.json`, and reads no register. A rule that names a check gets the status "text only for now".

**It writes nothing.** `--print-markdown` prints `REGISTER.md` as the register generates it, and `--print-instructions` prints the instruction file that the register names with the block brought up to date. Each prints that file to standard output and nothing else, prints nothing and fails when there is a problem, and takes no other option. To put a file in place, print it to a new file and move that over the old one:

```sh
rm -f REGISTER.md.new && python3 checks/check_register.py register.json --print-markdown > REGISTER.md.new && rm -f REGISTER.md && mv REGISTER.md.new REGISTER.md
rm -f AGENTS.md.new && python3 checks/check_register.py register.json --print-instructions > AGENTS.md.new && rm -f AGENTS.md && mv AGENTS.md.new AGENTS.md
```

`rm -f` removes a symbolic link that stands at either name, never what it points at, so neither the redirection nor `mv` follows a link, and `mv` puts a regular file in its place rather than moving the new file into a directory that a link leads to. The new file always stands in the directory the command runs in, under the file's plain name with `.new` after it, never under the file's own path. For an instruction file in a directory, such as `docs/AGENTS.md`, that is `rm -f AGENTS.md.new && python3 checks/check_register.py register.json --print-instructions > AGENTS.md.new && rm -f docs/AGENTS.md && mv AGENTS.md.new docs/AGENTS.md`: only the last two steps touch `docs/`, after the check has refused a link on that path. `AGENTS.md.new` beside the target, `docs/AGENTS.md.new`, would be emptied by the redirection before the check runs, through a link at `docs` if there is one. `upgrade.py` prints these commands for the register it reads.

**What it claims.** Every rule that `register.json` adopts is a rule in Ratchet at the version the register states, and for a copied row its rule, ratchet and source are Ratchet's own, character for character. A row adopted by reference claims less: see "Adoption by reference, the weaker mode" below. With `--markdown`, the file given is exactly what the data generates. With `--agents`, the file given exists and holds none of the placeholders of `templates/AGENTS.md`, a fixed list of exact texts, `PLACEHOLDERS`, a placeholder nested in another one on it on its own, and each one it still holds is named. It does not parse the file, so it does not see a placeholder that is not on the list. The workflow that `init.py` writes passes `--agents AGENTS.md`, so the project's CI stays red until `AGENTS.md` is filled in. The cases are in [test_init.py](test_init.py) and in `test_check_register_fails_on_the_placeholders_of_the_agents_template` in [test_checks.py](test_checks.py): the template fails naming each placeholder, a file with only the handover's `<n>` left fails naming it, this repo's `AGENTS.md` passes, and a missing file fails.

When the register names an instruction file in `instructions`, the check also generates a block of the rules from the register, the same sections as `REGISTER.md` under a heading of its own, and fails unless that file starts with the begin marker and holds one end marker after it, the HTML comments `BEGIN` and `END` in `check_register.py`, which hold `ratchet:begin` and `ratchet:end` with one space on each side between the comment's marks, each alone on its line, at its start, ending in LF, and between them, byte for byte, the block. A line that holds `ratchet:begin` or `ratchet:end` in any other form, in any case, anywhere in the file, inside a code block or a comment too, is a broken marker. Nothing else in the file is read: it must be UTF-8, and the rest of it is the project's own, never parsed. `--print-instructions` prints the file with the block between the markers, or, in a file with no marker, at its start followed by an empty line, and prints the block alone for a file that does not exist. It changes no other byte of the file, and it prints nothing where the markers are broken or the block is not at the start, where the file is not UTF-8 or not a plain file, or from a register that does not pass. So the project keeps its rules where its agents read, and the check sees the text of each rule, not a marker that stands for it.

**Where the block stands.** The begin marker is the first line of the file: no byte stands before it, not an empty line and not a byte order mark. So no text before it can open a code block, a comment, or an element such as `<div hidden>` or `<details>` that puts the block in an example or out of sight, and the check needs to read no Markdown to know it ([D-2026-11-16-strict-forms](../decisions/D-2026-11-16-strict-forms.md)). The start is the smaller rule: any other place would need a reader of Markdown that knows every way to open a code block or an HTML block. The cost is that the block comes before the project's own heading, and that a file which must start with something else, such as front matter, cannot hold it.

**How a marker word is found.** The words `ratchet:begin` and `ratchet:end` are found in any ASCII case, on every line, by a plain search. Each stands once, and each line that holds one is exactly its marker. A word with a character outside printable ASCII in it, such as a letter of another script, a full-width colon, a character that shows as nothing, or NUL or DEL, is not that word: it is text the check does not read. A decoy built that way is a deliberate act, outside [the threat model](#the-threat-model). The search is ASCII-only, so a dotless `ı` does not stand for `i`.

**The path of the instruction file.** Before anything is read or written there, every part of the path, from the directory of the register down, is checked: no part may be a symbolic link, each part before the last is a directory that exists, and the file, resolved, stays inside the directory of the register. The form of `instructions` already refuses `..`, `.`, an empty part and an absolute path. The file is read without following a link at its last part (`O_NOFOLLOW`), by the check and by `generate.py`, which checks the path the same way before it reads or writes this repo's instruction file. A project whose instruction file is a link, such as `CLAUDE.md` pointing at `AGENTS.md`, names the file the link points at, or replaces the link with a regular file. The register, and each file named with `--markdown` and `--agents`, is taken by the path as given and refused, in every mode, when that path holds a part `..`, or passes through a symbolic link below the working directory or the enclosing git root, so a register reached through a link that git tracks is not checked as if it were the project's (see [No write through a link](#no-write-through-a-link)).

**What it does not claim, about the block.** It does not read the rest of the file, so text after the block that contradicts it is the project's own; the block says that `REGISTER.md` takes precedence. A marker word disguised with a character outside ASCII, or written as an HTML entity such as `&#58;`, is not found, so a copy of the block under such a marker is text the check does not read. That is outside the threat model. A directory on the path that is replaced by a link between the check and the read is not caught: the threat is a link committed to the repo, not another process on the same machine.

An adopted rule may carry a translation of its rule: a language code, the text, and the sha256 of the rule's English text, its UTF-8 bytes in lowercase hex. The check fails when that sha256 is not the one of the rule's text in Ratchet at the version the register states, and names both. So an upgrade that changes the rule fails until its translation is made again, and `upgrade.py` names it. Only the rule is translated, not its ratchet: the rule is what the people who work in the project's language must follow, and the ratchet names a check, its files and its commands, for whoever builds it. The translation stands in `REGISTER.md` and in the block, in a table of its own under the English rules, which stay the rule. It is text from the fixed list of characters, like every value: Latin script, Swedish letters among them, passes, and every other script is refused.

**Adoption by reference, the weaker mode.** A Ratchet row has two modes. A copied row is as above, and is the only mode in which the check sees the text of a rule. A row by reference holds no rule text: it names the key, in `stands_in` the Markdown file where the rule stands in the project's own words, which is the wording in force, and in `sha256` the hash of the rule and its ratchet in Ratchet at the register's one `ratchet_version`: the sha256 of the UTF-8 bytes of the rule, one line feed and the ratchet, in lowercase hex. It may carry `status` and `where` on the same terms as a copied row, and nothing else. The file holds the marker line once, `MARKER` in `check_register.py`: an HTML comment that holds `ratchet:rule`, one space and the key, with one space on each side between the comment's marks, alone on its line and ending in LF. Nothing else in the file is read.

To take the sha256 of a rule, read it from `ratchet.json`, so that no rule text passes through the shell, where a backtick, a quote or a `$` in it would change it. With the key in place of `ratchet.fresh-context`:

```sh
python3 -c 'import hashlib, json, sys; r = [r for r in json.load(open(sys.argv[1], encoding="utf-8"))["rules"] if r["key"] == sys.argv[2]][0]; print(hashlib.sha256((r["rule"] + "\n" + r["ratchet"]).encode("utf-8")).hexdigest())' .ratchet/ratchet.json ratchet.fresh-context
```

`test_checks.py` runs this command through `/bin/sh` on every rule of Ratchet that holds a backtick or a quote, and on a rule made up in the test that holds a backtick, both quotes, `$`, `$()`, `\` and `%`, since no rule of Ratchet holds `$` today. A row whose sha256 is wrong fails, and the check prints the sha256 it expects, so the check itself gives the right one too. Set it only after the wording in the file has been read against the rule.

What it claims, for a row by reference: the key is a rule in Ratchet at the version the register states; the sha256 is that rule's and its ratchet's, so an upgrade that changes either fails until the sha256 is set again; `stands_in` has the path form of `instructions` and is checked on its path the same way, with no link on it, no `..` and `.md` only; the file exists, is a plain file and is UTF-8; every line in it that holds the word `ratchet:rule`, in any ASCII case as the words of the block are found, is an exact marker line; the marker of each row that names the file stands in it once; and no marker there names a key that no row by reference names that file for. It refuses a row with both rule text and `stands_in` or `sha256`, a row by reference with a translation, `stands_in` that names the instruction file, in any case, `stands_in` or `sha256` on a rule of the project's own, and a field it does not know. On a pass it prints, for each such row, the label the decision gives, with "guarded" in place of the decision's "built" so that "built" means only a rule's enforcement on the same screen, which `REGISTER.md` shows too: "Adopted by reference, the weaker mode. The wording in force is the project's own, in the file named. The check sees a marker, not the words. The wording is not guarded against softening." It says "guarded" only when the register copies the row of `ratchet.owner-paths`, not by reference, with the status `built`: the check reads the register's own claim, not the host. A row of `ratchet.owner-paths` by reference does not count, since the check does not see its wording, and that wording is what protects the others.

What it does not claim, for a row by reference: it does not read the words under the marker, or whether they say what the rule says, or whether any harness loads the file. It reads no Markdown, so a marker line in a code block or a comment counts as a marker. It reads only the files that rows by reference name, so a marker in another file is not seen. A softened wording is caught only by the owner's review of the file, which `ratchet.owner-paths` asks for and the check does not see. By the shared threat model, this mode gets its fixtures and no further hardening.

A register with rows by reference may mix them with copied rows and name an instruction file. `REGISTER.md` is optional for it: with `--markdown`, a file that is not there is not a failure, and the check says so; a file that is there, or anything else at that path, must be what the register generates. Where it is generated, and in the block, the rows by reference stand in a table of their own, "Rules adopted by reference", with the file each names and its label, and no rule text. `--print-markdown` and `--print-instructions` print that table, read no file a row by reference names, and never print a marker line: the marker is the project's to put in its own file. `upgrade.py` says, for a changed rule adopted by reference, whether its sha256 still matches, and when it does not, prints the new one and asks the project to read its wording again.

**Adopted in part.** A row by reference may be adopted in part, when the project's own wording states the rule's core but not every clause. No field is added, and the clauses stand in the row's `where`, which is then exactly `Not stated here: <clause>; <clause>.`: the phrase `PART` in `check_register.py`, the clauses that the project's wording does not state, each joined to the next by a semicolon and one space, and one period at the end. One clause is `Not stated here: <clause>.`. A clause is not empty, holds a letter or a digit, has no space at its ends, holds no `;` and no period followed by a space, so no sentence follows the list, does not end in a period, and stands once. It is text like every value, and may hold code between backticks. A row without the phrase claims the whole rule, as before. When the wording leaves out any part of a sentence of the rule, list that whole sentence as one clause, not the part. A row by reference of a text-only rule takes a `where` only as this phrase.

What it claims, for a row adopted in part: its `where` is in that one form; the row is by reference, since a copied row holds the whole rule and a rule of the project's own stands in full; it is not `built`, since the rule is not fully held, so a rule that names a check has the status `text only for now`; and on a rule that is text only, whose row has no `status` and otherwise no `where`, the phrase is the one `where` it may have. The words "not stated here" anywhere in a `where`, in any case, fail as a broken phrase unless they stand in that one form, so a list is never half read. A value holds only the characters of the fixed list, so a Cyrillic letter, a full-width letter or a character that shows as nothing fails before that, as every value does. A clause is text by itself, so a pair of backticks stands in one clause: a semicolon inside code, as in ``Not stated here: `one; two`.``, splits the code and fails, and so does a semicolon in code that splits nothing. On a pass it prints, before the label of every row by reference, "Adopted in part. Not stated in the project's wording: " and the clauses, and `REGISTER.md` and the block show the same in the table "Rules adopted by reference". The summary counts the rows adopted in part. `upgrade.py` keeps the phrase in the entry it prints, whether the rule comes to name a check or comes to be text only, asks that the clauses be read against a changed rule too, and leaves it out of the entry of a removed rule for `own`, which holds Ratchet's whole text. `init.py` in adopt mode names the option in one line.

What it does not claim, for a row adopted in part: the phrase split by marks or other characters, as in `` `Not` stated here`` or `Not-stated-here`, or with a letter outside ASCII, as in `Nót stated here`, is plain text in a `where` and not found; that is outside the threat model. It sees the phrase, not whether the clauses listed are the ones the project's wording leaves out, nor whether the wording states the rest. A row that claims the whole rule while its wording leaves a clause out passes as before, and a clause listed that the wording does state is not seen either. Both are for the owner's review of the register and the file, as for every row by reference.

**Against which threat, adopted in part.** A project whose wording holds a rule's core but not every clause either adopts far fewer rules than it follows, or puts a marker on wording that says less than the rule and claims the whole of it. With the phrase, the gap is written in the register, labeled wherever the row is shown, and a row with a gap cannot be marked built. Not against a list of clauses that is wrong on purpose: see what it does not claim.

A rule of the project's own may carry `status` and `where`, and does not have to. When it does, they are read as an adopted rule's: the rule's ratchet starts with "Check:", the status is `built` or `text only for now`, a built check says where it lives, and a `where` needs a status. Each own rule with a status gets a row under "Where each check stands", after the adopted rules, and the summary counts them apart.

**Against which threat.** An agent, or a person, softens an adopted rule in the project's own copy, or adds a rule of its own under Ratchet's name, and nobody notices because the register still looks like Ratchet. With an instruction file named: the copy of the rules in the file the agents read is edited by hand, or drifts from the register, or a second, softer copy is put next to it under a second marker. With a translation: the English rule changes and its translation in the block still says what the old rule said. With a row by reference: Ratchet changes the rule or its ratchet and the project's wording is never read again, the marker is lost or doubled in an edit, a copy of the marker is put next to it, or the row names a file outside the repo or behind a link. Not against a wording softened on purpose under its marker: see what it does not claim.

**The data file.**

```json
{"project": "the project's name",
 "ratchet_version": "0.11",
 "instructions": "AGENTS.md",
 "adopted": [{"key": "...", "rule": "...", "ratchet": "...", "source": "...",
              "status": "built", "where": "path to the check",
              "translation": {"language": "sv", "text": "...", "sha256": "..."}},
             {"key": "...", "stands_in": "docs/RULES.md", "sha256": "...",
              "status": "text only for now"}],
 "own": [{"key": "project.key", "rule": "...", "ratchet": "Check: ...", "source": "",
          "status": "built", "where": "path to the check"}]}
```

`status` and `where` stand on a rule whose ratchet starts with "Check:", and only there, but for the `where` of a row adopted in part, below. The status is `built` or `text only for now`, and a built check says where it lives. An adopted rule that names a check must have a status, and an own rule may. `instructions` and `translation` may be left out. `instructions` is a path relative to `register.json`: parts of letters, digits, `.`, `_` and `-` joined by `/`, none of them `.` or `..` and none starting with `-`, ending in `.md`, at most 200 characters. A language is two or three lowercase letters, with a region of two capitals after a hyphen if needed, such as `sv` or `pt-BR`. A translation has exactly the three fields, and only an adopted rule has one. A row by reference has `key`, `stands_in` and `sha256`, and `status` and `where` on the terms above, and may have its `where` in the one form of a row adopted in part, `Not stated here: <clause>; <clause>.`, on any rule, with no status `built`; `stands_in` has the form of `instructions`, and `sha256` is 64 characters `0` to `9` and `a` to `f`.

**The cases in the data.** Each is a `register.json` under [fixtures/register/](fixtures/register/) and a test in [test_checks.py](test_checks.py).

In a fixture that fails, every character outside ASCII stands as its JSON escape, such as `\u05be`, so that the file shows which character it holds and none of them hides or reorders a line of the fixture itself.

**The cases in the generated file** are the fixtures whose names start with `md-`. Each has a clean `register.json` and a `REGISTER.md` that is not what it generates: a row softened, indented, put in a comment or moved by an escaped pipe, a line added, or the file missing. All fail for the same reason, in [test_checks.py](test_checks.py).

**The cases in the instruction file.** Each has the register of `block-clean`, which names `AGENTS.md`, adopts a rule with a translation into Swedish, and has an own rule whose check is built. - A translation is in Latin script only, from the fixed list, and a rule has one translation, in one language.
- For a row by reference it sees a marker, not the words: see "Adoption by reference, the weaker mode" above. The label's "built" repeats the register's claim for `ratchet.owner-paths`, which the check does not compare with the host.
- The block is written with LF. A project whose instruction file has CRLF keeps it in the rest of the file, and the block, with its markers, has LF.
- It runs from the version of Ratchet it was fetched at. The project's workflow pins that version by commit, and a change to the workflow is a change to a check (`ratchet.owner-paths`).

## expected_tests.py

```sh
python3 checks/expected_tests.py
```

The reference check for `ratchet.expected-tests-ran`. It runs in a step of its own in CI, and it runs the suite in a process of its own: it starts [suite_runner.py](suite_runner.py), which runs `unittest discover -s checks` with unittest's own text runner, and reads what the runner records. A test that loads fixtures is a `FixtureTest`, from `suite_runner.py`, and loads each one by its name under [fixtures/](fixtures/), with `fixture_bytes`, `fixture_text`, `fixture_file` or `fixture_directory`. The last two give a copy in a scratch directory, made from the bytes that were loaded, and the check under test is run on the copy.

**What it claims.** In the run, every test that discover collects ran once under its id and passed, with exactly one outcome record, nothing ran that was not collected, the run finished, and every file under `checks/fixtures/` was loaded, with the bytes it held before the run, by a test that passed. Otherwise the check prints each problem and exits 1, whatever the suite's own exit status was.

**Against which threat.** Tests dropped by mistake, while the suite still looks green: a test skipped, errored or not prepared, a class or module whose set-up skips, a module that no longer imports, a run that exits before it is done, a run that returns before it is done because it was interrupted, told to stop or stopped at the first failure, two tests under one id so that one hides the other, a fixture added and never tested, or a test that names a fixture that is gone. A green summary says only that the tests that ran passed, not that the tests that were meant to run did.

**What it does not claim.** It does not stop test code written to defeat it. Such code runs with the same rights as the check: it can write records of its own, rewrite the runner or this check, or pass without testing anything. A change to `checks/` is read by the maintainer before it is merged (`ratchet.owner-paths`), and that reading is what stands against it.

**How it works.**

- **A process of its own.** The check makes a temporary directory, starts the runner as a child process with the path of a record file in it, waits for the child and reads the file. It does not run in the process it watches, so nothing the tests do to unittest's result, to its hooks or to the exit of their own process changes what the check sees: an exit is a missing record, not a pass.
- **What was collected.** Before the run, the runner writes a record "collected" for every test in the suite that discover returns, each with a number of its own, and the completion record holds unittest's own `countTestCases()` of the suite, taken before the run. A test that starts uses the number it was collected under. One that was not collected gets a new number, and fails the run.
- **The outcomes come from the runner.** The runner's result class takes the outcomes from unittest's result object: passed, failed, errored, skipped, expected failure or unexpected success. When a test stops, the runner writes one record "outcome" for it, with every outcome unittest gave it while it ran, in order. So a test that fails and then errors in `tearDown`, or whose subtests fail twice, has one record, and a second record of one instance is always a problem. An outcome of a subtest is an outcome of its test. An outcome given outside the run of its test, such as one given to a test after it stopped, is a record of its own at once. An outcome of a `setUpClass`, `tearDownClass`, `setUpModule` or `tearDownModule` has an instance that was never collected and never started, and fails the run.
- **The tests write only what they loaded.** A `FixtureTest` writes the fixture's name and the sha256 of the bytes it read, with the instance that was running. A load outside any test, as in `setUpClass`, does not count.
- **The completion record.** After unittest has printed its summary, the runner writes one last record with the number of tests collected, of tests run, of outcomes and of loads. A child that exits early, with `sys.exit` anywhere, `os._exit`, a `KeyboardInterrupt` or another error the runner does not catch, or that is killed, leaves it out, and the check fails. A run that returns early writes it: under unittest's Ctrl-C handler, after `result.stop()` sets `shouldStop`, or with `failfast` after a failure. The tests it did not run were collected and have no start, and the check fails on each.
- **Read strictly.** One JSON object per line, each ending in a line break, in UTF-8, parsed by the strict reader every check uses, `registry.strict_loads`: a field twice, `NaN` or `Infinity`, or a line nested too deeply is a problem, not a crash. The kind of a record is text, and its type is checked before the kind is looked up. Each kind of record has exactly its fields, each of its own form: an instance is a whole number from 1, the outcomes are a list of one or more of the six, a test is a name of one line with no lone surrogate, a fixture is a fixture's name, a sha256 is 64 lowercase hex digits. Anything else, a line cut off, a record after the completion record, a test collected after the run started, fails the run.
- **The comparison.** The check fails on: an exit status other than 0, or a signal; no completion record, two of them, or counts that disagree with the records; a test that was collected and did not run; a test that ran and was not collected, which covers no fixture; a test whose outcomes are not exactly one "passed", or that started and has no outcome; a second outcome record of one instance, after which the instance does not count as passed; an id that ran more than once; an instance collected twice or started twice, a start or an outcome that names another test than its instance; a fixture that no test that passed loaded with the bytes it held before the run; a load of a fixture that does not exist, or of other bytes; a fixture that changed while the suite ran; a suite that ran no tests.
- **The expected set.** The tests are the ones discover collects, and the fixtures are read from the directory, not from a list in a test and not from Markdown. Every file is one fixture. A file whose name starts with a dot, or holds a character other than letters, digits, `_`, `.` and `-`, fails, and so does a link.

**The cases.** Each is a test in [test_expected_tests.py](test_expected_tests.py). The tests in `Runs` run the check, as CI runs it, on a small suite in a scratch directory whose fixtures are a copy of [fixtures/tests-ran/tree/](fixtures/tests-ran/tree/). The tests in `Records` give the reader of the records a file that no runner wrote.

**Known limits.**

- Test code that defeats the check on purpose, as above.
- It does not see whether a test uses what it loads. A test that loads a fixture and then checks something else passes. One mutation per case shows that a test uses its fixture (`ratchet.test-can-fail`), and the PR that adds a case shows the mutation.
- The outcome is a test method's, not a subtest's. A method that loads many fixtures in subtests counts for all of them when it passes, and fails all of them when one subtest fails.
- A test can still open a fixture by its path. Such a test is not counted, so the fixture stays expected and the run fails unless another test loads it.
- It relies on unittest's runner and on discover. A test that discover does not collect, because its module's name does not start with `test`, is not expected. Another runner, such as pytest, needs a check of its own.
- It reads how unittest reports the set-up and tear-down of a class or a module: as an outcome of an object that is not a test, the same in 3.9 and 3.12. Every such outcome fails the run.
- `python3 -m unittest discover -s checks` still runs the suite on its own, and records nothing. Only `checks/expected_tests.py` checks that every expected test ran, and it is the one step of the job `own` that runs the suite. The release workflow still runs the suite with `unittest discover`.

## No write through a link

```sh
python3 -m unittest discover -s checks -p test_writes.py
```

What holds, and what does not, when a symbolic link could lead a script here to write outside the repo.

**What is guaranteed.**

- **`check_register.py` never writes.** It is the check that projects run. It prints `REGISTER.md` or the instruction file to standard output and writes no file. The sweep below allows no write in it.
- **The documented save commands never touch anything outside the repo, when they are run from inside the real repo directory.** They are the commands under [check_register.py](#check_registerpy), in `STARTING.md` and `UPGRADING.md`, and the ones `upgrade.py` prints. The new file always stands in the directory the command runs in, under a plain name, and `rm -f` removes a link at that name before the redirection, never what it points at. The two commands differ in their target. The one with `--print-markdown` writes `REGISTER.md`, a plain name in that same directory, and `rm -f` removes a link there before `mv`. The one with `--print-instructions` names the instruction file's own path, which may be nested: the check refuses a link on every part of that path before it prints, and only then do `rm -f` and `mv` run on it. `upgrade.py` quotes the script and the paths, and ends the options of `rm` and `mv` with `--`. A part of `instructions` may not start with `-`.
- **No script writes bytecode.** Every script in `checks/` and `maintain/` that runs as a program sets `sys.dont_write_bytecode` before it imports a module from `checks/` or `maintain/`, so Python writes no `__pycache__` next to the checks. `expected_tests.py` runs the suite with `-B` and `PYTHONDONTWRITEBYTECODE`, `suite_runner.py` sets the variable for every Python the tests start, and the tests that start `python -m unittest` or `python -c` pass `-B` too. Both workflows, `checks.yml` and `release.yml`, set `PYTHONDONTWRITEBYTECODE` for the job. `python3 -m unittest`, run by hand without `-B` or the variable, imports the tests and the checks before any code of theirs runs, and so writes bytecode.

**What the guards in `generate.py` and `init.py` are.** They are a safety net against mistakes, and against a tree that only adds links. They are not a boundary.

- `generate.py` runs code from the very tree it writes into. A pull request that adds a link can just as well change `generate.py`, and no guard inside `generate.py` can stop that.
- `init.py` is run by the owner, in their own project, at its start.
- Within that, `generate.py` writes only through `registry.write_file`, behind the gate `registry.refuse_links`. The gate takes the repo by the path as given and refuses it when the path holds `..` or passes through a link below the working directory or the enclosing git root, and when `register.json` is a link. It refuses a link that git tracks in the repo, or, where git cannot say, any link. `write_file` refuses a link on any part of the path it writes. The scan of Markdown files, in the root, `templates/`, `checks/` and `maintain/`, takes in no link: an untracked link in one of those folders, or a folder that is itself a link, is not scanned.
- `init.py` takes its root from `PWD` when that names the directory it runs in. It refuses one that passes through a link, checks every file it would write for a link on its path while it plans, and does so again when it writes. So `--check` never says "would write" for a file a real run refuses, and a real run writes nothing when any file would be refused.

**What is not covered.**

- Entering the repo through a symbolic link to a directory. `init.py` alone reads `PWD`, and refuses a root through a link only when `PWD` names it. `generate.py`, `check_register.py` and the save commands take the working directory as the system gives it, already resolved, so they cannot see such a link even when `PWD` is set. The guarantee for the save commands holds when they run from inside the real repo directory.
- `..` in `PWD`, in the path `generate.py` was run by (`__file__`), or in `--source`.
- An anchor of the path check, the working directory or the enclosing git root, that is itself a link.
- Code written to get past the sweep of writes. The sweep catches mistakes, not disguise.
- `python3 -m unittest` run by hand without `-B` or `PYTHONDONTWRITEBYTECODE`, which writes bytecode before any code of the checks runs.
- Another process of the same user racing a tool between a check and its use, and an attacker who already controls the user's account, the Python install or the `git` on the path.

**The cases**, in [test_writes.py](test_writes.py), [test_init.py](test_init.py) and [test_upgrade.py](test_upgrade.py). The trees are made in a temporary directory when the test runs and never committed: a link committed here would make `generate.py` refuse to run on this repo. A git work tree is made there with `git init`, its name, mail and `gc.auto` set in that repo only. Each failing case compares every entry under the temporary directory, before and after the run.

**The sweep.** A test reads every script in `checks/` and `maintain/` with `ast` and fails on a call that writes anywhere but in the functions named for that script in `WRITERS`:

- `open`, `io.open`, `io.FileIO`, `codecs.open` and `os.fdopen`, unless their mode is left out or is a literal string with none of `w`, `a`, `x` and `+`.
- `os.open`, unless its flags are `os.O_` names that only read, or `getattr(os, "O_NAME", 0)` of one, joined by `|`.
- Arguments with `*` or `**`.
- The methods of `pathlib` that write, and the functions of `os`, `shutil` and `tempfile` that write, move, remove, link or make.
- `__import__`, an import of `pathlib` or `importlib`, a writing module imported under another name, and `open` used without being called.

`check_register.py` and `generate.py` must have no such call, and `registry.py` only in `write_file`. `run_pinned.py` writes only in the new directory that `main`, or `stored_blob` for `init.py`, makes with `tempfile` and removes at the end: the empty git directory, home and config that `Git.__init__` makes to read the store through, and the tree that `export` writes. The clone into a missing store, and the objects a fetch adds to it, are git's. `init.py`'s two functions that write must call `registry.guard_path` first. A sample file shows each kind of write found and each kind of call that only reads let through. The files `test_*.py` are not swept: they are the suite, not the checks, and they write only in directories they make with `tempfile`. The sweep reads code, not what it does: a write through `getattr`, `eval`, a subprocess or a module outside `checks/` and `maintain/`, or any spelling written to get past it, is not seen. A change to `checks/` or `maintain/` is read by the maintainer before it is merged (`ratchet.owner-paths`).

## upgrade.py

```sh
python3 .ratchet/checks/upgrade.py register.json
```

This one checks no rule in a register. It is the upgrade path for a project ([UPGRADING.md](../UPGRADING.md)), in one command. `.ratchet` is a git clone of Ratchet. The command fetches its tags from `origin`, reads the version the register states, and compares that tag with the latest release, or with the one given with `--to`. `--no-fetch` uses the tags the clone has. Offline, `--from` is the `ratchet.json` of the version the register states, taken from its tag, and `--source`, by default the `ratchet.json` next to the script, is the newer Ratchet: `python3 .ratchet/checks/upgrade.py register.json --from .ratchet/from.json`. `--from` is not given with `--to` or `--no-fetch`, and `--source` only with `--from`.

**What the one command claims.** It runs git on the clone the script stands in, and on nothing else: no `GIT_` variable of the caller is used, and git does not look for a repo above the clone. It reaches no network but the clone's `origin`, through `git fetch --tags`. It refuses, with exit 2 and what to do, when:

- the clone is not a git work tree of its own, as when `.ratchet` is a copy. It names `--from`.
- the fetch fails. It names `--no-fetch`.
- the version the register states has no tag `v` and that version. After a fetch, that version was never released, and it lists the release tags. With `--no-fetch`, in a shallow clone, it says the clone holds only the tags it was cloned with, and prints the command that fetches them.
- `--to` is not a version, or its tag, such as `v9.11-rc1` or `v09.10`, or names no release tag.
- the clone has changes to files git tracks in it, or is on a branch and must move. Neither is moved. For a clone on a branch it prints the command that moves the clone, detached, to the release, whose `upgrade.py` runs the same command, and the command that goes back to the branch, which stays where it was.

A release is a tag `v`, a major and a minor version, with no leading zero, and nothing else. Any other tag is not listed, is never the latest, and is refused by `--to`. The latest is the highest by number, so `v0.10` comes after `v0.9`. When the release is older than the register's version, it fails with exit 1, and when it is the same, it says the register is not behind. Otherwise it reads `ratchet.json` at the register's tag with the reader for an older version below, and checks the register against it, as the offline mode does, before anything moves. Then it moves the clone, detached, to the commit of the release, prints the commit it was at and the command that moves it back, and runs the `upgrade.py` of the release, which knows that release's forms, with the register's path after `--`. That one says how many releases after the register's version the release is, and which, prints the steps as below, the commands to run after with the path of the script as typed, and the commit to pin `.github/workflows/ratchet.yml` to. A register with rows by reference, in a project with no `.github/workflows/ratchet.yml`, which adopt mode never writes, is told instead, with the same commit, the command that copies `checks/run_pinned.py` again and the lines for the local check script and for the CI step, as `init.py` prints them ([run_pinned.py](#run_pinnedpy)), so it need not run `init.py --check` for them. It writes no file of the project, and changes `.ratchet` only through git: its tags and its checkout.

**A register before 0.12.** The one command reads no `ratchet.json` before 0.12. For a register on 0.3 to 0.11 it moves nothing and prints, with exit 2, the commands of the first leg: fetch the tags, move `.ratchet` to `v0.11`, run that `upgrade.py` with `--to 0.13 --no-fetch`, and then this command with `--to` the release. A register on 0.2, or a target before 0.13, is refused.

**`--behind`.** `python3 .ratchet/checks/upgrade.py register.json --behind [--no-fetch]` reads `register.json` as strict JSON and its field `ratchet_version` alone, so a register of any form from 0.3 on will do. It fetches the tags as the one command does, compares the releases by number, and prints one line: how many releases come after that version, and which. It moves nothing and writes nothing. Exit 0: not behind. 1: behind. 2: it cannot tell: no release tag, a failed fetch, a register that is not strict JSON, a `ratchet_version` missing or not `MAJOR.MINOR`, a version newer than every tag, or 0.2, whose register was Markdown. The job `behind` of `templates/ratchet-checks.yml` runs it on the weekly `schedule` only, from the pinned checkout. Whether anyone reads that run is outside the claim.

**What it claims, in both modes.** It reads three data files strictly, and when they are valid it prints, rule by rule, what is different between the two versions of Ratchet and what the register must do about it:

- a rule the register adopts that changed: which of its status, enforcement, rule, ratchet and source changed, and the entry to put in its place. The entry is the newer rule, character for character. It keeps the status and the place of the check when the rule still names a check, gets `text only for now` when its ratchet now names one, and loses both when it is text only now. When the ratchet of a rule marked `built` changed, it says to look at the check again.
- a rule the register adopts that was removed: take it out of `adopted`, and, to keep it, add the printed entry to `own`. The entry is the older rule with the fields of an own rule, `key`, `rule`, `ratchet` and `source`, and the status and the `where` it had, which an own rule may have from 0.10. A translation is dropped, since an own rule has none. Its key is the prefix of the register's first own rule, or one made from the project's name, then a dot and the name in Ratchet's key, with `-2` and so on when that key is taken. A name that gives no prefix, or gives `ratchet`, gives `project`.
- when every rule the register adopts was removed: adopt at least one rule, from the new rules, or from the rules to start with when there are no new ones, each printed with its entry. A register that adopts no rule does not pass `check_register.py`.
- a new rule: its key, under the title of its part in `ratchet.json`. With `--new-rules full`, or when the register must adopt a rule, the entry to add. The one command passes `--new-rules` on to the `upgrade.py` it runs after the move, when that release is 0.17 or later.
- a rule that changed or was removed and is not adopted: its key, with nothing to do.
- when the fields of `ratchet.json` differ between the two versions, at the top or in its rules: which are new and which are gone, and that a copy of a Ratchet check kept in the project, or a check of the project's own, that reads `ratchet.json` must be updated. The checks in `.ratchet` need nothing, and nothing in the register changes. The older file holds no field the newer one does not know, so a field at the top is new or gone only when a later version changes the form. A field of a rule is new when some rule of the newer file holds it and no rule of the older one does, and gone the other way round.
- a rule the register adopts with a translation, whose rule changed: the translation must be made again. The entry is printed without it, with the sha256 of the new text. A translation of a rule whose text did not change, only its ratchet or its source, stays in the entry.
- a rule the register adopts by reference, whose rule or ratchet changed: that its sha256 no longer matches, the new one in the entry, which keeps `stands_in`, the status and the `where`, and that the project reads its own wording in the file again, with the new rule and its ratchet printed under the entry to read it against. The register passes against the version it states until the owner moves `ratchet_version`, and fails from then until the sha256 is set. When only the source changed, the sha256 still matches and it says so. A removed rule adopted by reference gets Ratchet's older text in the entry for `own`, and the step names its marker line to take out of the file.
- the commands that put `REGISTER.md` in place again, and, for a register that names an instruction file, that file too, as [check_register.py](#check_registerpy) gives them, with the path of the file, and the command that checks them. Each command gives `check_register.py` its options first and the register's path after `--`, so a path that starts with `-` is read as a path. A register with rows by reference after the steps, and no `REGISTER.md` beside it, is not told to print one: it may leave it out, and the command that checks it has no `--markdown REGISTER.md`.

Before it prints a step, it checks that the register passes `check_register.py` against the older Ratchet, and that the register with every step done, and no new rule adopted, passes it against the newer one. When the register adopts a removed rule, it checks that register twice: with each removed rule taken out, and with each also moved to `own` by the printed entry. When every adopted rule was removed, it checks both with every rule it printed to choose from adopted. A register that does not pass against the older Ratchet is not upgraded, so one that adopts no rule from Ratchet, or a rule that is not in the version it states, still fails. Offline, it writes nothing, runs no git, and reads no file but the three it is given.

**Against which threat.** Mistakes and drift, within [the threat model](#the-threat-model): a project that upgrades by hand misses a rule that changed, keeps a softened copy, or keeps a status that no longer holds, and the register still looks like Ratchet's. A project that compares the wrong two versions, by hand, from a clone that lacks the tag it needs, or from a newer clone with an older script, gets steps for versions it is not on. An upgrade that moves `.ratchet` by hand loses the commit it was at, or moves a clone someone works in.

**The older `ratchet.json`.** It is read with the same strict reader, `registry.validate`, with two things left out, because they are not what an upgrade compares: the files of its reference checks and of the decisions in `kept_by` are not looked for, and its budget is not counted. An upgrade starts from 0.12 or later. The `ratchet.json` of `v0.12` and of `v0.13` pass the reader, and so does this one. One that lacks the cap, the principles or the `since` of an experimental rule, or holds `date` or `sources`, as every version before 0.10 does, fails. A field it does not know, a field twice, a rule of another form or bytes that are not UTF-8 fail too.

**What it does not claim.**

- It does not see that `origin` is Ratchet, or that a tag is the one Ratchet released. It trusts the clone's `origin` and its tags, as the README's clone does. Someone who controls them, or the clone, is outside [the threat model](#the-threat-model).
- It prints the steps for a register of 0.12 and later only. A test compares the printed first leg with the four commands, character for character. That they lead through the real `v0.11` and `v0.13` to a register that passes was shown once by a run from a register that the `init.py` of `v0.9` wrote, not by a test. The tag ruleset locks those tags, so only the printed text can break it.
- Offline, it does not see that the file given with `--from` is the one at the tag. It checks that the register passes against it and that the version is older or the same, and that two files that name the same version have the same rules.
- It does not see whether a check marked `built` exists or works.
- It does not list a rule that only moved to another part, or whose reference check changed. Neither changes the register.
- It does not say why a rule changed. The changelog of the newer Ratchet does.

**The cases.** Each is a test in [test_upgrade.py](test_upgrade.py). The fixtures are under [fixtures/upgrade/](fixtures/upgrade/): a Ratchet 9.8 and a 9.9 with every kind of change between them, a register on 9.8, a smaller 9.8 and 9.9 under `removed/`, in which a rule that names a check and a rule that is text only are removed and one rule is added, and under `released/0.12/` the `ratchet.json` of the tag `v0.12`, with a `register.json` that the `init.py` of `v0.12` wrote in adopt mode, two rows by reference, one of whose rules changed in 0.13, and the `AGENTS.md` that holds their marker lines. `released/0.3/ratchet.json` and `released/0.9/ratchet.json`, the `ratchet.json` of those tags, are data for `test_budget.py` too. Under `released/0.9/` is also the `register.json` that the `init.py` of `v0.9` wrote, which the cases of `--behind` read.

The cases of the one command are in the class `OneCommand`. A git repo made in a scratch directory stands in for Ratchet's `origin`, with this repo's checks and the `ratchet.json` of `old/` at `v9.8`, of `new/` at `v9.9`, and the rules of 9.9 as `v9.10`. The `upgrade.py` at `v9.10` prints a line of its own first, so a test that moves the clone there sees whether that script ran. Two tags are not releases: `v9.11-rc1`, a lightweight tag after the latest, and `v09.10`, an annotated tag with a leading zero, both at the commit of `v9.10`. The project is a scratch directory with a register from `upgrade/` and a clone at a tag in `.ratchet`. No test reaches the network. Every run checks that no file of the project changed and no file git tracks in `.ratchet`.

## init.py

```sh
python3 .ratchet/checks/init.py --check            # say what it would write and what it skips, write nothing
python3 .ratchet/checks/init.py                    # write it
python3 .ratchet/checks/init.py --name "My project"
python3 .ratchet/checks/init.py --solo             # one agent and no control room
python3 .ratchet/checks/init.py --adopt ratchet.no-secrets   # adopt mode: write register.json with that row by reference
```

This one checks no rule in a register. It is the start of a project, run from the root of the project's repo with Ratchet cloned into `.ratchet`, as the [README](../README.md#start-here) says.

**What it claims.** It writes what the steps of "Start here" set up by hand, and never overwrites a file:

- `AGENTS.md` from `templates/AGENTS.md`, with the project's name in its title. The rest of the template, with its parts in angle brackets, is the project's to fill in. The two lines that mark the parts for a team, HTML comments holding `team` and `/team`, as `TEAM` in `init.py` spells them, are not written. With `--solo`, for one agent and no control room, neither is what stands between them: the line that the control room reads its handbook, and the section on skills. The marks must stand in pairs, each on a line of its own, one pair at least and none inside another, or it does not run.
- `CLAUDE.md` from `templates/CLAUDE.md` as it stands. Its one job is to make Claude Code, which reads `CLAUDE.md` and not `AGENTS.md`, load `AGENTS.md`, with its import line `@AGENTS.md`, and the template must hold that line on a line of its own, or it does not run. It is written only when `CLAUDE.md` is missing and the register is `init.py`'s own: `register.json` is missing, or is a plain file of the very bytes `init.py` would write. Such a register names no `CLAUDE.md`, in `instructions` or in `stands_in`, in any case of its letters, and a start cut off before `CLAUDE.md` is completed on the next run, since its register is still `init.py`'s own. In every other case `init.py` neither writes `CLAUDE.md` nor reads nor names it, and the register check at the end reads it only where the register names it. It is written after the workflow, so a start that wrote it, whole or stopped halfway, is still a start on the next run, and is not taken into adopt mode by the `CLAUDE.md` it wrote itself. A `CLAUDE.md` that exists is never touched: in a repo that `init.py` has not started it means adopt mode, as before, and in one it started it is not read or named.
- `register.json` from `templates/register.json`, with the project's name, checked with `check_register.py` before it is written.
- `REGISTER.md`, generated from the `register.json` that stands after the run, as `check_register.py --print-markdown` prints it. When `register.json` already exists, that is the one it is generated from.
- `.github/workflows/ratchet.yml` from `templates/ratchet-checks.yml`, with the commit of the Ratchet checkout it runs from as the pin. The commit is read with `git rev-parse` in that checkout and must be 40 characters `0-9` and `a-f`. It does not run when the checkout is not a git repo of its own, or has changes that are not committed, since the commit would then not hold the files it copies. It says whether the commit is the one of the tag of its version. The workflow has two jobs, and the template must hold each once: `ratchet`, whose step runs `check_register.py register.json --markdown REGISTER.md --agents AGENTS.md`, and `project-checks`, the place for the project's own checks, with one step that says what goes there.
- the line `/.ratchet/` at the end of `.gitignore`, unless the last line there that mentions `.ratchet` is exactly `.ratchet/` or `/.ratchet/`, with no line starting `!` after it. A space at the start or the end of a line is part of it, as gitignore reads a leading space, so ` .ratchet/` gets the line, and so does any other form, which at worst adds a line that is not needed. A file with CRLF gets CRLF. This is the one file it changes, and only by that line, in one step: it is read again just before it is replaced, and when it no longer holds what was read, the run stops with exit 2 and leaves it as it is.

**Which path.** It says in one line which of its two paths it takes. In a start the line is `init: a new start:`, then why, in the words of `adopt_mode`: the project has no instruction file of its own, or `.github/workflows/ratchet.yml` is there, which a start writes first, or `register.json` names an instruction file in `instructions`. Then it names what its plan writes and adds, only the files whose action is to write them and the line it adds to `.gitignore`, or says that it writes nothing and that the lines below say what it does with each file, since a file may be there already or may be one it cannot write. The line is printed once the plan is made, and is the same in `--check` and in a real run. In adopt mode the line is `init: adopt mode:`, as below, and the line of a start is not printed.

**Adopt mode.** A repo that already has an instruction file of its own is adopted instead. The instruction files are a fixed list, `INSTRUCTION_FILES` in `init.py`: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md` and `.claude/CLAUDE.md`, each counted only as a plain file with no link on its path. Adopt mode applies when one of them stands, unless `.github/workflows/ratchet.yml` exists or a `register.json` names an instruction file in `instructions`: the first is a project that `init.py` started, since a start writes the workflow first, so a start that stopped halfway is never taken for a project of its own, and the second has chosen the generated block. In adopt mode it says so, names the file, and suggests running `inventory.py` first, which writes nothing. It never writes, changes or reads the instruction file: it looks only at whether the file is there. The register check at the end reads each file that a row by reference names, for its marker lines, as `check_register.py` always does. Its first run writes nothing. It writes `register.json` alone, and only when the project names, with `--adopt <key>`, once for each, the rules whose marker line it has put in its file: the template's, with the project's name, a row by reference for each rule named, pointing at the first instruction file, and no other row and no `instructions`. It writes it only when the register passes, checked with `check_register.generated_problems` on the bytes it would write, so a register that fails is never written, and a key that is not a rule of Ratchet, or is named twice, stops the run. `--adopt` in a start stops the run too. No row is copied: a copied `ratchet.register-on-top` is false where the project's own instruction file is canonical, since a register that holds rules by reference neither lists every rule in force nor takes precedence. `check_register.py` is not loosened: a register that adopts nothing still fails. A `register.json` of the project's own is checked as it stands, with or without `--adopt`. It writes no `REGISTER.md`, which a register with rows by reference may leave out, and does not read one: a `REGISTER.md` that exists, whether a plain file, a link, a directory or one it cannot read, is left as it is and named as not checked, as `check_register.py register.json`, the check the printed step runs, does not read it, and the exit code is the same as without it. It writes no workflow and no line in `.gitignore`, and says to add `/.ratchet/` when `.gitignore` does not ignore the clone. It prints, for each rule to start with that the register that stands after the run does not adopt yet, `ratchet.register-on-top` included when a register of the project's own leaves it out, the rule, its marker line and its row by reference as one line of JSON, both from the first column, so that each is pasted as it stands, with `stands_in` the first instruction file, the `sha256` of the rule and its ratchet, and `status` "text only for now" where the rule names a check. It says where to put each marker: in that file, alone on a line, by the project's own wording of the rule, and to leave out a rule the file does not state. It says, every time and without reading the file, that a marker counts only in a file in UTF-8 with LF line endings: `check_register.py` fails on a file in another encoding and on a marker line that ends in CRLF. Other instruction files it found are named as ones a row may point at. It prints `ratchet.register-on-top` with the rest, and says it fits only where the register, not the project's file, lists every rule in force and takes precedence. It says how to record a rule whose row it prints "text only for now" as `built`: with a `where` that names the enforcement point and when it was read back, such as the protection of `main` at the host for `ratchet.protected-main`, as the glossary defines built. It does not say that the host enforces it, since it cannot see the host. It prints the command that copies [run_pinned.py](#run_pinnedpy) into the project's repo from the pinned commit, `.github/ratchet/run_pinned.py`, and the one step to add to a job that the protection of `main` already requires, which runs it with `python3 -I`, pinned to the commit: it adds no workflow and no required job, so no admin is needed. Beside the step it prints `permissions: contents: read` for the job, so that its token can only read the repo, and `persist-credentials: false` for its checkout, so that no token is left in `.git/config`, each with why, and the same command as a line for a local check script that CI runs, for a project whose definition of done is that script, in a subshell followed by `|| exit 1`, so that it stops a script with `set -e` or without it. It says that `inventory.py --ruleset <file>`, given the ruleset or branch protection of `main` exported from the host, names which jobs are required. The last line of a run that passes names no file left as it is: a `register.json` of the project's own is checked as it stands, with nothing to compare. The check at the end of a real run, and the verdict of `--check`, is `check_register.py register.json`, without `--markdown`, so a register whose rows by reference miss their marker fails both. `register.json` is written with the same write guards as a start: never over a file, never through a link, only inside the root. The exit codes are the same: 0 when the plan can be carried out and the register it leaves passes, 1 when it would not pass, 2 when it cannot run.

The name is the one `--name` gives, or else the repo's name in the url of its git remote, `origin` first and else the first remote with a url, read from the git config as a file, without `.git`, when that is a name, or else the folder's name. It says which, and why the remote's was not taken. A worktree's folder, which a tool may name, is then not taken for the project's name. The name is ASCII letters and digits, in words joined by one space, `-`, `.` or `_`, at most 100 characters, and nothing that is shown as a link. So it can stand as text in a heading and in the register.

A file that exists with the content it would write is unchanged. A file that exists with other content, or that is not a plain file, is skipped, named, and left as it is. That is reported, not a failure: the run writes the rest, and the exit code does not change for it. With `--check` it writes nothing and says the same, and checks in memory the register it would leave: that `register.json` passes `check_register.py`, that `REGISTER.md` is a plain file and what `register.json` generates, and, when `register.json` names an instruction file in `instructions`, that the file's path holds no link, and that the file exists and holds the block that `register.json` generates. It reaches that verdict with the same function as the check at the end of a real run, `check_register.generated_problems`, given the bytes it would write for each file it would write, and reading every other file from the disk, so the two cannot drift apart. Where a file is skipped or would be written, `--check` and a real run exit with the same code. Otherwise it ends by running `check_register.py register.json --markdown REGISTER.md` from the same checkout and shows its output. A second run says that nothing changed. The last line of a run that passes says only what applies: to compare each file left as it is, to fill in `AGENTS.md` when it was written, and to commit the files it wrote or changed, or that there is nothing to commit. Before the check at the end it names what is left to do: each placeholder of the template that `AGENTS.md` holds or would hold, from the fixed list in `check_register.py`, which the workflow's register check fails on, a placeholder nested in another one, such as the `<n>` of the handover's, on the list on its own; the jobs `ratchet` and `project-checks`, to require in the protection of `main`; and, when the repo's git config names no remote, the adopted rules whose check cannot run before it has one, with why: `ratchet.register-on-top`, `ratchet.protected-main`, `ratchet.owner-paths`, `ratchet.no-secrets` and `ratchet.lesson-names-check`, as far as the register that stands after the run adopts them. It reads the config as a file, in the repo's common directory for a worktree, looks for a line `[remote "`, and does not follow an include or read a worktree's own `config.worktree`. None of this changes the exit code. Each file is written in full to a temporary file beside it and synced, then linked into place with a hard link, which fails when the file appeared meanwhile, so a file is missing or whole. On a file system with no hard links it stops with exit 2 and writes no file there: it never writes a file directly, which a cut-off write could leave half written for a second run to skip. A run that stops halfway leaves whole files, and the next run writes the rest. Exit code 0: the plan was carried out, or with `--check` can be, and the register passes, whether a file was skipped or not. 1: the register does not pass, or with `--check` would not, `REGISTER.md` or the instruction file included. 2: it could not run, and wrote nothing, or it stopped at a file it could not write or at a `.gitignore` that changed, and says how many files it wrote before.

The paths it prints are as the user typed them. The root is the directory it runs in as the shell names it in `PWD`, never resolved, and the Ratchet checkout, when it stands under the root, is named from the root, such as `.ratchet/checks/check_register.py`. A link above the root, such as `/var` to `/private/var` on macOS, is not resolved in what it prints.

It runs only from the root of a git repo, read from the files and not by running git there: a `.git` directory that holds `HEAD` and `objects/`, or a `.git` file of the one line `gitdir: <path>`, the path absolute or from the project's root, naming a directory that holds `HEAD` and `commondir` or `objects/`, as a worktree, a submodule or `git init --separate-git-dir` leaves it.

The shared threat model, [The threat model](#the-threat-model) at the top of this file, holds for `init.py` too. What follows is its own, narrower claim.

**Against which threat.** Mistakes by the person or the agent who starts a project in their own repo: a dry run that reports failure on a project that only has files of its own, so that the result is ignored, or that passes where the real run fails, a path printed that is not the one the user typed, work overwritten by a template, a pin that is a tag name, a placeholder or the commit of other files than the ones copied, the line in `.gitignore` forgotten or not taking effect, an edit to `.gitignore` lost, a result left half written, a run in a folder that is not the root of a repo, a placeholder left in `AGENTS.md`, text there that does not apply to a project of one agent, a check of the project's own with no place to run or not marked as required, a rule taken to be running before the repo has a remote. In adopt mode also: the project's own instruction file written over, or rewritten with a template, a register that does not pass the moment it is written, a row by reference with the wrong hash typed by hand, a workflow or a required job added that only an admin can add, and a start that stopped halfway taken for a project of its own.

**What it does not claim.** It does not guard against a hostile Ratchet checkout: its code is the code that runs. It never runs code from the project's repo. It runs git only in the Ratchet checkout, never in the project's repo, whose git config could name a program to run (`core.fsmonitor`), and the check at the end is the checkout's own. It does not read `.git/info/exclude`, a global excludes file or a `.gitignore` below the root, and it does not stand against an edit made to `.gitignore` in the instant between the second read and the replacement. It does not guard against a concurrent attacker. It does not see whether the pinned commit is on GitHub: a commit that is not the one of a tag is named, and fetched by the workflow all the same. It does not merge an `AGENTS.md` the project already has with the template, and it does not build any check. It does not see a placeholder that is not on the fixed list, text that a project wrote and that does not apply, or a remote named only in an included config, or only in a worktree's `config.worktree` when `extensions.worktreeConfig` is set: git reports that remote, and `init.py` names the rules as waiting all the same. It does not turn on the protection of `main`: it names the jobs to require. In adopt mode it does not read the instruction file for what it prints, so it does not see whether the file states a rule, whether it is UTF-8 with LF line endings, or whether a marker the project adds stands by the wording of its rule: the check sees a marker, not the words. It does not add the step to a job, or see whether the job it goes into is required. It looks for instruction files only at the paths on its fixed list, not at any depth; `inventory.py` lists every one.

**The cases.** Each is a test in [test_init.py](test_init.py), on a project of its own: a git repo with a clone of a copy of this checkout, with one commit, as its `.ratchet`.

**The sample on the landing page.** The landing page shows the dry run, `<pre class="sample">`: the command, then lines that `init.py --check` prints in an empty repo. Its clone command fetches the released tag, so the sample is what that tag prints, and `sample_problems` in `test_init.py` compares it with the tag's own `init.py`. It reads the version from the page's clone command. When this checkout holds `refs/tags/vX.Y`, it clones the checkout into `.ratchet` of a new empty repo, checks out the tag's commit by its id, never by the name, so that a branch of the same name is not taken for it, and runs `init.py --check` there. The sample must hold at least two lines after the command, none of them empty, and each must be a line the run prints, so the lines that differ between runs, the commit and the project's name, need not stand in it. Only when there is no such tag and the checkout is the release of that version, where `ratchet.json` names it and the first entry of `CHANGELOG.md` is that version with a date, is the sample compared with the head. A tag that exists is compared even then. Anywhere else a missing tag fails the test, which says to fetch the tags: the head is never compared in its place. The job `own` checks out with `fetch-depth: 0`, which `released_text.py` needs too, and in the job `released` the copy is tagged in its release before its suite runs, so the sample is compared with that tag.

What it claims: the sample shows only what the version the page fetches prints. Against which threat: drift between the page and that version, when a change to `init.py`'s output is merged with the sample moved to the head's, and the page shows what the fetched version does not print until the next release. It does not claim that the sample shows every line, or the lines in their order. Each case is a test of the class `Sample`, on a copy of this checkout tagged `v9.0`, whose head after the tag prints `would draft` where the tag prints `would write`.

## run_pinned.py

```sh
python3 -I .github/ratchet/run_pinned.py <commit> -- register.json
python3 -I .github/ratchet/run_pinned.py <commit> --store .ratchet --repository <url> -- register.json --markdown REGISTER.md
```

This one checks no rule either. It runs `check_register.py` from the commit a project pins, for the step that adopt mode in `init.py` prints, and for a local check script that CI runs. It stands against running the check from a clone's working tree, where `git update-index --assume-unchanged` hides an edited `check_register.py` from `git status`, so edited code runs while `HEAD` matches the pin, and an ignored `checks/argparse.py` beside the check is imported the same way.

**How it is run.** The project copies the one file into its own repo, once, from the pinned commit's objects, and commits it. Adopt mode in `init.py` prints the two commands, built by `copy_command` and `run_command` in `run_pinned.py`, with the name of the file's blob in the pinned tree, which `init.py` reads through the commit and each tree on the way, every object hashed and with no git config. The copy command runs every git under `env -i`, so no `GIT_` variable of the environment, `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_CONFIG_COUNT` among them, is in effect, and reads the blob through a new, empty git directory with the store's object directory, with no config of the store's, the user's or the system's and no lazy fetch. It writes it beside the target, and keeps it only when `git hash-object --no-filters` gives it that name; otherwise it leaves nothing at the target and fails. Before it writes, it refuses, leaving both as they are, when anything stands at `<target>.new`, a file, a folder or a link, or when the target stands and is not a regular file, so it never writes through a link at either; a link in a folder above them is not looked at. The step, or the line for a local check script, hashes the copy the same way before it runs it, and fails when the copy is missing, empty, cut short or not that blob. That check is an `if` that ends in `exit 1`, not the left side of `&&`, which `set -e` does not stop on. The line for a local check script, built by `local_line`, is the step in a subshell followed by `|| exit 1`, so a script ends there in `sh`, `bash` and `dash`, with `set -e` or without it, both when the copy is not the blob and when the check fails. `upgrade.py` prints the same copy command and lines, with the new commit, to a register with rows by reference in a project with no `.github/workflows/ratchet.yml`. The step is printed as a YAML block scalar, `run: |`. It runs with `python3 -I`, which leaves the script's directory out of `sys.path`, and it imports nothing from beside it, so a module planted beside the copy is not imported. Its first lines refuse, exit 2, when the file does not end with its own last line, so a copy cut short after them refuses even without the step's hash. Before it runs the check it compares its own bytes with `checks/run_pinned.py` of the commit, read and hashed as below, and refuses to go on when they differ, naming the command that copies it again: a copy left stale by an upgrade, or edited, does not run the check.

**What it claims.** The check that runs is `checks/check_register.py` of the pinned commit, beside the commit's own files and no other. It uses the store, `.ratchet` unless `--store` names another, only as a store of git objects: when the store is missing it makes one, empty and with no checkout, and fetches the pinned commit alone into it, shallow and by its id, from GitHub unless `--repository` names another, so no other commit and no history is fetched and indexed; when the repository does not give a commit by its id, it fetches the repository's branches and tags into the store it made, what a clone fetches; when the commit is not in a store that was there, it fetches the commit; it never reads the store's working tree. When none of these gives the commit, because the repository cannot be reached or does not hold it, it refuses, exit 2: it never passes without the pinned commit. It removes nothing, so a store it made stays, empty, and the next run fetches into it. It refuses a store that is not a git repo of its own, so a plain folder at `.ratchet` is never taken for the project's repo. git never reads a config of the store's, the user's or the system's, and never fetches while it reads: it runs in a new, empty git directory of its own, with the store's object directory as `GIT_OBJECT_DIRECTORY`, so the store's config, hooks, refs and attributes are never read, with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG` an empty file, `HOME` and `XDG_CONFIG_HOME` a new directory, every `GIT_` variable of the environment dropped, `GIT_CONFIG_PARAMETERS` included, and `GIT_CEILING_DIRECTORIES` above the directory it runs in. With no config there is no promisor remote, so a missing object is never fetched lazily, and `GIT_NO_LAZY_FETCH=1` and `--no-lazy-fetch`, where the installed git knows it, say so again. Replace objects, hooks, `core.fsmonitor`, automatic gc and maintenance are off. The fetches into a missing store and the fetch of a missing commit are the only steps that reach the network: each explicit, from the repository named alone, and with the same isolation, the fetch writing into the store's object directory through the empty git directory, so not even the store's remotes or url rewrites are read. Objects that the store's alternates name are read too, which is harmless, since every object is hashed. It reads the commit, its tree and every blob under it with `git cat-file --batch`, and no other object of the store: the trees one level at a time, each level in one read, and then the blobs in one read, so the number of reads follows the depth of the tree and not its count of directories. It hashes each object itself, so an object whose bytes do not give its name, corrupt or swapped, is refused, and a replace ref is never followed. It reads raw objects and not the output of `git archive`, which applies the attributes and the filters that the store's own config names. It writes the tree into a new directory from `tempfile`, refusing a name that is `.`, `..` or `.git` or holds a `/`, writing no link and no submodule, and removes the directory at the end. It runs the check there with `python3 -E -s -B`, from the directory it was started in, with the arguments after `--`, and exits with the check's code. Exit 2: it could not run, and the check did not run.

**What it does not claim.** The shared threat model holds. The copy, the step and the script that runs it are files of the project, so it does not stand against someone who edits them: a change to them is in the project's diff, for the owner's required review of the owner's paths to catch, where that lock is built. Its self-check catches a copy that is not the pinned commit's, not a copy edited to skip the self-check. A copy cut short before its first lines, or empty, exits 0 when run on its own, with no step around it: the hash in the printed step and the printed line is what refuses it, and a step or a script that drops that hash is the project's edit. It does not stand against a `git`, a `python3` or a `PATH` that is not what it says, or against the repository it clones from, which is GitHub's `fabian-von-tiedemann/ratchet` unless `--repository` names another. The step and the line use `git hash-object` in the project's own repo, with its config and the environment's `GIT_` variables. It runs no `git fsck` of the whole store: every object it uses is hashed by itself, and an object it does not use does not change what runs. It does not see whether the commit is a release, or whether the job it runs in is required. It runs `check_register.py` only. The workflow that `init.py` writes for a start still runs the check from a fresh `actions/checkout` of the pinned commit, not through `run_pinned.py`.

**The cases.** Each is a test in [test_run_pinned.py](test_run_pinned.py), on a project of its own with a copy of `run_pinned.py` taken from the commit, and a store cloned from a copy of this checkout with one commit.

## python3 -I

Every script in `checks/` and `maintain/` runs under `python3 -I`. `-I` leaves the script's directory out of `sys.path`, so each script that imports a module beside it puts its own directory first on `sys.path`, named explicitly, before it does, and a script in `maintain/` puts `checks/` right after it. That brings back what a plain run has, and no more: a module planted beside a check in a working tree is still imported, which is why `run_pinned.py` runs the check from a directory that holds only the pinned commit's files. `run_pinned.py` imports nothing from beside it. The cases are in `Isolated` in [test_run_pinned.py](test_run_pinned.py): every script that imports one beside it puts its directory on the path before the first such import, every script with a command line starts with `--help` under `-I`, and `check_register.py` passes on this repo's register under `-I`.

## inventory.py

```sh
python3 .ratchet/checks/inventory.py                          # the repo in the folder it runs in
python3 .ratchet/checks/inventory.py --uses claude,codex      # and the files no harness in use loads
python3 .ratchet/checks/inventory.py --ruleset main.json      # and the jobs that run and are not required
python3 .ratchet/checks/inventory.py --global --json          # with the user's own layer, as JSON
python3 .ratchet/checks/inventory.py --exclude checks/fixtures # without a folder of test fixtures, named as not read
```

This one checks no rule in a register. A repo that already has an agent layer runs it first, to see what it has before it chooses.

**What it claims.** It lists, as names and short facts, the files that make up a repo's agent layer as it stands, and with `--global` the user's own layer under the home folder (`--home` names another folder). It reports facts and does not interpret Markdown (D-2026-11-16-strict-forms). Judging what each part means, and which principle it answers to, is the agent's job on its output, and the result is a proposal to the owner, never a change.

- **The files.** Instruction files at any depth (`CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `AGENTS.override.md`, `GEMINI.md`) and in the places a harness reads them, skills, commands, agents, hooks, settings, MCP config, workflows, pull request and issue templates, the code owners file and the register, each with its kind and the harnesses that load it. Which harness loads which file is the table `KINDS` in the script, as of 2026-11: Claude Code, Codex, Gemini CLI, Cursor, GitHub Copilot, Windsurf and Cline. Every file in a harness's own folder, such as `.claude/`, is listed, of a kind the table knows or not. From settings and MCP config it gives only the names of hook events, with a count, and of servers.
- **Same content and same name.** Files with the same bytes, by sha256, and skills, commands and agents with the same name, in the repo, across harnesses and, with `--global`, across the two layers, each group marked as the same or a different content.
- **Not loaded by a harness in use.** With `--uses`, the files that no harness named there loads, such as a session prompt for a harness the project left, each with the instruction files that name it. Without `--uses` it does not guess which harnesses are in use, and says to give them.
- **Look unused.** A hook under `.claude/hooks/` that no settings file of its layer names, a skill folder without `SKILL.md`, an empty file, and a file in a harness's folder of a kind the table does not know.
- **Paths named that do not exist.** In each instruction file, by line: the target of a Markdown link, read from the file's folder; an import, a word of its own that starts with `@` and has a `/` or a known extension, such as `@AGENTS.md` or `@docs/notes.md`, with punctuation at its end left off; and a span in backticks with a `/` in it, read from the file's folder or from the root. A span with no `/`, such as `` `generate.py` ``, is a name and is not looked at, and so is one with a space in it, such as `` `python3 maintain/generate.py --check` ``, which is a command, and one with no known extension whose first part does not exist, such as `owner/repo`. A word such as `@alice` or `@pytest.mark.skip` is not an import. A URL and an anchor are not looked at. Three kinds of path that does not exist are listed under "Paths named and not looked for" instead, each with a count, since an instruction file names them on purpose: a path that the `.gitignore` at the root ignores, such as a generated file that is not committed; a span in a row of a table, a line that starts with `|`, whose last part has no known extension, such as `` `feature/` `` or `` `feature/login` `` in a table of branch conventions; and a path outside the root, absolute, from `/` or `~/`, or relative and leaving the root, such as a file in another repo, named as outside the root and not checked. An absolute path inside the root is looked at as any other, and one with a single part and no known extension, such as `` `/review` ``, is a command and not a path. Every other path that does not exist is still named.
- **Workflows and the host's rules.** For each workflow, the events it runs on and its jobs, each with its name. Given with `--ruleset` the ruleset, branch protection or rules for a branch exported from the host as JSON, once or more: whether each job is required, the jobs that run on a pull request and are not required, under the heading "they look like a gate and are not", the required checks no job here names, and what the export says of required review and bypass: the number of approvals, code owner review, stale reviews dismissed, approval of the last push, the actors that may bypass, and administrators when branch protection does not apply to them. A ruleset that is not `active`, or not on branches, requires nothing. A job reports its check under its `name:` when it has a name written out, and under its id only when it has no name or a name that is an expression, which is known only when the job runs. A job is required when a required check is that one name, alone, with a matrix `(...)` after it, or with ` / ` and a called job: a job `checks` with `name: Run Checks` is not required by a ruleset that requires `checks`. A type of rule, or a parameter of the review, that it does not read is named. A field the export leaves out is shown as not in the export, never filled in: the bypass actors, which GitHub shows only to an account with admin rights, are "not shown in the export" when they are left out and "none" when the list is empty.
- **Folders left out, and named.** With `--exclude`, once for each folder, the walk of the repo does not enter a folder named from the root, such as `checks/fixtures`, whose test fixtures would otherwise be listed as the agent layer. Each folder given is listed under "Skipped, not read", and in `skipped` in `--json`, as "excluded with --exclude", a folder under another one given too, so nothing is left out silently. Nothing is excluded by default, and `--exclude` does not apply to `--global`. A folder is given in the one form the repo's other paths have: parts separated by single slashes, no `.` or `..`, no `/` at its start or its end, and no character of a glob. Each part must be a folder under the one before it, under exactly that name, through no link; anything else stops the run. The root cannot be excluded.
- **Code owners beside the register.** The lines of the code owners file that GitHub reads, `.github/CODEOWNERS`, `CODEOWNERS` or `docs/CODEOWNERS`, first found, with their numbers, beside the files `register.json` names: its `instructions`, a row's `stands_in`, and the paths in backticks in a row's `where`, read as in an instruction file, each marked when it does not exist. A code owners file that is not UTF-8, and a register whose `adopted` or `own` is not a list, are named as not read, and the rest is listed. It does not match one against the other: the owner compares them.

It writes nothing, reaches no network and runs no program. It reads only under the root, the home folder with `--global`, and the files given with `--ruleset`. In the home folder it looks only at the names at the top of `.claude`, `.codex`, `.gemini` and `.agents`, at `.claude.json`, and in the folders of `GLOBAL_WALKED`, and reads only the files of `GLOBAL_KINDS`. It follows no link: each one in the layer is named with its target and whether the target is inside the root, and nothing behind it is read. In the home folder it looks at every part of a path from the home folder down before it walks or reads under it, so a link at `~/.claude` or `~/.agents` is named there and nothing under it, such as `~/.claude/skills`, is read. It does not read a file whose name looks like a credential (`CREDENTIAL_NAMES`: `.env`, `*.pem`, `*token*`, `*secret*`, `*credential*`, `auth.json`, `.claude.json` and others), and names it as skipped. One exception: a Markdown file of a kind a harness loads into the session as text, an instruction file, a skill, a command, an agent or an output style, whose name matches only the words `*secret*`, `*token*` or `*credential*`, such as `.claude/rules/no-secrets.md`, is read. Such a name names a rule, and the harness already puts the file's text in front of the agent, so the inventory reading its paths shows nothing new; a name like `.env.md`, and every other kind of file, is still skipped. It does not read a file over 1,000,000 bytes, and names it. It reads every file, the repo's, the home folder's and the export alike, through one guarded reader, the functions named `guarded_` in the script: from its starting point, the root, the home folder, or for `--ruleset` the folder of the file given, it looks at each part of the path without following it and refuses at the first that is a link; it opens each folder under the one before it, and the file last, with `O_NOFOLLOW` and `O_NONBLOCK`, and reads it only if it is a regular file. The starting point itself may be reached through a link, as `/tmp` and `/var` are on macOS; nothing below it is. For `--ruleset` the starting point is the folder of the path the user typed, resolved through its links once, since the path given on the command line is the user's own choice of input: a file under a folder from `mktemp -d`, which is under `/var` on macOS, is read. No other function opens, lists, walks or looks at a path, and a test sweeps the script for any that does. Every name it prints is on one line, with a line break, a control character and a backslash escaped. It does not walk `.git` or `node_modules`, nor, at the root, `.claude/worktrees` or `.ratchet`, Ratchet's own copy in a repo that adopted it, and names the last two as skipped. The export is read through the same reader as every other file, from its folder: a link above it, such as `linked-directory/export.json`, is followed, and the file itself is refused when it is a link, read only if it is a regular file, and not at all if its name looks like a credential: the name is the last part of the path that names something, so `secret-token.json/` and `secret-token.json/.` are refused as `secret-token.json` is, and a path that ends in `/`, `/.` or `/..` names a folder and is refused. A refusal for an export that is a link says to give the file the link points to. Then the export is read with the strict reader, `registry.parse_json`. Each field it reads must be of its kind, `true` and `false` are not numbers, and a field is taken as left out only when it is absent or `null`. Exit code 0 when it ran, 2 when it could not: a root that is not a folder, a harness it does not know, `--uses` that names none, `--home` without `--global`, `--home` empty, an `--exclude` that is empty, `.`, starts or ends with `/`, has an empty part, `.` or `..`, holds a character of a glob, or does not name a folder of the repo under exactly that name, through no link, an export that is a link, a path of an export that ends in `/`, `/.` or `/..`, not a regular file, named like a credential, cannot be read, is not JSON or not UTF-8, has a field twice, holds no ruleset, is a ruleset without `target` or `enforcement`, has a field of the wrong kind, a rule without a type, a rule for a branch without the ruleset it comes from, a list that mixes the rules for a branch with a ruleset or a branch protection, or is none of the three forms.

**The exports it reads.** Three, as GitHub's REST API returns them, saved as JSON:

| Export | Endpoint | Who can get it |
|---|---|---|
| A ruleset | `GET /repos/{owner}/{repo}/rulesets/{id}` | An account that can read the repo; `bypass_actors` is shown only to one with admin rights, and is "not shown in the export" otherwise. The list `GET /repos/{owner}/{repo}/rulesets` holds no rules, and is not read: fetch each ruleset by its id |
| The rules for a branch | `GET /repos/{owner}/{repo}/rules/branches/{branch}` | An account that can read the repo. A list of rules, each with its `type`, its `parameters` and the ruleset it comes from (`ruleset_source_type`, `ruleset_source`, `ruleset_id`), from the repo and the organization, of rulesets that are active only. It is listed as one entry for each ruleset, with no bypass, which this export never shows. An empty list, no rule on the branch, cannot be told from an empty export and is refused, with a line that says what it means |
| Branch protection | `GET /repos/{owner}/{repo}/branches/{branch}/protection` | Only an account with admin rights on the repo |

Each rule of the rules for a branch must have its `type`, `ruleset_source_type` and `ruleset_source` as text and `ruleset_id` as a number; its parameters are read as those of a rule in a ruleset, and a field it does not know is named as not read.

**Against which threat.** Not knowing what governs a repo: instruction files and skills that grew over time, collide with each other or with the user's global ones, that no harness in use reads any longer, or that name files that are gone; and a job that runs on every pull request and looks like a gate, when the host does not require it, which is how a check is taken to be "built" when it cannot refuse. It is read only, so that a repo can be looked at before anything in it is chosen or changed. As [the threat model](#the-threat-model) says of every check, it catches mistakes and drift, not someone who means to hide a file from it.

**What it does not claim.**

- It does not read what a file says, or judge whether a rule is good, a duplicate in meaning, or in force. Two files that say the same thing in other words are not the same content.
- The table of harnesses and their files is as of 2026-11 and is not complete. It does not see a harness's own configuration that changes what it loads, such as Gemini CLI's `contextFileName` (named as a fact, not followed), an import beyond the one line `@path`, a rule set in an application's settings, or a plugin.
- It does not see whether a harness is in use. `--uses` is the owner's word.
- A path in an instruction file may be meant as something else, and a path written in another way is not seen. A name in backticks with no `/` is not looked at.
- It reads only the `.gitignore` at the root, not one below it, `.git/info/exclude` or a global excludes file, and of it only the simplest lines: a plain path of letters, digits, `.`, `-` and `_`, its parts separated by single slashes, with no part `.` or `..`, and at most one `/` at its start and one at its end. Such a line is read as git reads it: a `/` at the end makes it a folder, everything under it ignored; a `/` at the start or before the end reads it from the root; a name alone matches at any depth. Every other line is not read and is counted, and the count is printed: a line with `*`, `?`, `[`, `]`, `!` or a backslash, `//` anywhere, a space or a tab, a character outside that list, a CR at the end, or a byte that is not ASCII. A blank line and one that starts with `#` are no pattern, as in git, and are not counted. A path under a line that is not read is named as missing: the reader subtracts and fails closed, and a missing path is never hidden by a guess at git's rules. It reads names as they are written, where git on a file system that ignores case may not, so at worst it names a path as missing. A test compares each line it reads with `git check-ignore --no-index` on a table of paths. A path that a line ignores is not named as missing even when it was meant to be committed.
- A span in a row of a table that looks like a branch name is not looked for, so a folder that is gone, named in a table with a `/` at its end, is counted there and not named as missing. A branch name written in another way, or outside a table, is still named as missing when its first part exists.
- It reads workflows as far as their top-level keys, their events, their jobs and each job's `name`, with a reader of a subset of YAML that fails closed. The subset: block mappings indented with spaces, keys that are plain or quoted without an escape, comments, and block scalars, whose text it skips. Under `on:` it reads one event name, a list of names on one line, a block sequence of names at any indent, column 0 among them as PyYAML writes it, or a block mapping of names. Anything else is named as not read: a line that leaves a quote or a bracket open, an anchor, alias, tag or merge key on `on:` itself, as an event or an item of its list, or as a job's key, a job's `name` that is not a scalar on one line, a key given twice, a second document, a tab in the indent, a missing `on:` or `jobs:`, and any line it cannot place. A workflow whose events or jobs are not read is never left out: its jobs are listed under the heading "Jobs of workflows this reader could not read: it cannot tell whether they run on a pull request", or the file is, when its jobs were not read either, and so is a workflow too large or not UTF-8. What stands under an event, such as its `branches`, is not read, so an anchor or an alias there is taken as it is and changes nothing it reports. It does not see a job's `if`, the branches or paths a trigger is limited to, or what a reusable workflow runs.
- It does not reach the host. The export is what the owner gives it: it does not see whether the file is current, or a rule the export leaves out, such as one set at the organization. A required check from an app that is not a job here is listed, not judged. A job whose name is an expression is matched by its id, which may not be what GitHub reports.
- It does not match the code owners file against the files the register names, and does not see whether the owner's review is required. The register's `where` says where a check is enforced and when that was read back.
- A credential under a name not on the list is read like any other file of its kind, though it prints only names and short facts from it. A credential outside the layer is not looked at.
- It does not stand against a repo set up to mislead it: a file can be named or placed so that it looks like another kind.
- It does not see whether a folder given with `--exclude` holds a real part of the agent layer. It names each one as not read, and the owner judges the choice.

**Its scope, by [the threat model](#the-threat-model).** Two lines bound what it claims, and a finding outside them is a question of scope for the owner, not a defect. The workflow reader is a subset of YAML, and it names everything outside that subset as not read: a form it names as not read is the reader working as it should, and reading one more form is a change of scope. The inventory reads no file through a link anywhere on its path below the starting point, which for `--ruleset` is the folder of the path the user typed: a link is named, with its target, and nothing behind it is read, listed or looked at, and a path an instruction file or the register names through a link is shown as not looked at, neither present nor missing.

**The cases.** Each is a test in [test_inventory.py](test_inventory.py). The fixtures are under [fixtures/inventory/](fixtures/inventory/): a repo with an agent layer under `repo/`, a user's layer under `home/`, a ruleset, a branch protection and a ruleset that is only evaluated under `ruleset/`, and exports with one fault each under `faults/`. A fixture's name cannot start with a dot, so a part that starts with `dot-` is renamed to start with `.` in the copy the test makes. This repo holds no link, so the test makes the links in that copy.

## map.py

```sh
python3 .ratchet/checks/map.py           # the map at the root of the repo in the folder it runs in
python3 .ratchet/checks/map.py --json    # the same facts, as JSON
python3 .ratchet/checks/map.py --partial # while the map is written: a rule with no entry is listed, not a problem
```

This one checks no rule in a register. A repo with rules and checks of its own maps Ratchet's rules to them before it adopts anything, as the second path of [TRYING.md](../TRYING.md) says. The agent writes the map, `ratchet-map.json` at the root of the repo and only there. Ratchet never writes it, and the map puts nothing in a required job. Its name ends in `.json`, so it can never be a register's instruction or reference file, which end in `.md`.

**The form.** One exact form, read strictly with `registry.parse_json`: UTF-8 with no byte order mark, no field twice in one object, no NaN or Infinity, and no `null`, `true`, `false`, number, array or object where the form wants another kind. So nothing is nested deeper than the form, and a file nested deeper than 100 is refused before it is parsed.

```json
{
  "ratchet": "0.16",
  "rules": {
    "ratchet.protected-main": {"status": "covered", "by": [".github/workflows/ci.yml"], "note": "..."},
    "ratchet.no-secrets": {"status": "gap", "by": [], "note": "..."}
  }
}
```

- **The top level** is an object with the two fields `ratchet` and `rules`, and no other.
- **`ratchet`** is text of the form MAJOR.MINOR, equal to the `version` of the `ratchet.json` of the checkout that `map.py` runs from, the folder above `checks/`. Run it from a released checkout, as [Start here](../README.md#start-here) fetches it: the check compares the two versions and does not look at tags.
- **`rules`** is an object with one entry for every rule of that `ratchet.json`, core and experimental, and no other.
- **Each entry** is an object with the three fields `status`, `by` and `note`, and no other.
  - `status` is `covered`, the repo covers the rule fully, by a check or a rule of its own, or `gap`, it does not, or only in part, and the note says how. There is no "not wanted": whether a rule is wanted is the owner's decision, not the agent's.
  - `by` is an array of paths. With `covered` it holds at least one, and with `gap` it may hold the files of a partial cover, or none. No path stands twice in one array. A path is given from the root, with `/` between its parts: no empty part, `.` or `..`, no `/` at its start or end, no backslash, `:`, `#` or `?`, at most 200 characters, each an ASCII letter or digit, `.`, `_`, `-`, `+` or `/`. It names a regular file under the root, reached through no link at any part of the path.
  - `note` is text of 1 to 300 characters that passes `registry.text_problem`, as every value in a data file here does ([The characters a value may hold](#the-characters-a-value-may-hold)).

**What it claims.** A map that passes names every rule of the `ratchet.json` beside `map.py`, each once, with `covered` or `gap`, in the form above, and every path it cites exists as a regular file under the root, reached through no link. It prints every assessment for the owner to review, rule by rule with its status, paths and note, the gaps first under a heading of their own and each marked `<-- GAP`, with a count for each status. Under each rule whose `source` in the `ratchet.json` beside `map.py` is not empty, it prints that text as it stands, on a line `source:` and as the field `source` in `--json`. One line says the map is the agent's proposal and that `map.py` checks its form and paths, not whether a path covers a rule; it stands in the text and in `--json`, whether the map passes or not. With `--json` it prints the same facts as JSON, and the text is made from those facts and nothing else. It writes nothing, reaches no network, runs no program and writes no bytecode. It reads the map, and looks at each path it cites, only through the guarded reader of [inventory.py](#inventorypy), `guarded_read` and `guarded_look`, imported with no change to `inventory.py`: a link at any part of a path below the root is refused, and a path it cites is looked at for its kind and never read. The root is resolved as `inventory.py` resolves its own: the folder given, or the folder it runs in, may itself be reached through a link, as `/tmp` and `/var` are on macOS, and nothing below it is. Exit code 0 when the map is of its form and every path exists as stated; 1 when not, with every problem named, the map file missing, a link, a folder, a FIFO or unreadable among them; 2 when it could not run: no valid `ratchet.json` beside it, or a root that is not a folder.

**With `--partial`**, a rule of that `ratchet.json` with no entry in `rules` is not a problem. Everything else is checked as without it: the top fields, `ratchet` against the checkout's version, each entry given with its paths, and an entry for a key that is not a rule. The first line says that the run is partial and not yet a map of the whole Ratchet, with the count of rules given, covered and gaps, and how many rules are not yet mapped, with their keys in the order of `ratchet.json`. A second line says that the run is partial and to run `map.py` without `--partial` once every rule is mapped. It stands in the text and as the field `partial` in `--json`, on a pass and on a failure, and on standard error when `map.py` cannot run. Under them, the rules given are printed as without it, the gaps first. A partial run never prints the first line of a full pass. On a pass, `--json` gives the keys not yet mapped as the field `unmapped`; a run with problems gives only its problems, as without it. The counts count only the rules given. The exit codes are as without it. Without `--partial`, none of this applies: the output and the exit codes are those above.

**Against which threat.** Mistakes and drift, as [the threat model](#the-threat-model) says of every check: an agent forgets a rule, misspells a key, maps against another checkout's version, cites a file that is not there or one through a link, writes a malformed file, or marks a rule covered with no path. With `--partial`, an agent that reads a partial pass as a full one: so the first line says it is partial, and no line of a full pass is printed.

**What it does not claim.**

- Whether a path it cites covers the rule. Each row is the agent's proposal, and the owner judges it.
- That the version is released, or that the checkout matches a tag.
- Anything against an author who means to mislead it, such as a file named to look like a check.
- Whether an owner's decision about a rule is authentic, or that the owner has read the map.
- A change to the files while it runs.

**The cases.** Each is a test in [test_map.py](test_map.py). The fixtures are under [fixtures/map/](fixtures/map/): a checkout's `ratchet.json` with three rules under `checkout/`, one of them with a source, a repo with a valid map under `repo/`, and maps with one fault each under `faults/`, which the table `FAULTS` in the test pairs with the problem each names, and a test fails on a fixture there without its case. Each is loaded by a test through `FixtureTest`, so [expected_tests.py](#expected_testspy) fails on one that is not. A part that starts with `dot-` is renamed to start with `.` in the copy the test makes. Links, FIFOs and files that cannot be read are made in a scratch directory when the test runs, never committed.

## tripwire.py

```sh
python3 checks/tripwire.py < call.json   # exit 0: the call goes ahead; exit 2: it is denied, with the reason on stderr
```

The reference check for `ratchet.irreversible-waits`. It is a `PreToolUse` hook for Claude Code ([Anthropic's hooks reference](https://code.claude.com/docs/en/hooks)): Claude Code runs it before every Bash command and every write to a file, and gives it the call as JSON on stdin. This repo runs it from [.claude/settings.json](../.claude/settings.json), and a project copies it as [CONTROL-ROOM.md](../CONTROL-ROOM.md#what-cannot-be-undone) says.

**It is a tripwire, not a lock.** It reads a command line well enough to catch the usual spellings of the five steps, and no better. It does not claim every spelling: another spelling of the same step gets past it, and a hook that reads the shell can always be shown one (D-2026-11-19-locks-not-parsing). Its claim is exactly the cases listed below. Where each step is locked, and where nothing locks it, is in [CONTROL-ROOM.md](../CONTROL-ROOM.md#what-cannot-be-undone).

**What it claims.** For a Bash command, it exits 2 and names each step on a line of its own, `tripwire: <step>`, when the command is one of the cases below and the approvals file has no entry for each step it takes with that exact command. For `Write`, `Edit`, `MultiEdit` and `NotebookEdit`, it exits 2 when the path is the approvals file. Every other tool exits 0. Input it cannot read, an empty call, a call that is not JSON or not UTF-8, has a field twice, names no tool or lacks the command or the path, exits 2. Any failure of its own exits 2 as well: it never exits other than 0 or 2, and its settings use `"onFailure": "block"`, so a hook that cannot start or times out blocks the call too.

**Against which threat.** An agent's mistake: a force push it takes to be harmless, a tag or a release nobody asked for, `rm -rf` on the wrong directory, a change to the settings, written in the way agents usually write these commands. It does not stand against an agent that means to get past it: such an agent writes the step another way, from a script, from another language, or edits the hook and its settings, which are files the maintainer reads before a merge (`ratchet.owner-paths`).

**How it reads a line.** It splits the line into simple commands at `;`, `&`, `|`, `&&`, `||`, newlines and parentheses, and also reads every `$(...)`, backtick and `<(...)` as commands of their own. It takes quotes and backslashes away as the shell does, skips the body of a here-document, and skips assignments, `if`, `then`, `do` and the like. It looks past `env`, `command`, `builtin`, `exec`, `nohup`, `nice`, `timeout`, `sudo`, `xargs`, `stdbuf` and `time`, and past a path before the program, such as `/usr/bin/git`. A `cd` to a literal path is followed for the commands after it in the same line, and a `cd` to anything else makes every later path unknown. It does not expand a variable, a pattern or a tilde other than a leading `~`.

**The steps, as it reads them.**

- `force-push`: `git push` with an option that starts `--force`, with `-f` alone or in a cluster such as `-uf`, `--mirror`, `--prune`, `--delete` or `-d`, a refspec that starts with `+`, or one with no source, `:ref`; `gh api` deleting `git/refs/heads/...`, or changing one with `force=true` or with a body from `--input`.
- `tag`: `git tag` with a name, `-a`, `-s`, `-f`, `-m`, `-F` or `-u`, and no listing option, or with `-d` or `--delete`; `git push` with `--tags`, `--follow-tags` or `--mirror`, the word `tag`, a refspec under `refs/tags/`, or a name that is a tag in the local repository, also with `--delete` or as `:ref`; `git update-ref` and `git symbolic-ref` on `refs/tags/`; `gh api` changing `git/refs/tags/...` or `git/tags`, or creating `git/refs` with `ref=refs/tags/...` or with a body from `--input`.
- `release`: `gh release create`, `edit`, `delete`, `upload` and `delete-asset`; `gh api` with any method but `GET` under `repos/{owner}/{repo}/releases`.
- `delete-outside`: `rm` with `-r`, `-R` or `--recursive`, alone or in a cluster, when an operand resolves to the working tree itself or to a path outside it, after links are resolved, or holds a variable or a substitution. The one exception is the temporary directory of the same line: `d=$(mktemp -d)`, or `$(mktemp -d -t <name>)`, followed in the same line by `rm -r "$d"` or `"${d}"`, quoted and with nothing after it, when nothing else in the line assigns `d` or names it as a word. And since the shell's state does not last from one Bash call to the next, a later call may delete such a directory by its path, or a path inside it, written from the directory where `mktemp -d` writes or from `/tmp`. On macOS that directory is the per-user temporary directory the system gives, `confstr(_CS_DARWIN_USER_TEMP_DIR)`, which `mktemp -d` uses whatever `TMPDIR` says, so `TMPDIR` does not move the exception there. When the system gives no absolute path of an existing directory, or the call fails, that root is not trusted at all and nothing takes its place, not `TMPDIR` and not a default; `/tmp` stays. Elsewhere it is the temporary directory that `TMPDIR` names, as GNU `mktemp` reads it. The entry directly in it is a real directory, named `tmp.` and six or more letters or digits as `mktemp -d` names it, and owned by the user the hook runs as. That entry and every part of the path after it are read as written, with `lstat` and before any link is followed, so none may be a link, `.` or `..`, with or without a `/` at the end. A part that does not exist ends the walk, since nothing below it exists. Another session of the same user may have a directory of that form, which this does not tell apart. The tests put a fresh directory from `mktemp -d` in the place of `/tmp`, so that they need no write to `/tmp`. They do it through a constant in the hook, which nothing in a call, its JSON or its environment, can change.
- `settings`: `gh repo edit`, `delete`, `rename`, `archive`, `unarchive` and `deploy-key`; `gh secret` and `gh variable` with `set`, `delete` or `remove`; `gh workflow enable` and `disable`; `gh api` with any method but `GET` on `repos/{owner}/{repo}` itself, or under one of its settings paths: `rulesets`, `branches`, `collaborators`, `invitations`, `hooks`, `keys`, `actions`, `environments`, `pages`, `secrets`, `variables`, `topics`, `vulnerability-alerts`, `automated-security-fixes`, `autolinks`, `properties`, `private-vulnerability-reporting`, `transfer`, `tags`, `dependabot`, `codespaces`, `interaction-limits` and `teams`. Labels are not on the list: they count as harmless and can be undone. Of these, the role Write may change Actions secrets and variables, of the repository and of an environment, and GitHub's docs do not reserve Dependabot and Codespaces secrets or enabling a workflow to an admin, so for these the tripwire is the only guard ([CONTROL-ROOM.md](../CONTROL-ROOM.md#what-cannot-be-undone)). Their usual spellings, with `gh secret`, `gh variable` and `gh api`, are cases below.
- `approvals-file`: any word or redirection in the command that names the approvals file, from the directory the command runs in. No approval covers it.

`gh api` takes its method from `-X`, `-XMETHOD`, `--method` or `--method=METHOD`, and without one, from GitHub CLI's own default: `POST` when a field (`-f`, `-F`, `--field`, `--raw-field`) or `--input` is given, `GET` otherwise.

**The approvals.** They are in `.claude/ratchet-approvals.json` in the project, which git ignores, so an approval stays on the machine where the owner wrote it and is never published. ## The tag ruleset

[templates/tag-ruleset.json](../templates/tag-ruleset.json) is the lock on moving and deleting a tag (`repo.tags-stay`, D-2026-11-19-tag-ruleset-scope). It is a repository ruleset in the form of GitHub's REST API, [Create a repository ruleset](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset):

- `target` `tag`, and `conditions.ref_name.include` `~ALL`, every tag.
- `enforcement` `active`.
- `rules`: `deletion` ("Only allow users with bypass permissions to delete matching refs"), `update` ("Only allow users with bypass permission to update matching refs") and `non_fast_forward` ("Prevent users with push access from force pushing to refs"). Not `creation`.
- `bypass_actors`: one, `actor_type` `RepositoryRole` with `actor_id` 5 and `bypass_mode` `always`. Observation (O): the documentation does not list the ids of the repository roles. Public reports and rulesets made in GitHub's settings page show the repository admin role as id 5. The read-back below shows what GitHub stored.

Creation is left open because the release workflow creates each tag with the built-in token of GitHub Actions, and a block on creation would stop it (O: GitHub's documentation does not say whether that token can be a bypass actor, and public reports say it cannot; see the decision). [release.py](../maintain/release.py) only creates a tag, with one `POST` to `/repos/{owner}/{repo}/git/refs`, and never moves, deletes or edits one, so the ruleset does not touch a release.

**Applying it is the maintainer's.** Settings are the maintainer's, and the agents' account, with the role Write, cannot create a ruleset. The maintainer runs, under the maintainer's own login and from the root of a checkout:

```sh
gh api -X POST repos/fabian-von-tiedemann/ratchet/rulesets --input templates/tag-ruleset.json
```

or makes the same ruleset on the settings page: Rules, Rulesets, New tag ruleset, enforcement Active, target all tags, the rules "Restrict updates", "Restrict deletions" and "Block force pushes", and "Repository admin" on the bypass list.

**Reading it back.** The answer to the `POST` holds the ruleset's `id`. Then:

```sh
gh api repos/fabian-von-tiedemann/ratchet/rulesets/<id>
```

Under the maintainer's login, it shows `target` `tag`, `enforcement` `active`, `conditions` `~ALL`, the three rules and no `creation`, and the one bypass actor. Under the agents' account, `bypass_actors` is not shown, and `current_user_can_bypass` must be `never`.

**Applied and read back in this repo.** The maintainer applied the ruleset on 2026-11-19, as `tags-stay`. The answer to the maintainer's `POST` showed the one bypass actor, `[{"actor_id": 5, "actor_type": "RepositoryRole", "bypass_mode": "always"}]`. The control room read it back the same day with the agents' account: target `tag`, enforcement `active`, `conditions.ref_name.include` `["~ALL"]`, the rules `deletion`, `update` and `non_fast_forward` and no `creation`, `current_user_can_bypass` `never`, and `bypass_actors` null, because the role Write is not shown it. Not tried: deleting or moving a tag with the agents' account, which would put a published tag at risk if the rule did not apply. Tried: 0.7 is the first release under the ruleset, and the release workflow created the tag `v0.7` and its release with the built-in token, about two and a half hours after the ruleset was made. `ratchet.irreversible-waits` is "text only for now" in [REGISTER.md](../REGISTER.md): a hook is built only when it runs in every harness the project uses, and the tripwire runs only in Claude Code.

**The case.** `TagRuleset` in [test_tripwire.py](test_tripwire.py) reads the file strictly and pins exactly these fields, these three rules in this order and no `creation`, and the one bypass actor. It also reads `release.py` and fails if it holds a `PATCH`, `DELETE` or `PUT`, or no longer creates a tag with its one `POST`.

**What it does not claim.** The test reads the file and `release.py`, not GitHub. It does not see whether the ruleset on GitHub is still the one in the file, or still active: that was read back once, on 2026-11-19. Deleting or moving a tag has not been tried.

## Why JSON

The rules are data that the checks and a project's CI must read. The format was chosen so that the checks need nothing but a Python interpreter:

- Python's standard library reads JSON in every supported version. It reads TOML only from 3.11, and it does not read YAML at all.
- The Python that ships with a common developer operating system is older than 3.11. A check that needs a newer interpreter, or a package, is a check that does not get run.

The cost is that JSON has no comments and escapes quotation marks. The rules are one sentence per field, so it stays readable, and anything that needs explaining belongs in the changelog or in a decision.
