## The threat model

One text for every check here, by [D-2026-11-22-second-redraw](../decisions/D-2026-11-22-second-redraw.md). A review brief cites it.

**What every check here is for.** Ratchet's checks catch mistakes and drift: a rule copied wrong, a test that was dropped, a step taken the usual way without its approval, a job that stopped reporting.

**What no check here is for.** They are not written to stop someone who means to get past them. An agent or a person with write access can soften a rule, reword a check or take a step another way, and a check in the repo will often not see it. What stands against that is a lock at the host: the owner's required review of the paths that hold the rules and the checks, from an account the agents cannot approve with. Where that lock is not built, nothing stands against it, and the register says so. No check guards against someone who controls the owner's account, the host, or the machine a session runs on.

**Tripwires.** A script that runs only on an agent's machine, with no lock at the host behind it, is a tripwire. It catches the usual way and no other.

**Each check's own limits.** This shared text sets the threat model for every check. Each check states its own, narrower claim, under "What it claims" and "What it does not claim", and that claim sets what the check covers.

**When a review finds something the check does not cover.** A finding that the check's own claim does not cover starts no new round of hardening. It becomes one question to the owner: widen the claim by a decision, or record the finding as outside it. A finding inside the check's own claim is fixed as before, and `ratchet.two-rounds` still applies.

## Data files and strict forms

No check here looks for rules in free Markdown. A check that does can be shown a file in which a reader sees a row and the check does not: an indented row, a row in a comment, a row under a heading that is not a heading. Each way that was found is closed the same way:

- **What a check needs to read is data.** The register is `register.json`. A data file is read strictly: valid JSON in UTF-8, no field twice in one object, no field the check does not know, every value of the kind it must be.
- **Every file is strict UTF-8.** A check decodes every file it reads as UTF-8 and fails on bytes that are not, with the file and the byte named. No byte is read as some other character, so a file with a wrong byte never compares equal to a file without it.
- **What people read is generated.** `REGISTER.md` is written from the data file and compared with it byte for byte. Nothing can be added to the generated file, hidden in it or changed in it without failing the check.
- **A value is text, never Markdown.** When a value from a data file is written into a generated file, every ASCII punctuation mark in it gets a backslash, so Markdown reads none of it as markup. A value cannot become a link, an image, emphasis, HTML or a comment. The generator does not try to work out what Markdown would make of a value.
- **Code is the one other form.** A part of a value between a pair of backticks is code. That is the data's own way to mark it, and the generator writes it as a code span. Two such parts have text between them, and code has no spaces at its ends.
- **Characters from one fixed list.** A value is one line. Every character in it is a Latin letter, a digit, a plain space or one of the marks listed under [The characters a value may hold](#the-characters-a-value-may-hold). Everything else is refused, with the character named: other scripts, combining marks, control and format characters, other kinds of space, line and paragraph separators, fillers that show as nothing, lone surrogates, the replacement characters, characters that are written right to left, controls that change the order a line is shown in, and compatibility forms such as full-width letters. An `@` between two characters is refused outside code, because it is read as a mail address whatever is escaped.
- **The list is code points in the check.** It stands in [registry.py](registry.py) as ranges of code points. The check does not ask the interpreter what kind of character it has, because the answer depends on the version of Unicode the interpreter carries. A value is valid or not by the list alone, the same on every supported version of Python.
- **No name between two colons.** A colon, then one or more letters, digits, `_`, `+` or `-`, then a colon is refused, in text and in code. A site that renders the file may replace such a name with a picture after Markdown is done, and no backslash stops that.
- **What that costs.** A value is written in Latin script: no other script, no symbol that is not on the list, and an accented letter only in its one-character form. A time with seconds, or anything else with a word between two colons, is written another way. A link in a value is shown as its text.
- **Keys, statuses and versions are not free text.** Each has its own exact form and is written as it stands.
- **One policy for line endings.** CRLF is read as LF, by every check and by the generator. Generated files are written with LF. A carriage return alone counts as a difference. One exception: the block that `check_register.py` generates into a project's instruction file is compared as it stands, so a line of the block or a marker that ends in CRLF fails, and the rest of that file, which is never read, may keep its CRLF. See [check_register.py](#check_registerpy).
- **A file that failed once fails forever.** Every way that has been found to hide something from a check is a copy under [fixtures/](fixtures/) that must fail, with a test that names the message.

## The characters a value may hold

741 characters, and no other:

- **Latin letters.** `A` to `Z` and `a` to `z`. U+00C0 to U+00FF without the two signs U+00D7 and U+00F7. U+0100 to U+024F. U+1E00 to U+1EFF. Left out of those ranges: the compatibility forms U+0132, U+0133, U+013F, U+0140, U+0149, U+017F, U+01C4 to U+01CC, U+01F1 to U+01F3, U+1E9A and U+1E9B, and the click letters U+01C0 to U+01C3, which look like a pipe and an exclamation mark.
- **Digits.** `0` to `9`.
- **The plain space.** U+0020.
- **The ASCII marks.** All 32, from `!` to `~`. Two have a meaning of their own: a pipe is refused because it would break the table, and a backtick marks code.
- **Sixteen marks outside ASCII.** ¡ U+00A1, £ U+00A3, § U+00A7, « U+00AB, ° U+00B0, · U+00B7, » U+00BB, ¿ U+00BF, – U+2013, — U+2014, ‘ U+2018, ’ U+2019, “ U+201C, ” U+201D, „ U+201E and € U+20AC.

What the list is chosen to give, and how far that goes:

- **The order of a line.** No character on the list is written right to left, is a digit of a right-to-left script or is a control for direction. By the Unicode rules for mixing directions, a line made only of such characters is shown in the order it is stored. A test reads the direction class of every character on the list from the interpreter's own tables, on every supported version. It has not been tried in a browser.
- **Compatibility forms, not look-alikes.** No character on the list is a compatibility form: a test compares each with its normal form NFKC, and no two of them join into another, so a value is in the normal forms NFC and NFKC as it stands. That shuts out full-width letters, ligatures, the long s and the like. It is not a protection against characters that look like one another. Some on the list do in some fonts: the capital `I` and the small `l`, the digit `0` and the capital `O`, a dash and a hyphen, a curved quotation mark and a straight one, and letters that differ by a small accent. The division slash, the minus sign and the ratio sign are refused because they are not on the list, not because the check knows what they look like.
- **Adding a character.** A character is added to the list only by a decision, because that loosens the check.

## check_register.py

```sh
python3 checks/check_register.py register.json
python3 checks/check_register.py register.json --markdown REGISTER.md
python3 checks/check_register.py register.json --markdown REGISTER.md --agents AGENTS.md
python3 checks/check_register.py register.json --print-markdown
python3 checks/check_register.py register.json --print-instructions
```

**It writes nothing** (round 3 of #100). `--print-markdown` prints `REGISTER.md` as the register generates it, and `--print-instructions` prints the instruction file that the register names with the block brought up to date. Each prints that file to standard output and nothing else, prints nothing and fails when there is a problem, and takes no other option. To put a file in place, print it to a new file and move that over the old one:

```sh
rm -f REGISTER.md.new && python3 checks/check_register.py register.json --print-markdown > REGISTER.md.new && rm -f REGISTER.md && mv REGISTER.md.new REGISTER.md
rm -f AGENTS.md.new && python3 checks/check_register.py register.json --print-instructions > AGENTS.md.new && rm -f AGENTS.md && mv AGENTS.md.new AGENTS.md
```

`rm -f` removes a symbolic link that stands at either name, never what it points at, so neither the redirection nor `mv` follows a link, and `mv` puts a regular file in its place rather than moving the new file into a directory that a link leads to. The new file always stands in the directory the command runs in, under the file's plain name with `.new` after it, never under the file's own path. For an instruction file in a directory, such as `docs/AGENTS.md`, that is `rm -f AGENTS.md.new && python3 checks/check_register.py register.json --print-instructions > AGENTS.md.new && rm -f docs/AGENTS.md && mv AGENTS.md.new docs/AGENTS.md`: only the last two steps touch `docs/`, after the check has refused a link on that path. `AGENTS.md.new` beside the target, `docs/AGENTS.md.new`, would be emptied by the redirection before the check runs, through a link at `docs` if there is one. `upgrade.py` prints these commands for the register it reads.

**What it claims.** Every rule that `register.json` adopts is a rule in Ratchet at the version the register states, and for a copied row its rule, ratchet and source are Ratchet's own, character for character. A row adopted by reference claims less: see "Adoption by reference, the weaker mode" below. With `--markdown`, the file given is exactly what the data generates. With `--agents`, the file given exists and holds none of the placeholders of `templates/AGENTS.md`, a fixed list of exact texts, `PLACEHOLDERS`, a placeholder nested in another one on it on its own, and each one it still holds is named. It does not parse the file, so it does not see a placeholder that is not on the list. The workflow that `init.py` writes passes `--agents AGENTS.md`, so the project's CI stays red until `AGENTS.md` is filled in. The cases are in [test_init.py](test_init.py) and in `test_check_register_fails_on_the_placeholders_of_the_agents_template` in [test_checks.py](test_checks.py): the template fails naming each placeholder, a file with only the handover's `<n>` left fails naming it, this repo's `AGENTS.md` passes, and a missing file fails.

When the register names an instruction file in `instructions`, the check also generates a block of the rules from the register, the same sections as `REGISTER.md` under a heading of its own, and fails unless that file starts with the begin marker and holds one end marker after it, the HTML comments `BEGIN` and `END` in `check_register.py`, which hold `ratchet:begin` and `ratchet:end` with one space on each side between the comment's marks, each alone on its line, at its start, ending in LF, and between them, byte for byte, the block. A line that holds `ratchet:begin` or `ratchet:end` in any other form, in any case, anywhere in the file, inside a code block or a comment too, is a broken marker. Nothing else in the file is read: it must be UTF-8, and the rest of it is the project's own, never parsed. `--print-instructions` prints the file with the block between the markers, or, in a file with no marker, at its start followed by an empty line, and prints the block alone for a file that does not exist. It changes no other byte of the file, and it prints nothing where the markers are broken or the block is not at the start, where the file is not UTF-8 or not a plain file, or from a register that does not pass. This is `D-2026-11-20-generated-block`, from issues #76 and #89: the project keeps its rules where its agents read, and the check sees the text of each rule, not a marker that stands for it.

**Where the block stands.** The begin marker is the first line of the file: no byte stands before it, not an empty line and not a byte order mark. So no text before it can open a code block, a comment, or an element such as `<div hidden>` or `<details>` that puts the block in an example or out of sight, and the check needs to read no Markdown to know it ([D-2026-11-16-strict-forms](../decisions/D-2026-11-16-strict-forms.md)). Two places were weighed in round 2 of #100: the start, or anywhere after a test of the text before it that refuses an open code block, comment or element. The start was picked, as the smaller rule: it needs no reader of Markdown, and a reader of Markdown that is small and refuses what it is not sure of would still have to know every way to open a code block or an HTML block. The cost is that the block comes before the project's own heading, and that a file which must start with something else, such as front matter, cannot hold it.

**A marker in disguise.** The marker words are found in any case, and in disguise: a character outside printable ASCII may stand in place of each character of the word, and any number of them between two. So a letter of another script, an accented letter, a character that shows as nothing, a soft hyphen or a control character of ASCII such as NUL or DEL in the word still makes it the word, and a full-width form of ASCII is read as its ASCII character first. Such a word anywhere in the file is a second marker, so a copy of the block under markers that look like the real ones fails, and so does such a marker in place of the real one. At least 7 of the characters of the word must be its own, so text in another script is not taken for it. Where the word stands, a line is read in one of two ways, after the full-width forms are read as ASCII:

- A line shaped like an HTML comment is read as strictly as before the review of step 9a: 7 of the word's own characters are enough, wherever they stand. Such a line holds `<` or `>`, or stands after a line that opens a comment and before the line that closes it. So a decoy in a comment whose word is `ratchet:𝐫𝐮𝐥𝐞`, `ratchet:𝐛𝐞𝐠𝐢𝐧` or `ratchet:𝚎𝚗𝚍`, its letters after the colon all math-bold or monospace, accented, or of several scripts, is found, and so is such a word on a line of its own inside a comment, or between dashes that only look like ASCII. No Markdown is read, so the mark that opens a comment opens one in code too, and the lines after it are read this way.
- On any other line, one of the word's own characters must also be a letter after its colon. "ratchet" alone is 7 characters, so without that, prose that names Ratchet in a script with no spaces between words, such as `ratchetのルール` in Japanese or `ratchet的规则` in Chinese, was taken for the word in disguise (review of step 9a). There, a word that merely holds "ratchet" in prose is not taken for a marker in disguise. That is the boundary: only an exact marker line counts as a marker, and a line with no `<`, no `>` and no open comment cannot be one, so it cannot hide one either (review of d3f25aa).

`block-cjk-prose` and `ref-cjk-prose` hold prose in Japanese, Chinese, Korean, Thai and Russian that names Ratchet, and pass. `block-lookalike-in-cjk` and `ref-lookalike-in-cjk` hold a marker in disguise among it, and the fixtures named `-math-bold`, `-monospace`, `-accented`, `-mixed-script`, `-comment-lines` and `-dashes` hold the decoys above, and fail. The check asks no table of Unicode, so the answer is the same on every version of Python. A line of printable ASCII alone is searched for the word as it is, and a line with any other character is read in one pass.

**The path of the instruction file.** Before anything is read or written there, every part of the path, from the directory of the register down, is checked: no part may be a symbolic link, each part before the last is a directory that exists, and the file, resolved, stays inside the directory of the register. The form of `instructions` already refuses `..`, `.`, an empty part and an absolute path. The file is read without following a link at its last part (`O_NOFOLLOW`), by the check and by `generate.py`, which checks the path the same way before it reads or writes this repo's instruction file. A project whose instruction file is a link, such as `CLAUDE.md` pointing at `AGENTS.md`, names the file the link points at, or replaces the link with a regular file. The register, and each file named with `--markdown` and `--agents`, is taken by the path as given and refused, in every mode, when that path holds a part `..`, or passes through a symbolic link below the working directory or the enclosing git root, so a register reached through a link that git tracks is not checked as if it were the project's (see [No write through a link](#no-write-through-a-link)).

**What it does not claim, about the block.** It does not read the rest of the file, so text after the block that contradicts it is the project's own; the block says that `REGISTER.md` takes precedence. A marker word written entirely in lookalike letters, with fewer than 7 of its own characters, or with none of its own letters after the colon on a line that holds no `<` or `>` and stands in no comment, or written as an HTML entity such as `&#58;`, is not found. A directory on the path that is replaced by a link between the check and the read is not caught: the threat is a link committed to the repo, not another process on the same machine.

An adopted rule may carry a translation of its rule (#77): a language code, the text, and the sha256 of the rule's English text, its UTF-8 bytes in lowercase hex. The check fails when that sha256 is not the one of the rule's text in Ratchet at the version the register states, and names both. So an upgrade that changes the rule fails until its translation is made again, and `upgrade.py` names it. Only the rule is translated, not its ratchet: the rule is what the people who work in the project's language must follow, and the ratchet names a check, its files and its commands, for whoever builds it. The translation stands in `REGISTER.md` and in the block, in a table of its own under the English rules, which stay the rule. It is text from the fixed list of characters, like every value: Latin script, Swedish letters among them, passes, and every other script is refused.

**Adoption by reference, the weaker mode.** From 0.11 a Ratchet row has two modes ([D-2026-11-22-second-redraw](../decisions/D-2026-11-22-second-redraw.md), step 9a). A copied row is as above, and is the only mode in which the check sees the text of a rule. A row by reference holds no rule text: it names the key, in `stands_in` the Markdown file where the rule stands in the project's own words, which is the wording in force, and in `sha256` the hash of the rule and its ratchet in Ratchet at the register's one `ratchet_version`: the sha256 of the UTF-8 bytes of the rule, one line feed and the ratchet, in lowercase hex. It may carry `status` and `where` on the same terms as a copied row, and nothing else. The file holds the marker line once, `MARKER` in `check_register.py`: an HTML comment that holds `ratchet:rule`, one space and the key, with one space on each side between the comment's marks, alone on its line and ending in LF. Nothing else in the file is read.

To take the sha256 of a rule, read it from `ratchet.json`, so that no rule text passes through the shell, where a backtick, a quote or a `$` in it would change it. With the key in place of `ratchet.fresh-context`:

```sh
python3 -c 'import hashlib, json, sys; r = [r for r in json.load(open(sys.argv[1], encoding="utf-8"))["rules"] if r["key"] == sys.argv[2]][0]; print(hashlib.sha256((r["rule"] + "\n" + r["ratchet"]).encode("utf-8")).hexdigest())' .ratchet/ratchet.json ratchet.fresh-context
```

`test_checks.py` runs this command through `/bin/sh` on every rule of Ratchet that holds a backtick or a quote, and on a rule made up in the test that holds a backtick, both quotes, `$`, `$()`, `\` and `%`, since no rule of Ratchet holds `$` today. A row whose sha256 is wrong fails, and the check prints the sha256 it expects, so the check itself gives the right one too. Set it only after the wording in the file has been read against the rule.

What it claims, for a row by reference: the key is a rule in Ratchet at the version the register states; the sha256 is that rule's and its ratchet's, so an upgrade that changes either fails until the sha256 is set again; `stands_in` has the path form of `instructions` and is checked on its path the same way, with no link on it, no `..` and `.md` only; the file exists, is a plain file and is UTF-8; every line in it that holds the word `ratchet:rule`, in any case and in disguise as the words of the block are found, is an exact marker line; the marker of each row that names the file stands in it once; and no marker there names a key that no row by reference names that file for. It refuses a row with both rule text and `stands_in` or `sha256`, a row by reference with a translation, `stands_in` that names the instruction file, in any case, `stands_in` or `sha256` on a rule of the project's own, and a field it does not know. On a pass it prints, for each such row, the label the decision gives, with "guarded" in place of the decision's "built" so that "built" means only a rule's enforcement on the same screen ([D-2026-11-23-new-rules-first](../decisions/D-2026-11-23-new-rules-first.md)), which `REGISTER.md` shows too: "Adopted by reference, the weaker mode. The wording in force is the project's own, in the file named. The check sees a marker, not the words. The wording is not guarded against softening." It says "guarded" only when the register copies the row of `ratchet.owner-paths`, not by reference, with the status `built`: the check reads the register's own claim, not the host. A row of `ratchet.owner-paths` by reference does not count, since the check does not see its wording, and that wording is what protects the others.

What it does not claim, for a row by reference: it does not read the words under the marker, or whether they say what the rule says, or whether any harness loads the file. It reads no Markdown, so a marker line in a code block or a comment counts as a marker. It reads only the files that rows by reference name, so a marker in another file is not seen. A softened wording is caught only by the owner's review of the file, which `ratchet.owner-paths` asks for and the check does not see. By the shared threat model, this mode gets its fixtures and no further hardening.

A register with rows by reference may mix them with copied rows and name an instruction file. `REGISTER.md` is optional for it: with `--markdown`, a file that is not there is not a failure, and the check says so; a file that is there, or anything else at that path, must be what the register generates. Where it is generated, and in the block, the rows by reference stand in a table of their own, "Rules adopted by reference", with the file each names and its label, and no rule text. `--print-markdown` and `--print-instructions` print that table, read no file a row by reference names, and never print a marker line: the marker is the project's to put in its own file. `upgrade.py` says, for a changed rule adopted by reference, whether its sha256 still matches, and when it does not, prints the new one and asks the project to read its wording again.

**Adopted in part.** From 0.12 a row by reference may be adopted in part, when the project's own wording states the rule's core but not every clause. No field is added, and the clauses stand in the row's `where`, which is then exactly `Not stated here: <clause>; <clause>.`: the phrase `PART` in `check_register.py`, the clauses that the project's wording does not state, each joined to the next by a semicolon and one space, and one period at the end. One clause is `Not stated here: <clause>.`. A clause is not empty, holds a letter or a digit, has no space at its ends, holds no `;` and no period followed by a space, so no sentence follows the list, does not end in a period, and stands once. It is text like every value, and may hold code between backticks. A row without the phrase claims the whole rule, as before. When the wording leaves out any part of a sentence of the rule, list that whole sentence as one clause, not the part: an adoption report on 0.12 found that listing the parts missed one more each round of review. A row by reference of a text-only rule, which took no `where` before, takes one, and only as this phrase, so the form of `register.json` changes in 0.12 ([D-2026-11-23-partial-adoption-form](../decisions/D-2026-11-23-partial-adoption-form.md)), and the count toward 1.0 starts again from 0.12.

What it claims, for a row adopted in part: its `where` is in that one form; the row is by reference, since a copied row holds the whole rule and a rule of the project's own stands in full; it is not `built`, since the rule is not fully held, so a rule that names a check has the status `text only for now`; and on a rule that is text only, whose row has no `status` and otherwise no `where`, the phrase is the one `where` it may have. The words "not stated here" anywhere in a `where`, in any other form, fail as a broken phrase, so a list is never half read. They are found in a skeleton of the text, `part_skeleton` in `check_register.py`, so that a look-alike fails closed: read in NFKC, in lower case and decomposed, without combining marks; an ASCII letter stands as itself and a digit that looks like a letter of the phrase as that letter; every other ASCII character is left out, spaces, punctuation and every mark of Markdown with them, so `` `Not` stated here`` and `*Not* stated here` are found; any other letter or digit stands for any one letter, so `Nót` and `ħere` are found; and any other visible character outside ASCII stands for one letter or none. A value holds only the characters of the fixed list, so a Cyrillic letter, a full-width letter or a character that shows as nothing fails before that, as every value does. A clause is text by itself, so a pair of backticks stands in one clause: a semicolon inside code, as in ``Not stated here: `one; two`.``, splits the code and fails, and so does a semicolon in code that splits nothing. On a pass it prints, before the label of every row by reference, "Adopted in part. Not stated in the project's wording: " and the clauses, and `REGISTER.md` and the block show the same in the table "Rules adopted by reference". The summary counts the rows adopted in part. `upgrade.py` keeps the phrase in the entry it prints, whether the rule comes to name a check or comes to be text only, asks that the clauses be read against a changed rule too, and leaves it out of the entry of a removed rule for `own`, which holds Ratchet's whole text. `init.py` in adopt mode names the option in one line.

What it does not claim, for a row adopted in part: it sees the phrase, not whether the clauses listed are the ones the project's wording leaves out, nor whether the wording states the rest. A row that claims the whole rule while its wording leaves a clause out passes as before, and a clause listed that the wording does state is not seen either. Both are for the owner's review of the register and the file, as for every row by reference.

**Against which threat, adopted in part.** A project whose wording holds a rule's core but not every clause either adopts far fewer rules than it follows, or puts a marker on wording that says less than the rule and claims the whole of it. With the phrase, the gap is written in the register, labeled wherever the row is shown, and a row with a gap cannot be marked built. Not against a list of clauses that is wrong on purpose: see what it does not claim.

A rule of the project's own may carry `status` and `where` (#60). It does not have to, so a register written before 0.10 stays valid. When it does, they are read as an adopted rule's: the rule's ratchet starts with "Check:", the status is `built` or `text only for now`, a built check says where it lives, and a `where` needs a status. Each own rule with a status gets a row under "Where each check stands", after the adopted rules, and the summary counts them apart.

**Against which threat.** An agent, or a person, softens an adopted rule in the project's own copy, or adds a rule of its own under Ratchet's name, and nobody notices because the register still looks like Ratchet. With an instruction file named: the copy of the rules in the file the agents read is edited by hand, or drifts from the register, or a second, softer copy is put next to it under a marker that looks like the real one. With a translation: the English rule changes and its translation in the block still says what the old rule said. With a row by reference: Ratchet changes the rule or its ratchet and the project's wording is never read again, the marker is lost or doubled in an edit, a copy of the marker in disguise is put next to it, or the row names a file outside the repo or behind a link. Not against a wording softened on purpose under its marker: see what it does not claim.

**The data file.**

```json
{"project": "the project's name",

An adopted rule that names a check must have a status, and an own rule may. `instructions` and `translation` may be left out. `instructions` is a path relative to `register.json`: parts of letters, digits, `.`, `_` and `-` joined by `/`, none of them `.` or `..` and none starting with `-`, ending in `.md`, at most 200 characters. A language is two or three lowercase letters, with a region of two capitals after a hyphen if needed, such as `sv` or `pt-BR`. - That a value is shown as it stands has been tried with one Markdown library, the one with the table, strikethrough and autolink extensions that GitHub publishes. What a site adds on top, after Markdown is done, has not been tried.
- One such addition is shut out by the form of the data: a name between two colons is refused, so a value holds no emoji name for a site to replace with a picture.
- The others are not shut out. A value may hold `@name`, `@group/team`, `#123`, `owner/repo#123` and the id of a commit, short or full, and the check accepts them (fixture `references`). They are written with a backslash before each `@`, `#`, `/` and `-`, and Markdown shows them as text. A site that makes links of people, issues and commits after Markdown is done sees the same text with the backslashes as without, and may still make a link of it. Whether it does depends on the site and on the kind of page.
- It does not claim that two characters on the list cannot be taken for one another: see [The characters a value may hold](#the-characters-a-value-may-hold).
- A project may leave a rule out. A missing rule is a choice, not drift.
- It does not read the instruction file outside the block. What the project writes there, a rule that contradicts the block among it, is the project's own. The block says that `REGISTER.md` takes precedence.
- It does not see whether a translation says what the English rule says. A check cannot judge meaning. A changed translation is reviewed like any change to the register.
- A translation is in Latin script only, from the fixed list, and a rule has one translation, in one language.
- For a row by reference it sees a marker, not the words: see "Adoption by reference, the weaker mode" above. The label's "built" repeats the register's claim for `ratchet.owner-paths`, which the check does not compare with the host.
- The block is written with LF. A project whose instruction file has CRLF keeps it in the rest of the file, and the block, with its markers, has LF.
- It runs from the version of Ratchet it was fetched at. The project's workflow pins that version by commit, and a change to the workflow is a change to a check (`ratchet.owner-paths`).

## expected_tests.py

```sh
python3 checks/expected_tests.py
```

The reference check for `ratchet.expected-tests-ran`. It runs in a step of its own in CI, and it runs the suite in a process of its own: it starts [suite_runner.py](suite_runner.py), which runs `unittest discover -s checks` with unittest's own text runner, and reads what the runner records. A test that loads fixtures is a `FixtureTest`, from `suite_runner.py`, and loads each one by its name under [fixtures/](fixtures/), with `fixture_bytes`, `fixture_text`, `fixture_file` or `fixture_directory`. The last two give a copy in a scratch directory, made from the bytes that were loaded, and the check under test is run on the copy.

**What it claims.** In the run, every test that discover collects ran once under its id and passed, with exactly one outcome record, nothing ran that was not collected, the run finished, and every file under `checks/fixtures/` was loaded, with the bytes it held before the run, by a test that passed. Otherwise the check prints each problem and exits 1, whatever the suite's own exit status was.

**Against which threat.** Tests dropped by mistake, while the suite still looks green: a test skipped, errored or not prepared, a class or module whose set-up skips, a module that no longer imports, a run that exits before it is done, a run that returns before it is done because it was interrupted, told to stop or stopped at the first failure, two tests under one id so that one hides the other, a fixture added and never tested, or a test that names a fixture that is gone. A green summary says only that the tests that ran passed, not that the tests that were meant to run did.

**What it does not claim.** It does not stop test code written to defeat it. Such code runs with the same rights as the check: it can write records of its own, rewrite the runner or this check, or pass without testing anything. A change to `checks/` is read by the maintainer before it is merged (`ratchet.owner-paths`), and that reading is what stands against it.

**How it works.**

- **A process of its own.** The check makes a temporary directory, starts the runner as a child process with the path of a record file in it, waits for the child and reads the file. It does not run in the process it watches, so nothing the tests do to unittest's result, to its hooks or to the exit of their own process changes what the check sees: an exit is a missing record, not a pass.
- **What was collected.** Before the run, the runner writes a record "collected" for every test in the suite that discover returns, each with a number of its own, and the completion record holds unittest's own `countTestCases()` of the suite, taken before the run. A test that starts uses the number it was collected under. One that was not collected gets a new number, and fails the run.
- **The outcomes come from the runner.** The runner's result class takes the outcomes from unittest's result object: passed, failed, errored, skipped, expected failure or unexpected success. When a test stops, the runner writes one record "outcome" for it, with every outcome unittest gave it while it ran, in order. So a test that fails and then errors in `tearDown`, or whose subtests fail twice, has one record, and a second record of one instance is always a problem. An outcome of a subtest is an outcome of its test. An outcome given outside the run of its test, such as one given to a test after it stopped, is a record of its own at once. An outcome of a `setUpClass`, `tearDownClass`, `setUpModule` or `tearDownModule` has an instance that was never collected and never started, and fails the run.
- **The tests write only what they loaded.** A `FixtureTest` writes the fixture's name and the sha256 of the bytes it read, with the instance that was running. A load outside any test, as in `setUpClass`, does not count.
- **The completion record.** After unittest has printed its summary, the runner writes one last record with the number of tests collected, of tests run, of outcomes and of loads. A child that exits early, with `sys.exit` anywhere, `os._exit`, a `KeyboardInterrupt` or another error the runner does not catch, or that is killed, leaves it out, and the check fails. A run that returns early writes it: under unittest's Ctrl-C handler, after `result.stop()` sets `shouldStop`, or with `failfast` after a failure. The tests it did not run were collected and have no start, and the check fails on each.
- **Read strictly.** One JSON object per line, each ending in a line break, in UTF-8, parsed by the strict reader every check uses, `registry.strict_loads`: a field twice, `NaN` or `Infinity`, or a line nested too deeply is a problem, not a crash. The kind of a record is text, and its type is checked before the kind is looked up. Each kind of record has exactly its fields, each of its own form: an instance is a whole number from 1, the outcomes are a list of one or more of the six, a test is a name of one line with no lone surrogate, a fixture is a fixture's name, a sha256 is 64 lowercase hex digits. Anything else, a line cut off, a record after the completion record, a test collected after the run started, fails the run.
- **The comparison.** The check fails on: an exit status other than 0, or a signal; no completion record, two of them, or counts that disagree with the records; a test that was collected and did not run; a test that ran and was not collected, which covers no fixture; a test whose outcomes are not exactly one "passed", or that started and has no outcome; a second outcome record of one instance, after which the instance does not count as passed; an id that ran more than once; an instance collected twice or started twice, a start or an outcome that names another test than its instance; a fixture that no test that passed loaded with the bytes it held before the run; a load of a fixture that does not exist, or of other bytes; a fixture that changed while the suite ran; a suite that ran no tests.
- **The expected set.** The tests are the ones discover collects, and the fixtures are read from the directory, not from a list in a test and not from Markdown. Every file is one fixture. A file whose name starts with a dot, or holds a character other than letters, digits, `_`, `.` and `-`, fails, and so does a link.

**The cases.** Each is a test in [test_expected_tests.py](test_expected_tests.py). The tests in `Runs` run the check, as CI runs it, on a small suite in a scratch directory whose fixtures are a copy of [fixtures/tests-ran/tree/](fixtures/tests-ran/tree/). The tests in `Records` give the reader of the records a file that no runner wrote. **Known limits.**

- Test code that defeats the check on purpose, as above.
- It does not see whether a test uses what it loads. A test that loads a fixture and then checks something else passes. One mutation per case shows that a test uses its fixture (`ratchet.test-can-fail`), and the PR that adds a case shows the mutation.
- The outcome is a test method's, not a subtest's. A method that loads many fixtures in subtests counts for all of them when it passes, and fails all of them when one subtest fails.
- A test can still open a fixture by its path. Such a test is not counted, so the fixture stays expected and the run fails unless another test loads it.
- It relies on unittest's runner and on discover. A test that discover does not collect, because its module's name does not start with `test`, is not expected. Another runner, such as pytest, needs a check of its own.
- It reads how unittest reports the set-up and tear-down of a class or a module: as an outcome of an object that is not a test, the same in 3.9 and 3.12. Every such outcome fails the run.
- `python3 -m unittest discover -s checks` still runs the suite on its own, and records nothing. Only `checks/expected_tests.py` checks that every expected test ran.

## from_base.py

```sh
git show "HEAD^1:checks/from_base.py" > "$dir/from_base.py"
python3 -I "$dir/from_base.py" --base-sha BASE --head-sha HEAD
```

The base branch's checks judge a pull request. The job `base` of [checks.yml](../.github/workflows/checks.yml) runs on `pull_request`, checks out the merge commit that GitHub makes, takes this script from the base commit, `HEAD^1`, never from the pull request, and runs it from a directory of its own. The job `own` runs the pull request's own checks, as the job `checks` did before. The job `checks`, the status that the ruleset on `main` requires, waits for both, runs whatever they did, and passes only when `own` passed and, on a pull request, `base` passed too. On a push to `main`, `base` does not run, and `checks` passes when `own` does. This is how six entries of [REGISTER.md](../REGISTER.md) are "built" by where they are enforced ([D-2026-11-22-second-redraw](../decisions/D-2026-11-22-second-redraw.md)): `ratchet.register-on-top`, `ratchet.expected-tests-ran`, `repo.rules-as-data`, `repo.checks-fail-on-fixtures`, `repo.version` and `repo.new-rule-used`.

**What is the rule, and what is the data under test.** For Ratchet a pull request changes `ratchet.json`, `register.json` and the generated text as a matter of course: they are what it is judged on, not what it is judged by. The code of the checks is what it is judged by: every file directly under `checks/` whose name ends in `.py`, and every file in a directory under `checks/` other than `fixtures/`. Everything else, `checks/fixtures/` and `checks/README.md` among it, is data, since `generate.py` writes part of it. So the script makes two work trees, beside the checkout, sharing its history and tags:

- **The tree of the data**: the merge commit, with the code of the checks taken from the base, and none of the pull request's. A file of code that only the pull request has is there, empty, so that a link to it from the data leads somewhere and none of its code runs: a `json.py` beside the checks, which the base's scripts would import in place of the standard library's, has nothing in it. The base's `generate.py --check`, `check_register.py register.json --markdown REGISTER.md` and `released_text.py` run there, on the pull request's data.
- **The tree of the code**: the base commit, with the pull request's code of the checks, but the base's tests, `checks/test_*.py`, and the base's runner, `expected_tests.py` and `suite_runner.py`. The base's `expected_tests.py` runs the base's suite there, with the base's fixtures and data. So every fault the base's fixtures show must still be caught by the pull request's checks, under the base's runner.

**What it claims.** On a pull request, the job `checks` is red unless the base branch's scripts pass the pull request's data and the base branch's tests, under its runner, pass the pull request's checks. It is red when the pull request changes `.github/workflows/checks.yml` or the runner of the suite, `checks/expected_tests.py` or `checks/suite_runner.py`, since the base cannot judge what judges it, when the base lacks a script the job runs, and when the checkout is not the merge of the pull request's head into the base or a later commit of it. When it fails, it names each command that failed, in which tree, and the paths the pull request changes that the base judges by.

**Against which threat.** The shared one: a pull request that softens a check, its test or its runner together with what the check judges, by mistake, so that its own checks pass it. A change of form is the same case seen from the other side: the base cannot judge it, and says so.

**A change the base cannot judge fails closed.** A pull request that changes a check so that the base's tests no longer pass it, renames a field of a data file, changes what `generate.py` writes, or changes the workflow or the runner, fails `base`, and never passes silently. Its job `checks` stays red, so the agents' account cannot merge it. The maintainer reads the change and merges it as an administrator, who is exempt from the protection ([D-2026-11-16-code-owner](../decisions/D-2026-11-16-code-owner.md)). So it is for the pull request that adds this job: its base has no `checks/from_base.py`, and the step says so. A new script that writes files fails too, since the base's sweep in `test_writes.py` names every script that may write, and so does a new script that the base's tests read in another way. A check tightened so that the base's data and fixtures still pass, a new test, a new fixture and a new check that writes nothing pass `base`.

**What it does not claim.** GitHub runs the workflow of the pull request's merge commit on `pull_request`, so a pull request can change the workflow so that `base` does not run, or does not run this script. Such a change fails `base` as long as `base` still runs this script from the base, and nothing in the repo stands against a change that removes it: the owner's required review of `.github/` does (`ratchet.owner-paths`). It does not use `pull_request_target`, which would run the base's workflow with the base's rights on the pull request's code. It does not see what the host requires: that the ruleset on `main` requires the job `checks` was read back on 2026-11-22, and the register says so. The ruleset does not require a branch to be up to date before the merge, so the base it judges by is the one GitHub merged the pull request into when the job ran, and a later commit on `main` is not judged with it. The data it reads is the pull request's: a rule's `since` or text changed on purpose in `ratchet.json` is read by the owner, as before. The tests that run in the tree of the code run with the same rights as the checks, as `expected_tests.py` says. `templates/ratchet-checks.yml`, the workflow a project adopts, is not changed: it runs a tagged copy of Ratchet's checks, not the project's own.

| Case | Result |
|---|---|
| The data changes within the base's rules | Passes, and the two work trees are gone after the run |
| A check softened together with the data it judges, by less than the base's fixtures catch. The pull request's own checks pass it | Fails in the tree of the data |
| A check softened together with the test that would catch it | Fails in the tree of the code |
| A check softened together with its runner, which passes whatever happens | Fails in the tree of the code: the base's runner runs |
| A check and its test removed | Fails in the tree of the code |
| A `json.py` added beside the checks, which the base's script would import in place of the standard library's | Fails in the tree of the data: the file is there and empty |
| A new check that the data links to | Passes: the link leads to the empty file |
| A check tightened | Passes |
| A new test and a new fixture | Passes |
| A field renamed in the data, the check and its fixtures together, a change of form | Fails in both trees, names the paths and says why |
| A change to `.github/workflows/checks.yml` | Fails, and names it |
| A change to the runner, `checks/expected_tests.py` or `checks/suite_runner.py`. Merged, it would be the base's runner for the next pull request | Fails, and names it |
| A script the job runs that the base lacks, added by the pull request | Fails, and names it: the base cannot judge by a check it does not have |
| The base moved on after the pull request branched, with a stricter limit | Fails: the merge is judged by the newer base |
| A checkout that is not the merge: the head is not its second parent, the base is not an ancestor of its first parent, a commit id of another form, a commit with one parent | Fails, and says which |

The cases are in [test_from_base.py](test_from_base.py), each a dry run of the job: a small repo of its own with a base commit, a pull request's commit and their merge, judged by this script as the workflow runs it, with `python3 -I`. The checks of the small repo stand in for Ratchet's under the same names, so no case runs this repo's suite. `test_budget.py` checks that every entry of the register marked "built" is in its table of enforcement points, that its `where` names the point and the command the base runs, that the workflow shows the job `base` and a job `checks` that waits for it, and that a claim the repo does not show fails.

## watch_sources.py

```sh
python3 checks/watch_sources.py
python3 checks/watch_sources.py --data sources.json
```

This is not a reference check for a rule. It is a tool this repo runs on its own sources, the list `sources` in [sources.json](../sources.json) that `RATCHET.md` shows under Sources. The data file is an object with the one field `sources`, and any other field fails the run before anything is read ([D-2026-11-19-batched-releases](../decisions/D-2026-11-19-batched-releases.md)). Its tests run in this repo's CI with the others. The script itself is meant to run once a day in a workflow of its own, with the workflow's built-in token.

**What it claims.** For each pinned source, the run reads the head of the source's default branch and compares the pinned commit with it, through the GitHub REST API. It reads the head as `commits/HEAD`, which GitHub resolves to the head of the default branch, so it never reads the name of the branch.

- A source without a directory has moved when the compare is not `identical`.
- A source with a directory has moved when at least one changed file is under the directory, or when the compare is `behind` or `diverged`. If the API does not say which files changed, or lists 300 files and none of them under the directory, the watch cannot tell, and counts the source as moved.
- A source that has moved has one open issue, titled `Source moved: <name>`. A pinned commit that is not found upstream has one open issue, titled `Source pin missing: <name>`. A source that has not moved writes nothing.
- Every read comes before any write. Then every title and body is built and passes one gate, and only then is anything written. A read that fails, an answer of a form the watch does not know, or a title or body that fails the gate, fails the run before anything is written.

**Against which threat.**

1. A pinned source moves, and nobody notices, so a rule keeps crediting a source that now says something else, or a project keeps copying a skill at a pin that has gone (`ratchet.skills-pinned`).
2. Text from a source, from an answer of the API or from `sources.json` is written so that the issue pings someone, links somewhere, shows HTML or reads as an instruction (`ratchet.material-not-instructions`), or so that a line in the log is read by the runner as a command, such as `::warning::` or `##[error]`.
3. The token is printed in a log or an error, written into an issue, or sent to another host.

**No text from a source (`D-2026-11-17-new-approaches`, in PR #13).** Two review rounds found text from upstream that escaping did not make inert, and a token that got through an encoding the watch did not undo. So the watch no longer tries to make such text safe. No text from a source, and no text from an answer of the API, reaches an issue, a title or a printed line. An issue holds only these values:

| Value | From | Checked as |
|---|---|---|
| Name | `sources.json` | The narrow form below |
| Directory | `sources.json` | The narrow form below |
| Pinned commit | `sources.json` | 40 lowercase hex characters |
| Head of the default branch | The API | 40 lowercase hex characters |
| Status | The API | One of `identical`, `ahead`, `behind`, `diverged` |
| Commits ahead and behind | The API | Integers from 0 to 999999999 |
| Changed files, and those under the directory | Counted by the watch from the API's list | Integers, or "not listed by the API" |
| Compare link | Owner and repo from `sources.json`, and the two shas | `https://github.com/<owner>/<repo>/compare/<pin>...<head>` |
| Everything else | Fixed English text in the script | Each line exactly |

No commit subject, file name, branch name, author or message is written. The issue tells the reader to follow the compare link to see the commits and the files, and that what they find there is material, not instructions. File names are read only to count those under the directory. The name of the default branch is not read at all.

**No path in an error, and no unchecked value in a path.** An error names the request by a fixed kind written in the script and, where there is one, the source's name or the title, for example `source pstack: reading the head of the default branch gave 404`. It gives the HTTP status as an integer. It never names a path or an address. Every path is built from values of a strict form, and the transport sends no other:

| Request | Its kind in an error | The values in its path, and their form |
|---|---|---|
| `GET /repos/<owner>/<repo>/commits/HEAD` | `source <name>: reading the head of the default branch` | Owner and repo from `sources.json`, and the fixed `HEAD` |
| `GET /repos/<owner>/<repo>/compare/<pin>...<head>` | `source <name>: comparing the pinned commit with the head` | The pin from `sources.json`; the head from the API, checked as 40 lowercase hex characters first |
| `GET /repos/<owner>/<repo>/commits/<pin>` | `source <name>: reading the pinned commit` | The pin, 40 lowercase hex characters |
| `GET /repos/<target>/issues?state=open&per_page=100&page=<n>` | `reading the open issues of the target repository` | `GITHUB_REPOSITORY`, checked as owner/repo; integers |
| `POST /repos/<target>/issues` | `opening the issue <title>` | The target |
| `PATCH /repos/<target>/issues/<number>` | `updating the issue <title>` | The target; the number from the API, checked as an integer from 0 to 999999999 first |

Before it sends a request, the watch matches its path in full against one of these forms. A path of any other form fails the run with `<kind>: the watch does not build such a request`, and nothing is sent. Only the issue numbers that the watch opened or updated are printed, as integers.

**The data.** A source has a `name`, a `repo`, a `commit` and a `license`, and may have a `directory` and an `author`:

```json
{"name": "pstack", "repo": "https://github.com/cursor/plugins", "directory": "pstack",
 "author": "Lauren Tan", "commit": "35a90942a7f02e1ebbc2443643179815f2147954", "license": "MIT"}
```

- **The name** is lowercase letters, digits, `.`, `-` and `/`, starts with a letter or a digit, and is at most 100 characters long. It has no `_`, since the gate allows no `_` outside a link: in Markdown an `_` can start emphasis. 100 characters keep `Source pin missing: ` and the name at 120 characters, well within the 256 that GitHub takes for a title, so a title is never cut. A name that would be longer is refused. A name is used once, so two sources never share a title.
- **The directory** is parts of lowercase letters, digits, `.` and `-`, joined by single `/`, at most 100 characters. No part is `.`, no `..` stands anywhere in it, and it does not start or end with `/`.
- **Neither holds `www.` or `GH-` and a digit**, in any case. GitHub makes a link of the one and a reference to an issue of the other, from characters the form allows.
- **The repo** is `https://github.com/`, an owner and a repository, and nothing else. The owner is letters, digits and `-`, starts with a letter or a digit and is at most 39 characters. The repository is letters, digits, `.`, `_` and `-`, at most 100 characters, not `.` or `..` and not ending in `.git`.
- **The commit** is a full sha in lowercase hex. The author and the license are text from [the list](#the-characters-a-value-may-hold).

`RATCHET.md` shows the repo, then `, directory` and the directory as code, then the author in brackets after `by`. The generator and the watch read the sources with the same function in [registry.py](registry.py), and the generator fails on the same sources as the watch.

**One gate.** Every planned title and body, and every printed line, passes the same check before it leaves the watch:

- **A grammar of lines.** A title is `Source moved: ` or `Source pin missing: ` and a name of the narrow form. Each line of a body is a blank line, one of the fixed sentences, or one of the lines in the table above, each matched in full by a pattern of its own.
- **A small set of characters.** Outside a link, a line holds only ASCII letters, digits, the space and `.` `,` `:` `'` `(` `)` `/` `-`. So it holds no `@`, `#`, `<`, `>`, `[`, `]`, `!`, backtick, `|`, `\`, `*`, `_`, line break, control, or any character outside ASCII. Inside a link to `https://github.com/`, it may also hold `_`, as a repository name may. No printed line names a path, so a path is not let through. A line never holds `::`, and outside a link never `www.` or `GH-` and a digit.
- **The token.** No title, body or printed line holds the token as it stands.

If one planned title or body fails, nothing is written. The error names the planned issue and the line, never the text. A printed line that fails is replaced by `a line that did not pass the output gate is left out`. Errors give only the kind of the request and the HTTP status as an integer, never a path, never anything from the body or the headers of an answer, and never the text of a network error. An error the watch does not know is printed as its kind and the line of the script.

The gate cannot tell a token that is encoded, for example in hex, from a sha or a name. That is why nothing from an answer may reach a line, a path in an error included, and not a reason to undo encodings.

**Why the token needs nothing more.** The earlier version replaced the token in every answer and looked for it behind escapes and encodings, because upstream text went into issues and logs. Now no text from an answer is written anywhere, so a token that an answer holds, in any encoding, has no way out. The only values that are written are checked for a form that a token of GitHub's does not have, and the gate refuses the token as it stands in case one ever did.

**The size of a body.** No list from the API reaches a body, so its size does not depend on the source. The largest body has a name and a directory of 100 characters, an owner of 39 and a repository of 100, nine-digit counts, 300 changed files, all under the directory, and the notes on a `diverged` compare and on a capped list. It is 1390 bytes, and a test builds it. GitHub takes 65536 characters.

**The token and the transport.** The token is read from the environment variable `GITHUB_TOKEN` and from nowhere else. It is sent only to `https://api.github.com`: the transport refuses an address before it connects unless it is printable ASCII, since `urllib.parse` drops tabs and line breaks that `urllib.request` keeps, and unless, split with `urllib.parse`, the scheme is `https`, the netloc (the host and the port as written, and any userinfo) is exactly `api.github.com`, the path starts with `/` and there is no fragment. It never compares by prefix, so `https://api.github.com.evil.invalid/`, `https://api.github.com@evil.invalid/`, `https://user@api.github.com/`, `https://api.github.com:443/`, `http://api.github.com/` and `https://API.GITHUB.COM/` are all refused. A redirect is not followed. It is an answer of its own, and the run fails on it, so the token is never sent on. Without a token the reads run unauthenticated. If nothing has moved, the run passes. If something would be written, the run fails, names the titles and writes nothing.

**What the run does with each answer.**

| The compare says | What the watch writes |
|---|---|
| `identical`, and the head is the pin | Nothing. |
| `ahead`, for a source with no directory | It opens or updates `Source moved: <name>`, also when no file differs, as after an empty commit. |
| `ahead`, with a change under the directory | It opens or updates `Source moved: <name>`. |
| `ahead`, with changes only outside the directory, or with no changed file | Nothing. The run prints that the source has not moved under its directory. |
| `ahead`, with 300 files listed and none under the directory, or with no list of files | It opens or updates the issue and says that it cannot tell whether a file under the directory changed. |
| `diverged` or `behind` | It opens or updates `Source moved: <name>` whatever the directory, and says that the pinned commit is not in the history of the default branch. |
| `identical` while the head is not the pin, or anything else while the head is the pin | The run fails and writes nothing. |
| Not found, and the pinned commit is not found | It opens or updates `Source pin missing: <name>`. |
| Not found, and the pinned commit is found | The run fails. |
| Any other error, a redirect, or an answer of a form the watch does not know | The run fails and writes nothing. |

The watch updates only an open issue that it opened itself, as `github-actions[bot]`, with exactly the title. An issue by someone else with the same title is left alone. Two open issues of its own with one title fail the run. When the body would be the same, the watch writes nothing.

**What it does not claim.**

- It does not judge whether a move matters for a rule. That needs a reader, and the compare is material for one.
- It sees only the default branch and only sources on GitHub. It takes the default branch to be what GitHub resolves `HEAD` to, as it did for the sources here and for a repository whose default branch is `master` when this was written.
- It recognizes its own issues by the account `github-actions[bot]`. Run with another token, it does not find them and opens new ones.
- A run writes all of its issues or none, unless GitHub fails a write after an earlier one went through. Then the issues before it are written and those after it are not, and the next run writes them.
- GitHub may show a sha in an issue as a link to a commit of this repository, if this repository has one with that sha. That is a link to this repo, not a mention.
- That GitHub makes no mention, reference or link of a line in the gate's set, other than `www.` and `GH-` and a digit, is how GitHub documents its autolinks today. It has not been tried against a live issue. A repository with custom autolinks of its own may link more.
- A name or a directory of a source upstream that has a capital or an `_` cannot be watched as it stands. The name is ours to choose; the directory is not.
- The limit of 65536 is the one GitHub's answer to a body that is too long states. It is not in the REST reference.

## No write through a link

```sh
python3 -m unittest discover -s checks -p test_writes.py
```

Five rounds of review of #100 found ways for a script here to write outside the repo through a symbolic link. On 2026-11-21 the maintainer chose to stop hardening there and to state plainly what holds and what does not. A later pull request may remove the guards against links from `generate.py`, under "subtract first".

**What is guaranteed.** A second reviewer, from another model family, tried hard to break each of these at the head of #100 and confirmed all three.

- **`check_register.py` never writes.** It is the check that projects run. It prints `REGISTER.md` or the instruction file to standard output and writes no file. The sweep below allows no write in it.
- **The documented save commands never touch anything outside the repo, when they are run from inside the real repo directory.** They are the commands under [check_register.py](#check_registerpy), in `STARTING.md` and `UPGRADING.md`, and the ones `upgrade.py` prints. The new file always stands in the directory the command runs in, under a plain name, and `rm -f` removes a link at that name before the redirection, never what it points at. The two commands differ in their target. The one with `--print-markdown` writes `REGISTER.md`, a plain name in that same directory, and `rm -f` removes a link there before `mv`. The one with `--print-instructions` names the instruction file's own path, which may be nested: the check refuses a link on every part of that path before it prints, and only then do `rm -f` and `mv` run on it. `upgrade.py` quotes the script and the paths, and ends the options of `rm` and `mv` with `--`. A part of `instructions` may not start with `-`.
- **No script writes bytecode.** Every script in `checks/` that runs as a program sets `sys.dont_write_bytecode` before it imports a module from `checks/`, so Python writes no `__pycache__` next to the checks. `expected_tests.py` runs the suite with `-B` and `PYTHONDONTWRITEBYTECODE`, `suite_runner.py` sets the variable for every Python the tests start, and the tests that start `python -m unittest` or `python -c` pass `-B` too. Both workflows, `checks.yml` and `release.yml`, set `PYTHONDONTWRITEBYTECODE` for the job. `python3 -m unittest`, run by hand without `-B` or the variable, imports the tests and the checks before any code of theirs runs, and so writes bytecode.

**What the guards in `generate.py` and `init.py` are.** They are a safety net against mistakes, and against a tree that only adds links. They are not a boundary.

- `generate.py` runs code from the very tree it writes into. A pull request that adds a link can just as well change `generate.py`, and no guard inside `generate.py` can stop that.
- `init.py` is run by the owner, in their own project, at its start.
- Within that, `generate.py` writes only through `registry.write_file`, behind the gate `registry.refuse_links`. The gate takes the repo by the path as given and refuses it when the path holds `..` or passes through a link below the working directory or the enclosing git root, and when `register.json` is a link. It refuses a link that git tracks in the repo, or, where git cannot say, any link. `write_file` refuses a link on any part of the path it writes. The scan of Markdown files takes in no link.
- `init.py` takes its root from `PWD` when that names the directory it runs in. It refuses one that passes through a link, checks every file it would write for a link on its path while it plans, and does so again when it writes. So `--check` never says "would write" for a file a real run refuses, and a real run writes nothing when any file would be refused.

**What is not covered.**

- Entering the repo through a symbolic link to a directory. `init.py` alone reads `PWD`, and refuses a root through a link only when `PWD` names it. `generate.py`, `check_register.py` and the save commands take the working directory as the system gives it, already resolved, so they cannot see such a link even when `PWD` is set. The guarantee for the save commands holds when they run from inside the real repo directory.
- `..` in `PWD`, in the path `generate.py` was run by (`__file__`), or in `--source`.
- An anchor of the path check, the working directory or the enclosing git root, that is itself a link.
- Code written to get past the sweep of writes. The sweep catches mistakes, not disguise.
- `python3 -m unittest` run by hand without `-B` or `PYTHONDONTWRITEBYTECODE`, which writes bytecode before any code of the checks runs.
- Another process of the same user racing a tool between a check and its use, and an attacker who already controls the user's account, the Python install or the `git` on the path.

**The cases**, in [test_writes.py](test_writes.py), [test_init.py](test_init.py) and [test_upgrade.py](test_upgrade.py). The trees are made in a temporary directory when the test runs and never committed: a link committed here would make `generate.py` refuse to run on this repo. A git work tree is made there with `git init`, its name, mail and `gc.auto` set in that repo only. Each failing case compares every entry under the temporary directory, before and after the run.

- `check_register.py`: in trees with links of every kind, tracked by git or not, both print modes print the right bytes and write nothing. The documented commands, run through `/bin/sh` with links at `REGISTER.md`, `REGISTER.md.new`, `AGENTS.md.new` and a tracked link at `docs` for a nested instruction file, write nothing outside. An instruction file that is a link, or under one, is not printed. A register reached through a tracked link, or by a path with `..`, is refused in every mode, as are `--markdown` and `--agents` with `..`. A register that is not JSON or not UTF-8 is reported by both print modes. Compare mode with `CLAUDE.md` pointing at `AGENTS.md` passes. `upgrade.py` prints `rm -f --` and `mv --`, and quotes a script and a path with a space.
- `generate.py`: in a git work tree, untracked `.venv/bin/python` and `node_modules/.bin/x` do not refuse it, and nothing is written through them. A link that git tracks refuses it, as does a repo reached through a tracked link, with or without `--root`, and `--root` with `..`. An untracked link as the parent of a file it writes, as the file itself, and as `register.json` is not written through. Untracked links in `templates/` and `checks/`, and `templates/` itself as one, are not scanned. A folder that git does not track or ignores is walked, as is any repo with no `git` on the path or outside a work tree, and a link in it refuses.
- `init.py`: a project whose directory is a tracked link, with `PWD` naming it, is refused. A tracked `.github` link to a directory outside makes both `--check` and a real run refuse while they plan, and write nothing. So does a regular file at `.github` or `.github/workflows`, with no traceback.
- `registry` in the same process: `write_file`, the gate, `guard_path` and `link_on_path` on links made before and after the gate, a root that is missing, a link or not a directory, a link above the workspace that is not flagged, `..` refused, and the file of a part in `ratchet.json`, which must be a plain relative path.
- No bytecode: every script that runs as a program passes the sweep for the flag. The sweep fails on each wrong order in a sample. `generate.py --check` and both modes of `check_register.py`, run in a copy without `-B`, leave no `__pycache__`. A copy of `expected_tests.py` runs a suite of one test, whose child processes run `python -c` and `python -m unittest` on a module of their own, without `-B` and without the variable, and no `__pycache__` appears anywhere.

**The sweep.** A test reads every script in `checks/` with `ast` and fails on a call that writes anywhere but in the functions named for that script in `WRITERS`:

- `open`, `io.open`, `io.FileIO`, `codecs.open` and `os.fdopen`, unless their mode is left out or is a literal string with none of `w`, `a`, `x` and `+`.
- `os.open`, unless its flags are `os.O_` names that only read, or `getattr(os, "O_NAME", 0)` of one, joined by `|`.
- Arguments with `*` or `**`.
- The methods of `pathlib` that write, and the functions of `os`, `shutil` and `tempfile` that write, move, remove, link or make.
- `__import__`, an import of `pathlib` or `importlib`, a writing module imported under another name, and `open` used without being called.

`check_register.py` and `generate.py` must have no such call, and `registry.py` only in `write_file`. `run_pinned.py` writes only in the new directory that `main`, or `stored_blob` for `init.py`, makes with `tempfile` and removes at the end: the empty git directory, home and config that `Git.__init__` makes to read the store through, and the tree that `export` writes. The clone into a missing store, and the objects a fetch adds to it, are git's. `init.py`'s two functions that write must call `registry.guard_path` first. A sample file shows each kind of write found and each kind of call that only reads let through. The files `test_*.py` are not swept: they are the suite, not the checks, and they write only in directories they make with `tempfile`. The sweep reads code, not what it does: a write through `getattr`, `eval`, a subprocess or a module outside `checks/`, or any spelling written to get past it, is not seen. A change to `checks/` is read by the maintainer before it is merged (`ratchet.owner-paths`).

## generate.py

```sh
python3 checks/generate.py            # write the generated text
python3 checks/generate.py --check    # fail if any generated text is out of date
```

[ratchet.json](../ratchet.json) is the one place a rule is written. From it the generator writes the rule tables, the section of the principles in `RATCHET.md` and the list of their titles in `README.md`, the count of rules, [templates/register.json](../templates/register.json) and the registers under [fixtures/register/](fixtures/register/). From this repo's [register.json](../register.json) it writes `REGISTER.md`, and the block of rules at the start of the instruction file that the register names in `instructions`, `AGENTS.md`, as `check_register.py --print-instructions` prints it, with no other byte of that file changed. It fails, and writes nothing there, where the markers of that block are broken, the block is not at the start, or a part of the path is a symbolic link or leads out of the repo. Before anything else, with or without `--check`, it refuses to run when the repo, as given, passes through a symbolic link, while git tracks one in the repo, or, outside a git work tree, while any entry in it is one. It writes only through one function, which never writes through a link on its path, and its scan of Markdown files takes in no link (see [No write through a link](#no-write-through-a-link)).

**What it claims.** With `--check` it changes nothing and fails when:

- a generated table, count, file or fixture differs from what its data file gives
- a file does not hold exactly the generated blocks it must hold, once each, or a marker is missing or broken
- a file that must hold generated blocks is missing
- a file that holds generated blocks could hide one: it has a comment that is not a marker, a line that starts with `<`, a generated block inside a code block, or a code block opened in any way but three backticks
- a data file breaks its own format, for example a rule labeled `enforced` whose ratchet does not start with "Check:", a rule that is text only without its reason, or a value that holds a character outside the list or a name between two colons
- a file it reads is not valid UTF-8
- a markdown file in the root, in `templates/` or in `checks/` mentions a key that is not a rule
- such a file links to a local file that does not exist, with an inline link or with a link definition at the start of a line. Links to the web and links inside a page are not followed.
- the first entry in the changelog is not the version in `ratchet.json`, headed `## <version> (<date>)` or `## <version> (unreleased)`, an entry after the first is headed `(unreleased)`, or a heading of an entry is of another form
- the entries in the changelog do not stand newest first: each version, compared as a pair of integers, must be higher than the one after it, so a version twice or an entry moved up fails
- the command in `README.md` that fetches Ratchet is not the one line `git clone --branch v<version> https://github.com/fabian-von-tiedemann/ratchet .ratchet`, once, in a code block marked `sh`, for the highest version with a date in the changelog, or another line of `README.md` runs `git clone`. The line is matched whole, after the spaces that indent it, so a pin written in prose, a command with more on its line, or the command outside such a block does not count. `generate.py` reads no tags, so it does not claim that the tag exists: the window in which it does not is under "What it does not claim" in [released_text.py](#released_textpy)
- the landing page, `docs/index.html`, does not hold the line `<pre><code>git clone --branch v<version> https://github.com/fabian-von-tiedemann/ratchet .ratchet</code></pre>` exactly once, with any version, after the spaces that indent it, or another line of the page holds `git clone`. The generator writes into that line the version that the command in `README.md` must fetch, so `--check` fails when the page fetches another version than the README. The rest of the page is checked by a test: see [The landing page](#the-landing-page)
- the landing page does not hold the line `<p id="count" class="count"><strong>Ratchet today:</strong> the core has N rules. N describe a check and N are text only. Ratchet ships a reference check for N of the N, and you build the others.</p>` exactly once, with any numbers, after the spaces that indent it, or another line of the page holds `id="count"`. The generator writes the numbers from `ratchet.json`, as in the count of rules, so `--check` fails when a rule of the core changes kind, or gets or loses a reference check, and the page is not written again. The line says how many of the rules that name a check come with one from Ratchet, so that the number does not read as the number of checks that exist
- the landing page does not hold the line `<section id="values" class="values">` exactly once, after the spaces that indent it, then lines of the six forms the generator writes only, each exactly as it writes it, with text that holds no `<` or `>`, then a line `</section>`, or another line of the page holds `id="values"`. The generator writes the story, the line that leads to the values, each value and the line that weighs them from `values.json`, each as text, so `--check` fails when a value is changed and the page is not written again. A line between the two that is not of those forms fails, with or without `--check`, and the file is not written: a link added inside one of its paragraphs, or a second paragraph added on the line of one
- `values.json` is not a valid data file: not strict JSON in UTF-8, a field twice, a field missing or one it does not know, a list of values that is empty or not a list, a value that is not an object of exactly `prefer` and `over`, or a text that is not one line from [the list](#the-characters-a-value-may-hold), holds no words or holds code. Its story and values are text, not rules: no rule stands under a value, and nothing checks what a value says (`D-2026-11-23-values-and-principles`)
- `sources.json` is not a valid data file: not strict JSON in UTF-8, a field twice, any field but `sources`, a source of another form, a name twice
- the source of a rule cites a name that is not a source in `sources.json`. The source of a rule is empty, or citations separated by `; `, each of which starts with the name of a source and then, after a space or a comma, says what is taken from it
- `.github/CODEOWNERS` holds anything but the one rule that gives every path to the maintainer.
- there are more experimental rules than `experimental_cap` in `ratchet.json`, or the cap is not a whole number from 0 (see [The budget](#the-budget)).
- an experimental rule has stood through three releases and 60 days with no decision, `since` or `kept_by` breaks its form, or a heading of the changelog has a date that does not exist or is earlier than that of the version before it (see [The age of an experimental rule](#the-age-of-an-experimental-rule)).
- a principle or the principle of a rule breaks its form, or a markdown file in the root, in `templates/` or in `checks/` mentions a principle that is not in `ratchet.json` (see [The principles](#the-principles)).
- an experimental rule enters in this version and this repo's register does not adopt it nor does the rule say why Ratchet cannot use it, or the register adopts a rule that says so (see [A rule that enters is used](#a-rule-that-enters-is-used)).

From [sources.json](../sources.json) it writes the table of sources in `RATCHET.md`, and the first line of `RATCHET.md` says the version and its date, or that it is not yet released. The date of a version is in the heading of its entry in the changelog, and nowhere else ([D-2026-11-19-batched-releases](../decisions/D-2026-11-19-batched-releases.md)).

In the changelog only the first entry is generated: the entry of the version that `ratchet.json` names, which is released when it is merged with a date in its heading. While it is headed `(unreleased)`, changes are collected under it, and no merge publishes it. Every entry after it is released text, and the generator never rewrites it. That it stays as it was released is checked against the tags, by `released_text.py`.

**What it does not claim.** It compares what it generates with its data files, and the data files with their form. It does not judge whether the data is right beyond that form: the words of a rule, the cap or a pin in `sources.json`. The maintainer reads those in the pull request (`ratchet.owner-paths`). It reads no tags, so whether released text stayed as it was released is `released_text.py`'s to see. Its guards against links are a safety net, not a boundary: see [No write through a link](#no-write-through-a-link).

## released_text.py

```sh
python3 checks/released_text.py
```

**What it claims.** Released text is as it stood at its tag. It reads the tags of the checkout, every one of the form `vMAJOR.MINOR`, and compares:

- every entry of `CHANGELOG.md` that a tag holds, from its heading to the next one, with the same entry at that tag, byte for byte after CRLF is read as LF. Every tag that holds a changelog is compared with every entry it holds, so an entry is compared with each later tag too.
- `ratchet.json`, when it names a version that has a tag, with `ratchet.json` at that tag. A change to the rules raises the version (`D-2026-11-17-new-approaches`). It is read first as every check reads it, with `registry.strict_loads` and `registry.validate`, and fails when it is not a valid data file.

It also fails when a tag has no entry in the changelog (`repo.version`, this repo's own rule), when an entry after the first has no tag, when a heading is not of the form `## <version> (<date>)` or a version stands twice, when there are no tags, when a tag is of another form, and when the tags cannot be read.

**An unreleased first entry** ([D-2026-11-19-batched-releases](../decisions/D-2026-11-19-batched-releases.md)). The first entry may be headed `## <version> (unreleased)`, exactly. It passes while its version has no tag, and `ratchet.json` may name that version and change: nothing of it is released. An entry after the first headed so fails, and so does the first when its version has a tag: a released version stays released. Once the heading has a date, the next push to `main` releases it, and from its tag on the entry and `ratchet.json` are compared as every released one is. `sources.json` is not read: the list of sources is not part of what is released, so a pin that moves needs no new version. The threat here is the one that item 3 of [D-2026-11-17-new-approaches](../decisions/D-2026-11-17-new-approaches.md) named: an unreleased heading was once how released text got rewritten. So the heading has one exact form, only the first entry may have it, and released text is compared from its tag on as before.

**Against which threat.** Released text rewritten after its tag, as the count under the released heading of 0.3 was, by the generator, in the first round of PR #12. A record of the release kept in the repo does not protect it, because the same PR can change the record. The tag is published, and is never moved (`repo.tags-stay`).

**In CI.** The checkouts of the jobs `own` and `base` fetch the tags, with `fetch-depth: 0`. A step of `own` runs this check, and on a pull request `base` runs the base branch's copy on the pull request's changelog ([from_base.py](#from_basepy)). Without the tags it fails, and says so: it is never skipped. The tests in [test_released_text.py](test_released_text.py) make a git repo of their own, with tags of their own, so they need none of this repo's tags.

| Case | Result |
|---|---|
| Released text as it stood at its tags | Passes |
| The version not yet released changes | Passes |
| A word changed in a released entry, its count regenerated, its date changed, or a line added at the end of the last entry | Fails |
| A released entry removed | Fails |
| A tag with no entry, also a tag that holds no changelog, as `v0.1` | Fails |
| An entry after the first with no tag | Fails |
| A heading of another form, such as `## Unreleased`, `## 0.4` or `## 0.4 (soon)`, or an entry twice | Fails |
| The first entry headed `## 0.4 (unreleased)`, with no tag `v0.4`, and `ratchet.json` and the entry changed under it | Passes, and says that the first entry is unreleased |
| That entry given its date, then tagged | Passes. From the tag on, the entry headed `(unreleased)` again fails |
| An entry headed `(unreleased)` after the first, two such entries, or the first for a version that has a tag | Fails |
| `(Unreleased)`, a space or a no-break space after it, no parentheses, no space before them, or one left open | Fails, not the heading of an entry |
| `ratchet.json` with `sources` or `date`, which left it in 0.9 | Fails, an unknown field |
| A changelog that is not UTF-8, or no changelog | Fails |
| `ratchet.json` names a released version and is as it stood at its tag | Passes |
| `ratchet.json` names a released version and its rules changed, or the tag holds no `ratchet.json`, or it cannot be read | Fails |
| `ratchet.json` is not a valid data file, read as every check reads it: a field twice, `NaN` or `Infinity`, an unknown or a missing field, nested too deeply, not an object, not UTF-8. Finding 4 of round 1 of the new approach. | Fails |
| A tag of another form, such as `v0.4-rc1` or `latest` | Fails |
| An annotated tag | Passes |
| No tags, or no git checkout | Fails |
| The version that `ratchet.json` names, on a copy of this repo, with `release.py`'s own code and no copy of it, against a fake GitHub that holds the tags and releases from before it. First headed `(unreleased)`: `RATCHET.md` says it is not yet released, the README fetches the newest release, the checks pass, and a push and a scheduled run, on the history of `main` in the copy read with `release.main_history` and `release.read_pending`, write nothing and say why. Then given its date, with the README moved to its tag and `generate.py` run: the checks pass, `release.publish` tags the merge and releases it, the next scheduled run writes nothing, the guard passes, and the full suite passes after it. Finding 3 of round 1 of the new approach | Passes |
| While that version is unreleased, a rule changed | Passes |
| After its release, a rule changed without a new version | Fails |
| After its release, a pin moved in `sources.json` | Passes, with no new version. `generate.py` writes only `RATCHET.md` |

**What it does not claim.** It trusts the tags it is given. A tag deleted or moved on the server is outside what it can see: that is a setting of the repository. It does not see whether the text of the first entry, the version not yet released, is right. It does not see whether a dated first entry was released: on a pull request, and on the push of `main` before the release run is done, the tag does not exist yet. That is the release workflow's to see, on its next run and on its schedule. So the command in `README.md` that fetches Ratchet names a tag that may not exist yet: the pull request of a release moves it to the version it dates, and the tag is created by the release run after the merge. For the minutes that run takes, the command fails. If the run is cancelled or fails before it tags, the command fails until a rerun tags, and the daily scheduled run of `release.py` is red each day until then ([PR #50](https://github.com/fabian-von-tiedemann/ratchet/pull/50), round 2, finding 2). Moving the pin in a pull request of its own after the tag exists would close that window, at the cost of a second pull request for each release, and is a question for the maintainer.

## release.py

```sh
python3 checks/release.py notes --repo OWNER/NAME   # print the release text, with no token and no network
python3 checks/release.py publish                   # tag and release, in the release workflow; only report, on a schedule
```

This one checks no rule in a register. It is the script that the release workflow, [release.yml](../.github/workflows/release.yml), runs after the three commands of the job `own` ([D-2026-11-17-release-on-merge](../decisions/D-2026-11-17-release-on-merge.md), [D-2026-11-17-release-links](../decisions/D-2026-11-17-release-links.md), [D-2026-11-17-release-narrow-claim](../decisions/D-2026-11-17-release-narrow-claim.md), [D-2026-11-17-release-fail-closed](../decisions/D-2026-11-17-release-fail-closed.md)). The workflow holds no logic of its own, so that the logic can be tested. Its tests, in [test_release.py](test_release.py), run with the others and never reach the network: the GitHub API is a function given to the script, and the HTTP client is given a fake opener.

The script reads no Markdown and copies nothing from the changelog. The versions that must already be released come from the history of `main`, read with git, and not from the changelog. It does not try to finish an older version. When anything older is unfinished, the run is red, nothing is written, and the message names the commit whose run the maintainer reruns.

**What it claims, in short** ([D-2026-11-17-release-narrow-claim](../decisions/D-2026-11-17-release-narrow-claim.md), [D-2026-11-17-release-fail-closed](../decisions/D-2026-11-17-release-fail-closed.md)). It catches mistakes in normal operation, and it fails closed. With the history on `main` intact, a run is green only when it has confirmed, from git and from the answers of the GitHub API, that every version that was ever dated on `main`, up to the one in the checkout, has a tag and a published release (a version that `main` only named under a first entry headed `(unreleased)` needs nothing, see below), and, when the first entry of the changelog, the one of the version in the checkout, has a date, that the tag of that version is at this commit or at an earlier commit of it. While that entry is headed `(unreleased)`, the version in the checkout has no tag yet, nothing is written for it, and a run passes once every older version is finished. Every run, whether of a push, by hand or on the schedule, that cannot confirm that is red:

- A scheduled run writes nothing at all.
- A run of a push or by hand writes nothing when it cannot confirm that every older version is finished, or when any check before its writes fails. Its only writes are the tag and the release of the version in `ratchet.json`, made after every check has passed. If it cannot confirm either one, it is red.

The workflow also runs on a schedule, every day, on the head of `main`, also when nothing is merged. While a version is unfinished, the scheduled run is red each day that GitHub starts it (see "What it does not claim").

Naming the version, the commit and the rerun is best effort. The run names them when it has read what is unfinished, and in the one message after the tag. It is red either way. When the API does not answer, or answers with an error such as HTTP 503, or with something that is not JSON or not of the form expected, before the run has read the tags and the releases, the run is red. It writes nothing, and its message may name only the request that failed. An error the script does not expect before any write is not caught. Python exits with 1, so the run is red and names nothing.

That holds through:

- a run that was cancelled or failed, before or after its tag;
- a publication that failed: a refused tag, a release that was not created, an answer lost;
- a changelog that was edited, with an entry taken out or a heading moved out of its form;
- a merged version left without a tag or a release, for any of these reasons or because a waiting run was replaced by a newer one.

It does not stand against someone who changes the runner's git data, such as a graft, a replace ref, a shallow file, an object store of its own or a forged object, nor against someone who deliberately writes a version in an unusual form. Two cheap barriers stand there anyway, and they are not a claim: every version must have one strict form, and a checkout with any of the first four is refused.

**Why that boundary holds.** Nothing reaches `main` but through a pull request, and every commit on it has passed the code owner's approval and the required job `checks` (`ratchet.owner-paths`). The ruleset on `main` refuses a force push and a deletion, so a commit on `main` stays as it was approved. Every run of the release workflow starts from a fresh checkout on a runner of GitHub's, so the git data it reads are the ones the checkout wrote, from `main`, and not ones a person left behind. To change the git data or the version on purpose, someone has to get it past that approval, or turn the ruleset off. The review of the change, not the script, is what stands against that.

**What it claims, in detail.**

- **The release text is one fixed line, written in the script.** For version 0.4 of `OWNER/NAME` it is, exactly: `Ratchet 0.4: see [the changelog entry](https://github.com/OWNER/NAME/blob/v0.4/CHANGELOG.md) and [the files at this tag](https://github.com/OWNER/NAME/tree/v0.4)`. Nothing else is in it. No byte of `CHANGELOG.md` reaches the release, so the release cannot say something other than the entry: it says where the entry is. The links name the file and the tree at the tag, with no anchor, so they do not depend on how GitHub makes the anchor of a heading.
- **Every version has one form.** Each version the script reads must match `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`: ASCII digits, no leading zero, nothing before or after. That holds for `ratchet.json` in the checkout, `ratchet.json` at each commit on `main`, each tag under `refs/tags/v` (`v` and the version), and each heading of a version in the changelog. Anything else fails the run, and the message names the value, as JSON in ASCII, and where it came from: the checkout, the commit, the tag, or the line of the changelog. Versions are compared only as pairs of integers, so 0.10 is newer than 0.9, and `00.4` never stands beside `0.4`.
- **From the changelog it reads only which versions have an entry.** It reads the version from `ratchet.json` at the checked-out commit, strictly, and `CHANGELOG.md` as strict UTF-8. CRLF is read as LF, and the text is split at LF. A line is the heading of a version only when the whole line matches `^## ([0-9]+\.[0-9]+) \(([0-9]{4}-[0-9]{2}-[0-9]{2})\)\Z`: `[0-9]`, because `\d` in Python matches the digits of every script, and `\Z`, because `$` also matches before a final LF. Every other line is passed over, whatever a reader makes of it.
- **The version has an entry, and nothing newer has one.** The run fails before any request when no line names the version in `ratchet.json`, or when a line names a newer version.
- **A checkout that swaps objects or parents is refused.** Before it reads any history, the run fails when the checkout has `.git/info/grafts`, a ref under `refs/replace/`, loose or packed, a `.git/shallow` file, even an empty one, or a `.git/objects/info/alternates` file, even an empty one. git reads a graft as the parents of a commit, a replace ref as another object, a shallow file as the end of the history, and an alternate store as the source of an object the checkout lacks, without checking its hash: each changes what is read, and the tests show it. Beside the refusal, git runs with `GIT_NO_REPLACE_OBJECTS=1`, `--no-replace-objects` and `GIT_GRAFT_FILE` set to an empty file in a directory the script makes for each call, so that the reading ignores grafts and replace refs anyway. A fresh checkout on GitHub has none of these.
- **The older versions are the ones `main` has had.** Before any request, it reads with git every commit on the first-parent history of `GITHUB_SHA` (`git rev-list --first-parent`) and the bytes of `ratchet.json` in each (`git cat-file`), and reads each as strictly as `registry.py` reads a data file: UTF-8, no field twice, no NaN, and a `version` of the form `MAJOR.MINOR`. Every commit is read, not only those git reports as changing the file. The run fails when the checkout is shallow, when it is not at `GITHUB_SHA`, when `ratchet.json` at `GITHUB_SHA` names another version than the checkout, when a commit names a version newer than the one being released, or when the file is missing at a commit after an earlier commit held it. Commits from before `ratchet.json` existed name no version. git runs with no `GIT_` variable of the environment, no system or global config, no replace refs and no graft file of the checkout, and it does not look for a repository above the checkout.
- **Every tag has an entry, and every older version is finished.** Before any write, it lists the tags and the releases. A tag `vMAJOR.MINOR` up to this version with no line of its own fails the run, and so does a tag under `refs/tags/v` of another form, which is named. Each version that was dated on `main` and that is older than the one being released must have a tag and a published release, not a draft. Which versions those are is under "The versions that must be released" below. 0.1 needs only its tag, because it was tagged before Ratchet published releases (`BEFORE_RELEASES` in the script). If any is missing, the run fails, names each version, what it lacks and the commit whose run to rerun, and writes nothing. Tags and releases of versions newer than the one in `ratchet.json` are ignored, so that a rerun for 0.4 does not trip over a `v0.5`.
- **An unreleased first entry publishes nothing** ([D-2026-11-19-batched-releases](../decisions/D-2026-11-19-batched-releases.md)). A line `## MAJOR.MINOR (unreleased)`, matched as a whole line as the dated heading is, is an entry of a version that is not released. When the first entry is headed so, for the version in `ratchet.json`, the run reads the tags and the releases, fails as before when an older version is not finished, and otherwise passes, writes nothing and says: `Ratchet <version> is not released: its entry in CHANGELOG.md is headed "(unreleased)". Every older version is finished. Nothing was written.` That holds for a push, a run by hand and a scheduled run. It fails and writes nothing when that version already has a tag or a release, when an entry after the first is headed `(unreleased)`, when a version has two headings, and when the checkout and its commit on `main` disagree on whether the entry is unreleased. A heading of any other form, such as `(Unreleased)`, is no entry at all, so the run fails as for a missing entry. The release is the push of the commit that gives the entry its date.
- **The versions that must be released are the ones `main` has named with a date.** Beside `ratchet.json`, the run reads with git the `CHANGELOG.md` of every commit on the first-parent history (`release.read_pending`), as strict UTF-8, and only its headings. A commit is pending when its first entry is the one exact unreleased heading for the version its `ratchet.json` names. A version must be released once a commit on `main` names it and is not pending, so a version merged with a date cannot be hidden by a later pull request, as before. A version that `main` only named as pending needs nothing. A version that a commit on `main` named and that was not pending must be released also when a later commit is pending for it again, with `(unreleased)` put back: the run of that later commit, on a push and on a schedule, fails, writes nothing and says `Ratchet <version> is not finished: commit <sha> on main gave its entry in CHANGELOG.md a date, and at commit <head> it is headed "(unreleased)" again.`, with the rerun. The commit that a message names for a rerun is the first commit on `main` that names the version and is not pending, since a rerun of a pending commit publishes nothing. A commit whose changelog is missing, or holds the heading in another form, counts as not pending: its version must be released. A changelog that is not UTF-8 at a commit on `main` fails the run and names the commit.
- **A release is made only from `main`.** `GITHUB_REF` must be `refs/heads/main`, or the run fails before any request. A scheduled run is on the default branch, `main`, and passes this check like the others.
- **The event is one of three.** `GITHUB_EVENT_NAME` must be exactly `push`, `workflow_dispatch` or `schedule`, or the run fails before any request. A push and a run by hand write as described below.
- **A scheduled run writes nothing, and is red on what is unfinished.** It runs the same checks on the head of `main` and reads the same tags and releases. Its API function sends a `GET` and refuses every other request, which is not sent, whatever the logic asks for. When a read fails, it is red as any run is, and its message may name only the request that failed. When the reads are answered and a run of a push would write, it fails instead: for a version with no tag, the message names the version, the head commit, the first commit on `main` whose `ratchet.json` names it, and the rerun; for a tag at the head with no published release, it names the version, the commit the tag points at, and that the release is missing. Every other fault fails as in a run of a push, and writes nothing. On a state where every version is finished, it passes.
- **Why a scheduled run only reports.** It could also create the release when the tag is at the head of `main`, since that write would be the same as a rerun's. It does not, because that is the safer choice: every write stays tied to an event that a person caused, the push of an approved commit, a rerun or a run by hand. A run that nobody started then never writes a tag or a release, and an error in its logic can at most turn a run red. The cost is one click: the maintainer reruns the run that the message names.
- **Nothing is written before every check has passed.** The writes are two, in this order: the tag, then the release.
- **The tag is created at this commit, or not at all.** It is created with `POST /repos/OWNER/NAME/git/refs`, which refuses a ref that exists. Then the release is created for that tag, and the tag is read back. The run fails when the answer to the creation or the tag read back points anywhere but `GITHUB_SHA`.
- **Every failure after the tag ends in one message.** Once the tag may exist, a failure of any kind, whether no answer, an error the script does not expect, an HTTP error, an answer that is not JSON or an answer of the wrong form, gives one message. It says what failed, then names the version and the commit, says what is missing, and gives the rerun. There are four states, one form each, in `release.py`: the creation of the tag failed in a way that may have written it (`TAG_MAYBE`), the answer to the creation does not confirm the commit (`TAG_ELSEWHERE`), the tag is at the commit and the release is missing or not confirmed (`RELEASE_MISSING`), and the release was created and the tag was not confirmed (`TAG_UNCONFIRMED`). The creation of the release and the read-back are in one `try` that catches every `Exception`. An error the script does not expect is named by its type and the request, and its text is not shown. Only HTTP 422 on the creation of the tag, a ref that exists, still says that nothing was written. A cancelled run is stopped by GitHub and prints nothing. The next scheduled run is red on it, and names it when the API answers.
- **A tag that exists is never moved, deleted or edited** (`repo.tags-stay`). What the run does with the tag of the version being released:

| The tag for the version | The release for it | What the run does |
|---|---|---|
| does not exist | none | creates the tag at `GITHUB_SHA`, then the release, then reads the tag back |
| does not exist | exists, draft or not | fails and writes nothing |
| at `GITHUB_SHA` | none | a rerun of this version's run: creates only the release, then reads the tag back |
| at `GITHUB_SHA` | draft | fails and writes nothing: publish the draft by hand |
| at `GITHUB_SHA` | published | nothing to do |
| at an earlier commit of `GITHUB_SHA` | published | nothing to do: this commit does not raise the version |
| at another commit, or not a plain tag | none, a draft, or a commit that is not earlier | fails and writes nothing |
| any | two or more | fails and writes nothing |

- **The token.** Only `GITHUB_TOKEN` from the environment is used. It is sent in one header, to `https://api.github.com` only, to paths under `/repos/OWNER/NAME/`, and a redirect is not followed. It is never printed: it is taken out of every message. An error names the method, the path and the status. Nothing from the body of an answer is read for an error or printed, except a version that has matched `MAJOR.MINOR` and a tag name of another form, which is written as JSON in ASCII and cut at 60 characters.
- **The workflow keeps its reviewed form.** The tests read the workflow as strict UTF-8, read CRLF as LF, and refuse every other control character but the tab and LF, among them a lone CR and NEL, and U+2028 and U+2029: a YAML parser may break a line there where the comparison does not. Then they compare the workflow, without its comments, line for line with the reviewed form, and test each part the design leans on. A line is blank, or a comment, by ASCII rules only: a line that holds a tab or a space that is not ASCII before `#` is kept, and then fails the comparison. The checkout has `fetch-depth: 0`, so that the history of `main` is there to read.

**Against which threat.** Mistakes in normal operation, as above:

- A release that says something other than the entry that was approved. Two review rounds found that a script reading free Markdown could not know what a renderer will show ([D-2026-11-16-strict-forms](../decisions/D-2026-11-16-strict-forms.md)). Now no text is copied, so there is nothing to differ.
- A version that is merged and left unreleased, or made impossible to release, with no red run: a run that fails or is cancelled after it tags, a waiting run replaced in the concurrency group by a newer one, or a later pull request that takes the version's heading out of the changelog.
- A release attached to a tag at another commit than the one approved, because the tag appeared between a check and a write.
- A version hard-coded in the script instead of read from `ratchet.json`.
- A version collected under an unreleased entry that is published before its pull request of release, or a version merged with a date that is then never released because the changelog says it was unreleased. Only the exact heading, as the first entry, holds a version back, and only at commits whose own changelog says so ([D-2026-11-19-batched-releases](../decisions/D-2026-11-19-batched-releases.md)). Once a commit on `main` has dated a version, a later commit that heads it `(unreleased)` again does not take the duty away: the run fails and names the commit that dated it (PR #50, round 2, finding 1).
- The token sent somewhere else, or shown in a log.

A version written in an odd form by mistake, such as `0.04`, fails the run and is named. The threats that are out of scope are under "What it does not claim".

**Why an edit of the changelog can no longer hide a version.** The versions that must be released are read from commits already on `main`. A pull request adds a commit on top of them and cannot change one of them: the ruleset on `main` refuses a force-push and a deletion, and git names a commit by the hash of its content and of its parents. The first-parent line is the line of `main` itself: a commit on a branch that was merged in is not on it, and the merge commit is. What the script still reads from the changelog can only make a run fail: the version must have an entry, no entry may be newer, and every tag up to the version must have one. A heading taken out of the exact form, or an entry taken out, therefore turns the run red or changes nothing. It never lets a version on `main` through without its tag and its release.

**Why the rerun of this version finishes its release.** A rerun that finds the tag of the version being released at its own `GITHUB_SHA`, with no release, creates the release. This is the version's own run, not an older one. It is safe: the tag is on the commit that was approved, where it would be anyway, so nothing has to move; the text is the fixed line for that version; every older version has passed the check above; and a release created before an answer was lost is found, so no second one is made. Failing there instead would leave no way through the workflow to finish the version.

**When a run is red because something is unfinished.** The message names each version and what it lacks. Then, in this order:

1. Under Actions, open the workflow `release` and find the run of the commit that the message names. If the tag exists, that is the commit the tag points at. It may be a later commit than the first one with the version, when the run of the first was replaced and a later run made the tag. A run of any other commit fails on that tag and writes nothing. If the tag is missing, it is the first commit on `main` at which `ratchet.json` names the version. Choose "Re-run all jobs". It tags that commit if the tag is missing, and creates the release. It ignores the newer versions.
2. When that run is green, rerun the red run, with "Re-run all jobs".
3. If the run of step 1 cannot be rerun (GitHub allows a rerun for 30 days, and a run may never have started), and the head of `main` still has that version in `ratchet.json` and its tag is missing or is at the head, start the workflow by hand: Actions → `release` → "Run workflow", on `main`. It takes no input, runs the same three checks, and releases what `ratchet.json` names at the head of `main`. On any other branch it fails before any request.
4. If neither is possible, the maintainer makes the release by hand for the tag that exists, or the tag by hand on the first commit with the version, with the line that `python3 checks/release.py notes --repo OWNER/NAME` prints at that commit. The workflow never does this.

**Why the concurrency group stays.** It keeps one release run at a time, so that two runs never write at once. A waiting run can still be replaced by a newer one, and the replaced run shows as cancelled. That cannot lose a version without a red run: the newer run checks every older version that `main` has had, and fails and names one without a tag or a published release. The last run in the queue is never replaced. A run that was cancelled can be rerun for its commit, and then the newer one.

A scheduled run is in the same group, `release`, with no expression, so it never runs beside a run that writes. It cannot read a state halfway through a run of a push. When it replaces a waiting run of a push, it is red, and when the API answers it names the version that the replaced run would have released, with no tag or with a tag and no release. When a run of a push replaces a waiting scheduled run, the run of the push does the work, and the next day's scheduled run reads its result.

**What it does not claim.**

- A line of the exact form counts wherever it stands, also where a renderer does not show it as a heading: in a code block, in an HTML comment. Then the script may take a version for one that has an entry when a reader sees none. No text is copied, so such a line can no longer put text into a release. The most it can do is let a tag or a release through for a version whose entry a reader cannot see, in a pull request the maintainer has approved.
- A heading a renderer shows in another form, for example after a space or in a list item, is not counted. That fails the run, and never releases anything.
- It does not check that the entry says anything, that its date is a real date, or that the entries stand in any order.
- The release page shows no text of the entry. A reader follows the link. The link opens `CHANGELOG.md` at the tag at its top, not at the entry for the version.
- It does not see branch protection or tag protection. Who may push a tag by hand is a setting of the repository.
- It does not read the release text back after it is published.
- It does not make GitHub start a scheduled run. GitHub may start one late, and at times of high load it may drop one. In a public repository, GitHub turns off a scheduled workflow after 60 days with no activity in the repository, and it stays off until someone turns it on again. Within those limits, while a version is unfinished, the scheduled run is red each day. A cancelled run prints nothing itself. The next run is red on it.
- It does not promise to name the unfinished version ([D-2026-11-17-release-fail-closed](../decisions/D-2026-11-17-release-fail-closed.md)). When the GitHub API is down, or answers a read with an error such as HTTP 503, or with something that is not JSON or not of the form expected, the run is red and writes nothing. Its message may name only the request that failed, and not the version, the commit or the rerun. As long as the API fails that way on the scheduled runs, a version can stay unfinished with no run that names it. Each of those runs is still red.
- A scheduled run has the same job, and so the same token with `contents: write`, as a run of a push. What keeps it to reading is the script, which sends nothing but a `GET` on a schedule, not the token. A second job with a read-only token would need an `if:` on the event, and the workflow has none.
- A version that is collected under an unreleased entry can be dropped on purpose, by a later pull request that raises `ratchet.json` past it before the entry has a date. That is a choice made in a pull request, as a skipped version is. Once a commit on `main` has dated the entry, the version must be released, whatever the changelog says later.
- A version may be skipped on purpose, from 0.4 to 0.6, by a pull request that never puts 0.5 in `ratchet.json` on `main`. That is a choice made in a pull request, not a version lost. A version that a pull request names only in its own commits, and that `main` never names, is not counted.
- Versions from before `ratchet.json` was on `main`, 0.1 and 0.2, are not in that history. Both were tagged by hand. The script checks them only as tags with an entry.
- It does not stand against someone who changes the runner's git data ([D-2026-11-17-release-narrow-claim](../decisions/D-2026-11-17-release-narrow-claim.md)). It refuses grafts, replace refs, a shallow file and alternates, and nothing more: a forged object written into the checkout's own store, a changed `HEAD` or ref, or a changed `git` binary are not looked for. On a fresh checkout on GitHub there is none, for the reasons under "Why that boundary holds".
- It does not stand against someone who deliberately writes a version in an unusual form. It refuses every form but one, so such a version makes the run red; a version skipped on purpose, as below, is still possible.
- It trusts the history of `main` as the ruleset keeps it. An administrator who turns the ruleset off and force-pushes `main` could take a version out of that history.
- `generate.py` and `check_register.py` read `version` in `ratchet.json` with the older form `^[0-9]+\.[0-9]+$`, so they accept `00.4`. Only the release script refuses it. Making `registry.py` as strict is a proposal (P) in the decision, not done here.
- A workflow file on another branch can be changed by anyone who can push to it. The check of `GITHUB_REF` stops a mistake, not a change to the workflow or the script.

## The budget

`ratchet.json` holds `experimental_cap`: the most rules outside the core there may be ([D-2026-11-17-pull-and-budget](../decisions/D-2026-11-17-pull-and-budget.md)). It is 23. It was 25: there were 20 experimental rules in `ratchet.json` at the commit on `main` that added that decision, and the decision put the cap at that number plus five. In 0.10 two rules that applied only to Ratchet moved into this repo's own register, and the cap went down by two, so that the move freed no place (`D-2026-11-20-proposal-triage`, choice 5).

**What it claims.** Every check that reads `ratchet.json` through `registry.load` fails when there are more experimental rules than the cap, so `generate.py --check` is red and nothing is generated. It fails the same way when the cap is missing, stands twice, or is anything but a whole number from 0: text, `true`, `2.0` or a negative number. The count of rules, in the README, `RATCHET.md`, `SELF-IMPROVEMENT.md` and the first entry of the changelog, states the cap.

**Against which threat.** Ratchet grows a rule at a time until no one reads it. With the cap, a new experimental rule replaces, merges or removes one, or a decision raises the cap.

**What it does not claim.** It does not count the core, which is frozen, and it does not judge whether a rule is worth its place. A PR can raise the cap in the same change that adds a rule. That is a change to `ratchet.json`, which the maintainer reads before it is merged (`ratchet.owner-paths`), and raising the cap is a decision.

|---|---|---|
| `budget/at-cap.json` | Nothing. Two experimental rules under a cap of 2. | Passes |
| `budget/over-cap.json` | Two experimental rules under a cap of 1. | Fails |
| `budget/no-cap.json` | No cap. | Fails |
| `budget/cap-text.json`, `budget/cap-true.json`, `budget/cap-fraction.json`, `budget/cap-negative.json` | A cap that is text, `true`, `2.0` or `-1`. | Fails |
| `budget/cap-twice.json` | The cap twice, and the higher one would win. | Fails |

The tests are in [test_budget.py](test_budget.py). Each runs `generate.py --check` on a directory that holds only the fixture as `ratchet.json`, and the data file fails before anything else is read. ## The age of an experimental rule

Every experimental rule in `ratchet.json` names `since`, the version it entered Ratchet, and may name `kept_by`, the id of a decision that kept it once more ([D-2026-11-19-one-point-oh](../decisions/D-2026-11-19-one-point-oh.md), choice 4). How the age is counted is in [SELF-IMPROVEMENT.md](../SELF-IMPROVEMENT.md#the-age-of-an-experimental-rule).

**What it claims.** `generate.py --check` fails, with one line per rule that names it, when an experimental rule has stood through three releases and 60 days with no decision. The releases are the versions with a date in the changelog after `since`, and the days run from the date of `since` to the date of the newest of them. A rule with `kept_by` stands one age more, counted the same way from the release at which it first stood too long, and then fails with only three outcomes: move it into the core, merge it, or remove it. The date of the decision does not move the count, so naming a later decision in `kept_by` keeps the rule no longer: a rule is kept once. The age moves only when a release is dated, so the check first fails in the pull request of a release, and never on a day with no change. Every check that reads `ratchet.json` through `registry.load` fails when an experimental rule has no `since`, when a core rule has `since` or `kept_by`, when `since` is not a version, when `kept_by` is not the id of a decision with a date that exists, or names a decision with no file in `decisions/`, and, as before, on a field it does not know or a field twice. `generate.py --check` also fails when `since` does not name a version with an entry with a date in the changelog, or the version of the file, so a version later than the file's fails there. It fails, naming both entries, when a release is dated before the version before it, since the age is measured at the newest version, and a year mistyped there would hide every rule. Two versions may have the same date.

**Against which threat.** A mistake in the bookkeeping of rules: an experimental rule that lingers release after release with no one deciding on it, and a field misspelled so that the reader passes over it.

**What it does not claim.** It does not see whether `since` is true. It was read from the tags once, for 0.10, and a released `ratchet.json` cannot change after its tag (`released_text.py`), but between two releases a pull request can change it, as it can raise the cap, and the maintainer reads it (`ratchet.owner-paths`). A check that it stays as it was at the last tag is issue #74. It does not judge the decision in `kept_by`, only that it exists. A rule removed and added again under another key starts a new age, which the maintainer reads in the pull request. It reads no clock: a rule that has stood long since the last release is not caught until the next one is dated. It passes on the releases up to 0.10, which are dated from 2026-11-16 to 2026-11-21. The first release that can make it fail is one dated 2027-01-15 or later.

## A rule that enters is used

A new experimental rule is already used by Ratchet itself, or says why Ratchet cannot use it (`D-2026-11-20-proposal-triage`, choice 5). A rule says so in `not_used_because`, a field of an experimental rule in `ratchet.json`: text from the fixed list, with at least one letter or digit.

**What it claims.** `generate.py --check` fails, with one line per rule that names it, when an experimental rule has `since` equal to the version of `ratchet.json`, this repo's `register.json` does not adopt it, and the rule has no `not_used_because`. It fails, naming the rule, when the register adopts a rule that has `not_used_because`, whatever its `since`, so a rule does not both claim to be used and give a reason it is not. Every check that reads `ratchet.json` through `registry.load` fails on a misspelling such as `not_used_becuase` in a rule, as an unknown field, when a core rule has `not_used_because`, and when the reason is not a string, holds a character outside the list, or holds no letter or digit. When `register.json` does not pass `check_register.py`, this part says nothing: the register is named as failing already.

**Against which threat.** A mistake in the bookkeeping of rules: a rule enters Ratchet that Ratchet itself does not use, and nobody notices that it was never tried here, or a rule is said to be used when the register does not adopt it.

**What it does not claim.** It reads the register, not the repo: it does not see whether Ratchet follows a rule that the register adopts, or whether a check marked "built" works. It does not judge the reason, only that it is words. It holds a rule only in the version it enters, as `since` gives it, so it does not see a rule that was in Ratchet before 0.10, and a rule whose `since` is changed to an older version passes, which the maintainer reads in the pull request (`ratchet.owner-paths`) and issue #74 would catch.

## The principles

`ratchet.json` holds a list `principles`, and every rule names one of them in `principle` (`D-2026-11-20-principles-and-obligations`). A principle is a question an agent asks when no rule fits, or an aim, never a claim that something is protected. It is guidance, text only, and what is checked is only the rules under it. A principle has exactly a `key`, `principle.` followed by lowercase words joined by hyphens, a `title`, the principle in one or two short sentences, and a `text`, the question (`D-2026-11-23-values-and-principles`). The generator writes each principle in `RATCHET.md`, under "The principles", with its number and title as a heading, its text, the mark "Guidance, text only", and the keys of the rules under it, each marked "names a check" or "text only", and "experimental" where it is. It writes the titles as a numbered list in `README.md`. In both, the line `production` of `values.json` stands before the first principle whose rules all stand in `PRODUCT.md`, and the line `aims` after the last.

**What it claims.** Every check that reads `ratchet.json` through `registry.load` fails when the list is missing or is not a list, a principle is not an object, lacks a field or has one it does not know, such as a `check`, a field is not text, a key is not of its form or is used twice, a title holds no words, has two spaces in a row or a space at an end, is longer than 120 characters, or is the title of another principle without regard to case, a text holds no words, does not end with a full stop, a question mark or an exclamation mark, or has more than three sentences, a title or a text holds a character outside [the list](#the-characters-a-value-may-hold), a rule has no `principle`, names one that is not in the list, or has the field misspelled, or a principle has no rule under it. A sentence ends at a `.`, `?` or `!` followed by a space or the end of the text. `generate.py --check` fails when the section or the list is not what the data generates, and when a markdown file mentions a principle that does not exist. An older `ratchet.json`, which `upgrade.py` reads, may lack the list, and then no rule of it may name a principle. One that has the list is read as strictly as this one.

**Against which threat.** A principle that reads as more than guidance: a heading with no rule under it, a principle that names a check of its own, a generated section that drops the mark "Guidance, text only", or a text rewritten in the generated file. And two titles that differ only in their spaces, which HTML shows as one. And the bookkeeping: a rule with no principle, or one that names a principle that is gone.

**What it does not claim.** It does not judge whether a rule stands under the right principle, or whether a text is a question or an aim rather than a claim of protection. The pull request that adds or moves a principle shows the map, and the review and the maintainer read it. The principle of a rule is not part of a register: `check_register.py` and `upgrade.py` compare the key, the rule, the ratchet and the source, so moving a rule to another principle asks nothing of a project. It counts sentences by their marks, so a text that writes an abbreviation with a full stop is counted as more sentences, and one that leaves out a full stop between two sentences as fewer.

## The issue form

A proposal starts as an issue with the form [proposal.yml](../.github/ISSUE_TEMPLATE/proposal.yml), which asks for the five fields of [D-2026-11-17-pull-and-budget](../decisions/D-2026-11-17-pull-and-budget.md): what happened, the failure class, the ratchet, whether it would apply in other projects, and the primary source. See [CONTRIBUTING.md](../CONTRIBUTING.md). The form is a test of this repo, not a reference check.

**What it claims.** The form has exactly these five fields, in this order, each a text area marked required, and it gives an issue opened with it the one label `proposal`. GitHub reads the form as YAML, and the standard library has no YAML parser, so the test reads one fixed form line by line and fails on every line outside it: a top of `name`, `description`, `labels` and `body`, then seven lines per field in a fixed order and indentation. A value is one plain line that starts with a capital letter and holds only letters, digits, spaces and `,.;()'?-`, and is not a word that YAML 1.1 reads as true, false or null. The labels line is exactly `labels: [proposal]`. Any YAML parser reads such a file the same way, so what the test reads is what GitHub reads.

**What it does not claim.** It does not claim that GitHub accepts the form or shows it, or that the label `proposal` exists in the repo, without which GitHub adds no label: that is seen on GitHub once the form is on `main`. It does not stop an issue opened without the form, from the blank issue or through the API.

A page that moves must not move for a visitor who has asked for less motion. The threat is a mistake, not intent. A release that moves the README and forgets the page would send people to an older version, a count or a value written by hand would go stale at the next change, and a link that leads nowhere would go unseen, because nothing else reads the page. A page that grows back to many sections is read by fewer people, so its length is held too.

**What it does not claim.** It does not claim that a browser shows the page or the figure as intended, or that Pages is turned on and serves it. It does not draw the figure: that its labels fit where they stand, that each lies on the background it is checked against, and that the picture says what the alt text says, is read by the maintainer. The logos are not read at all, only compared with their copies in `assets/`. It reads hex colors only, so a named color is not checked for contrast. It reads the CSS by its braces after removing its comments, so a brace in a comment is not read, but a brace in a string is read as a brace. It does not check that the text is true: it is taken from `README.md` and the files the page links to, and read by the maintainer. A link into the repo is checked against the checkout, not against GitHub, so the fragment of such a link, as in `RATCHET.md#the-principles`, is checked for its form only.

## upgrade.py

```sh
python3 .ratchet/checks/upgrade.py register.json
```

This one checks no rule in a register. It is the upgrade path for a project ([UPGRADING.md](../UPGRADING.md)), in one command ([D-2026-11-22-second-redraw](../decisions/D-2026-11-22-second-redraw.md), step 6). `.ratchet` is a git clone of Ratchet. The command fetches its tags from `origin`, reads the version the register states, and compares that tag with the latest release, or with the one given with `--to`. `--no-fetch` uses the tags the clone has. Offline, `--from` is the `ratchet.json` of the version the register states, taken from its tag, and `--source`, by default the `ratchet.json` next to the script, is the newer Ratchet: `python3 .ratchet/checks/upgrade.py register.json --from .ratchet/from.json`. `--from` is not given with `--to` or `--no-fetch`, and `--source` only with `--from`.

**What the one command claims.** It runs git on the clone the script stands in, and on nothing else: no `GIT_` variable of the caller is used, and git does not look for a repo above the clone. It reaches no network but the clone's `origin`, through `git fetch --tags`. It refuses, with exit 2 and what to do, when:

- the clone is not a git work tree of its own, as when `.ratchet` is a copy. It names `--from`.
- the fetch fails. It names `--no-fetch`.
- the version the register states has no tag `v` and that version. After a fetch, that version was never released, and it lists the release tags. With `--no-fetch`, in a shallow clone, it says the clone holds only the tags it was cloned with, and prints the command that fetches them.
- `--to` is not a version, or its tag, such as `v9.11-rc1` or `v09.10`, or names no release tag, or a release before 0.11, whose `upgrade.py` does not fetch, and not older than the register's version.
- the clone has changes to files git tracks in it, or is on a branch and must move. Neither is moved. For a clone on a branch it prints the command that moves the clone, detached, to the release, whose `upgrade.py` runs the same command, and the command that goes back to the branch, which stays where it was. Not to the tag of the register's version: for a register on 0.10 or earlier, the `upgrade.py` there does not run the one command.

A release is a tag `v`, a major and a minor version, with no leading zero, and nothing else. Any other tag is not listed, is never the latest, and is refused by `--to`. The latest is the highest by number, so `v0.10` comes after `v0.9`. When the release is older than the register's version, it fails with exit 1, also when the release is before 0.11, and when it is the same, it says the register is not behind. Otherwise it reads `ratchet.json` at the register's tag with the reader for an older version below, and checks the register against it, as the offline mode does, before anything moves. Then it moves the clone, detached, to the commit of the release, prints the commit it was at and the command that moves it back, and runs the `upgrade.py` of the release, which knows that release's forms, with the register's path after `--`. That one says how many releases after the register's version the release is, and which, prints the steps as below, the commands to run after with the path of the script as typed, and the commit to pin `.github/workflows/ratchet.yml` to. A register with rows by reference, in a project with no `.github/workflows/ratchet.yml`, which adopt mode never writes, is told instead, with the same commit, the command that copies `checks/run_pinned.py` again and the lines for the local check script and for the CI step, as `init.py` prints them ([run_pinned.py](#run_pinnedpy)), so it need not run `init.py --check` for them. It writes no file of the project, and changes `.ratchet` only through git: its tags and its checkout.

**What it claims, in both modes.** It reads three data files strictly, and when they are valid it prints, rule by rule, what is different between the two versions of Ratchet and what the register must do about it:

- a rule the register adopts that changed: which of its status, enforcement, rule, ratchet and source changed, and the entry to put in its place. The entry is the newer rule, character for character. It keeps the status and the place of the check when the rule still names a check, gets `text only for now` when its ratchet now names one, and loses both when it is text only now. When the ratchet of a rule marked `built` changed, it says to look at the check again.
- a rule the register adopts that was removed: take it out of `adopted`, and, to keep it, add the printed entry to `own`. The entry is the older rule with the fields of an own rule, `key`, `rule`, `ratchet` and `source`, and the status and the `where` it had, which an own rule may have from 0.10. A translation is dropped, since an own rule has none. Its key is the prefix of the register's first own rule, or one made from the project's name, then a dot and the name in Ratchet's key, with `-2` and so on when that key is taken. A name that gives no prefix, or gives `ratchet`, gives `project`.
- when every rule the register adopts was removed: adopt at least one rule, from the new rules, or from the rules to start with when there are no new ones, each printed with its entry. A register that adopts no rule does not pass `check_register.py`.
- a new rule: the entry to add, if the project adopts it.
- a rule that changed or was removed and is not adopted: its key, with nothing to do.
- when the fields of `ratchet.json` differ between the two versions, at the top or in its rules: which are new and which are gone, and that a copy of a Ratchet check kept in the project, or a check of the project's own, that reads `ratchet.json` must be updated. The checks in `.ratchet` need nothing, and nothing in the register changes. The older file may lack the cap and may hold `date` and `sources`, which left `ratchet.json` in 0.9 ([D-2026-11-19-batched-releases](../decisions/D-2026-11-19-batched-releases.md)), and no other field the newer one does not know. A field of a rule is new when some rule of the newer file holds it and no rule of the older one does, as `since` is from 0.10 ([D-2026-11-19-one-point-oh](../decisions/D-2026-11-19-one-point-oh.md)), and gone the other way round.
- a rule the register adopts with a translation, whose rule changed: the translation must be made again. The entry is printed without it, with the sha256 of the new text. A translation of a rule whose text did not change, only its ratchet or its source, stays in the entry.
- a rule the register adopts by reference, whose rule or ratchet changed: that its sha256 no longer matches, the new one in the entry, which keeps `stands_in`, the status and the `where`, and that the project reads its own wording in the file again, with the new rule and its ratchet printed under the entry to read it against. The register passes against the version it states until the owner moves `ratchet_version`, and fails from then until the sha256 is set. When only the source changed, the sha256 still matches and it says so. A removed rule adopted by reference gets Ratchet's older text in the entry for `own`, and the step names its marker line to take out of the file.
- when the register moves past a version that changed the form of `register.json`, what changed. In 0.10 the fields `instructions`, `translation` and the status of an own rule came, all of which may be left out, so none of it is a step. In 0.11 the rows by reference came, with the new fields `stands_in` and `sha256`, which it names, and which may be left out too. It prints the commands that put `REGISTER.md` in place again, and, for a register that names an instruction file, that file too, as [check_register.py](#check_registerpy) gives them, with the path of the file, and the command that checks them. Each command gives `check_register.py` its options first and the register's path after `--`, so a path that starts with `-` is read as a path. A register with rows by reference after the steps, and no `REGISTER.md` beside it, is not told to print one: it may leave it out, and the command that checks it has no `--markdown REGISTER.md`.

Before it prints a step, it checks that the register passes `check_register.py` against the older Ratchet, and that the register with every step done, and no new rule adopted, passes it against the newer one. When the register adopts a removed rule, it checks that register twice: with each removed rule taken out, and with each also moved to `own` by the printed entry. When every adopted rule was removed, it checks both with every rule it printed to choose from adopted. A register that does not pass against the older Ratchet is not upgraded, so one that adopts no rule from Ratchet, or a rule that is not in the version it states, still fails. Offline, it writes nothing, runs no git, and reads no file but the three it is given.

**Against which threat.** Mistakes and drift, within [the threat model](#the-threat-model): a project that upgrades by hand misses a rule that changed, keeps a softened copy, or keeps a status that no longer holds, and the register still looks like Ratchet's. A project that compares the wrong two versions, by hand, from a clone that lacks the tag it needs, or from a newer clone with an older script, gets steps for versions it is not on. An upgrade that moves `.ratchet` by hand loses the commit it was at, or moves a clone someone works in.

**The older `ratchet.json`.** It is read with the same strict reader, `registry.validate`, with these things left out, because they are not what an upgrade compares and an older version may not have them in today's form: it may lack the cap, which came in 0.5, it may hold `date` and `sources`, which left in 0.9, its experimental rules may lack `since`, which came in 0.10, its sources are not read (Ratchet 0.3 wrote one in a form that 0.4 refuses), the files of its reference checks and of the decisions in `kept_by` are not looked for, and its budget is not counted. A field it does not know, a field twice, a rule of another form or bytes that are not UTF-8 still fail.

**What it does not claim.**

- It does not see that `origin` is Ratchet, or that a tag is the one Ratchet released. It trusts the clone's `origin` and its tags, as the README's clone does. Someone who controls them, or the clone, is outside [the threat model](#the-threat-model).
- It does not run the `upgrade.py` of a release before 0.11. A clone on one is moved once by hand, as `UPGRADING.md` says.
- Offline, it does not see that the file given with `--from` is the one at the tag. It checks that the register passes against it and that the version is older or the same, and that two files that name the same version have the same rules.
- It does not see whether a check marked `built` exists or works.
- It does not list a rule that only moved to another part, or whose reference check changed. Neither changes the register.
- It does not say why a rule changed. The changelog of the newer Ratchet does.

## init.py

```sh
python3 .ratchet/checks/init.py --check            # say what it would write and what it skips, write nothing
python3 .ratchet/checks/init.py                    # write it
python3 .ratchet/checks/init.py --name "My project"
python3 .ratchet/checks/init.py --solo             # one agent and no control room
python3 .ratchet/checks/init.py --adopt ratchet.no-secrets   # adopt mode: write register.json with that row by reference
```

This one checks no rule in a register. It is the start of a project, run from the root of the project's repo with Ratchet cloned into `.ratchet`, as the [README](../README.md#start-here) says. It is new in 0.9.

**What it claims.** It writes what the steps of "Start here" set up by hand, and never overwrites a file:

- `AGENTS.md` from `templates/AGENTS.md`, with the project's name in its title. The rest of the template, with its parts in angle brackets, is the project's to fill in. The two lines that mark the parts for a team, HTML comments holding `team` and `/team`, as `TEAM` in `init.py` spells them, are not written. With `--solo`, for one agent and no control room, neither is what stands between them: the line that the control room reads its handbook, and the section on skills. The marks must stand in pairs, each on a line of its own, one pair at least and none inside another, or it does not run.
- `register.json` from `templates/register.json`, with the project's name, checked with `check_register.py` before it is written.
- `REGISTER.md`, generated from the `register.json` that stands after the run, as `check_register.py --print-markdown` prints it. When `register.json` already exists, that is the one it is generated from.
- `.github/workflows/ratchet.yml` from `templates/ratchet-checks.yml`, with the commit of the Ratchet checkout it runs from as the pin. The commit is read with `git rev-parse` in that checkout and must be 40 characters `0-9` and `a-f`. It does not run when the checkout is not a git repo of its own, or has changes that are not committed, since the commit would then not hold the files it copies. It says whether the commit is the one of the tag of its version. The workflow has two jobs, and the template must hold each once: `ratchet`, whose step runs `check_register.py register.json --markdown REGISTER.md --agents AGENTS.md`, and `project-checks`, the place for the project's own checks, with one step that says what goes there.
- the line `/.ratchet/` at the end of `.gitignore`, unless the last line there that mentions `.ratchet` is exactly `.ratchet/` or `/.ratchet/`, with no line starting `!` after it. A space at the start or the end of a line is part of it, as gitignore reads a leading space, so ` .ratchet/` gets the line, and so does any other form, which at worst adds a line that is not needed. A file with CRLF gets CRLF. This is the one file it changes, and only by that line, in one step: it is read again just before it is replaced, and when it no longer holds what was read, the run stops with exit 2 and leaves it as it is.

**Adopt mode.** A repo that already has an instruction file of its own is adopted instead (step 9b of [D-2026-11-22-second-redraw](../decisions/D-2026-11-22-second-redraw.md)). The instruction files are a fixed list, `INSTRUCTION_FILES` in `init.py`: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md` and `.claude/CLAUDE.md`, each counted only as a plain file with no link on its path. Adopt mode applies when one of them stands, unless `.github/workflows/ratchet.yml` exists or a `register.json` names an instruction file in `instructions`: the first is a project that `init.py` started, since a start writes the workflow first, so a start that stopped halfway is never taken for a project of its own, and the second has chosen the generated block. In adopt mode it says so, names the file, and suggests running `inventory.py` first, which writes nothing. It never writes or changes the instruction file, and does not read it to choose adopt mode or the rules and rows it prints: for those it looks only at whether the file is there. It reads `AGENTS.md` once, as bytes, for one note: when the file is, below its title, byte for byte the `AGENTS.md` that `init.py` writes, with or without `--solo`, it says so, and that a start that stopped halfway is restarted by deleting `AGENTS.md` and `register.json` and running `init.py` again. That is the boundary with earlier versions: a start before 0.11 wrote `AGENTS.md` first, so one that stopped before the workflow is now taken for adopt mode and never gets its workflow on its own. An `AGENTS.md` from another version's template is not recognized. The register check at the end reads each file that a row by reference names, for its marker lines, as `check_register.py` always does. Its first run writes nothing. It writes `register.json` alone, and only when the project names, with `--adopt <key>`, once for each, the rules whose marker line it has put in its file: the template's, with the project's name, a row by reference for each rule named, pointing at the first instruction file, and no other row and no `instructions`. It writes it only when the register passes, checked with `check_register.generated_problems` on the bytes it would write, so a register that fails is never written, and a key that is not a rule of Ratchet, or is named twice, stops the run. `--adopt` in a start stops the run too. No row is copied: an earlier adopt mode wrote a copied `ratchet.register-on-top` as the floor that makes the check pass, and the adoption report of a real project showed that it is false where the project's own instruction file is canonical, since a register that holds rules by reference neither lists every rule in force nor takes precedence. The floor is now no row, by [D-2026-11-23-adopt-mode-no-copied-row](../decisions/D-2026-11-23-adopt-mode-no-copied-row.md), which replaces "one copied row" of step 9b, and `check_register.py` is not loosened: a register that adopts nothing still fails. A `register.json` of the project's own is checked as it stands, with or without `--adopt`. It writes no `REGISTER.md`, which a register with rows by reference may leave out, and does not read one: a `REGISTER.md` that exists, whether a plain file, a link, a directory or one it cannot read, is left as it is and named as not checked, as `check_register.py register.json`, the check the printed step runs, does not read it, and the exit code is the same as without it. It writes no workflow and no line in `.gitignore`, and says to add `/.ratchet/` when `.gitignore` does not ignore the clone. It prints, for each rule to start with that the register that stands after the run does not adopt yet, `ratchet.register-on-top` included when a register of the project's own leaves it out, the rule, its marker line and its row by reference as one line of JSON, both from the first column, so that each is pasted as it stands, with `stands_in` the first instruction file, the `sha256` of the rule and its ratchet, and `status` "text only for now" where the rule names a check. It says where to put each marker: in that file, alone on a line, by the project's own wording of the rule, and to leave out a rule the file does not state. It says, every time and without reading the file, that a marker counts only in a file in UTF-8 with LF line endings: `check_register.py` fails on a file in another encoding and on a marker line that ends in CRLF. Other instruction files it found are named as ones a row may point at. It prints `ratchet.register-on-top` with the rest, and says it fits only where the register, not the project's file, lists every rule in force and takes precedence. It says how to record a rule whose row it prints "text only for now" as `built`: with a `where` that names the enforcement point and when it was read back, such as the protection of `main` at the host for `ratchet.protected-main`, as the glossary defines built. It does not say that the host enforces it, since it cannot see the host. It prints the command that copies [run_pinned.py](#run_pinnedpy) into the project's repo from the pinned commit, `.github/ratchet/run_pinned.py`, and the one step to add to a job that the protection of `main` already requires, which runs it with `python3 -I`, pinned to the commit: it adds no workflow and no required job, so no admin is needed. Beside the step it prints `permissions: contents: read` for the job, so that its token can only read the repo, and `persist-credentials: false` for its checkout, so that no token is left in `.git/config`, each with why, and the same command as a line for a local check script that CI runs, for a project whose definition of done is that script, in a subshell followed by `|| exit 1`, so that it stops a script with `set -e` or without it. It says that `inventory.py --ruleset <file>`, given the ruleset or branch protection of `main` exported from the host, names which jobs are required. The last line of a run that passes names no file left as it is: a `register.json` of the project's own is checked as it stands, with nothing to compare. The check at the end of a real run, and the verdict of `--check`, is `check_register.py register.json`, without `--markdown`, so a register whose rows by reference miss their marker fails both. `register.json` is written with the same write guards as a start: never over a file, never through a link, only inside the root. The exit codes are the same: 0 when the plan can be carried out and the register it leaves passes, 1 when it would not pass, 2 when it cannot run.

The name is the one `--name` gives, or else the repo's name in the url of its git remote, `origin` first and else the first remote with a url, read from the git config as a file, without `.git`, when that is a name, or else the folder's name. It says which, and why the remote's was not taken. A worktree's folder, which a tool may name, is then not taken for the project's name. The name is ASCII letters and digits, in words joined by one space, `-`, `.` or `_`, at most 100 characters, and nothing that is shown as a link. So it can stand as text in a heading and in the register.

A file that exists with the content it would write is unchanged. A file that exists with other content, or that is not a plain file, is skipped, named, and left as it is. That is reported, not a failure: the run writes the rest, and the exit code does not change for it (step 5 of [D-2026-11-22-second-redraw](../decisions/D-2026-11-22-second-redraw.md)). With `--check` it writes nothing and says the same, and checks in memory the register it would leave: that `register.json` passes `check_register.py`, that `REGISTER.md` is a plain file and what `register.json` generates, and, when `register.json` names an instruction file in `instructions`, that the file's path holds no link, and that the file exists and holds the block that `register.json` generates. It reaches that verdict with the same function as the check at the end of a real run, `check_register.generated_problems`, given the bytes it would write for each file it would write, and reading every other file from the disk, so the two cannot drift apart (review of d86ff3e). Where a file is skipped or would be written, `--check` and a real run exit with the same code. Otherwise it ends by running `check_register.py register.json --markdown REGISTER.md` from the same checkout and shows its output. A second run says that nothing changed. The last line of a run that passes says only what applies: to compare each file left as it is, to fill in `AGENTS.md` when it was written, and to commit the files it wrote or changed, or that there is nothing to commit. Before the check at the end it names what is left to do: each placeholder of the template that `AGENTS.md` holds or would hold, from the fixed list in `check_register.py`, which the workflow's register check fails on, a placeholder nested in another one, such as the `<n>` of the handover's, on the list on its own; the jobs `ratchet` and `project-checks`, to require in the protection of `main`; and, when the repo's git config names no remote, the adopted rules whose check cannot run before it has one, with why: `ratchet.register-on-top`, `ratchet.protected-main`, `ratchet.owner-paths`, `ratchet.no-secrets` and `ratchet.lesson-names-check`, as far as the register that stands after the run adopts them. It reads the config as a file, in the repo's common directory for a worktree, looks for a line `[remote "`, and does not follow an include or read a worktree's own `config.worktree`. None of this changes the exit code. Each file is written in full to a temporary file beside it and synced, then linked into place with a hard link, which fails when the file appeared meanwhile, so a file is missing or whole. On a file system with no hard links it stops with exit 2 and writes no file there: it never writes a file directly, which a cut-off write could leave half written for a second run to skip. A run that stops halfway leaves whole files, and the next run writes the rest. Exit code 0: the plan was carried out, or with `--check` can be, and the register passes, whether a file was skipped or not. 1: the register does not pass, or with `--check` would not, `REGISTER.md` or the instruction file included. 2: it could not run, and wrote nothing, or it stopped at a file it could not write or at a `.gitignore` that changed, and says how many files it wrote before.

The paths it prints are as the user typed them. The root is the directory it runs in as the shell names it in `PWD`, never resolved, and the Ratchet checkout, when it stands under the root, is named from the root, such as `.ratchet/checks/check_register.py`. A link above the root, such as `/var` to `/private/var` on macOS, is not resolved in what it prints: a run from a temporary folder there once named the check `../../../../private/var/...`.

It runs only from the root of a git repo, read from the files and not by running git there: a `.git` directory that holds `HEAD` and `objects/`, or a `.git` file of the one line `gitdir: <path>`, the path absolute or from the project's root, naming a directory that holds `HEAD` and `commondir` or `objects/`, as a worktree, a submodule or `git init --separate-git-dir` leaves it.

The shared threat model, [The threat model](#the-threat-model) at the top of this file, holds for `init.py` too. What follows is its own, narrower claim.

**Against which threat.** Mistakes by the person or the agent who starts a project in their own repo: a dry run that reports failure on a project that only has files of its own, so that the result is ignored, or that passes where the real run fails, a path printed that is not the one the user typed, work overwritten by a template, a pin that is a tag name, a placeholder or the commit of other files than the ones copied, the line in `.gitignore` forgotten or not taking effect, an edit to `.gitignore` lost, a result left half written, a run in a folder that is not the root of a repo, a placeholder left in `AGENTS.md`, text there that does not apply to a project of one agent, a check of the project's own with no place to run or not marked as required, a rule taken to be running before the repo has a remote. In adopt mode also: the project's own instruction file written over, or rewritten with a template, a register that does not pass the moment it is written, a row by reference with the wrong hash typed by hand, a workflow or a required job added that only an admin can add, and a start that stopped halfway taken for a project of its own.

**What it does not claim.** It does not guard against a hostile Ratchet checkout: its code is the code that runs. It never runs code from the project's repo. It runs git only in the Ratchet checkout, never in the project's repo, whose git config could name a program to run (`core.fsmonitor`), and the check at the end is the checkout's own. It does not read `.git/info/exclude`, a global excludes file or a `.gitignore` below the root, and it does not stand against an edit made to `.gitignore` in the instant between the second read and the replacement. It does not guard against a concurrent attacker. It does not see whether the pinned commit is on GitHub: a commit that is not the one of a tag is named, and fetched by the workflow all the same. It does not merge an `AGENTS.md` the project already has with the template, and it does not build any check. It does not see a placeholder that is not on the fixed list, text that a project wrote and that does not apply, or a remote named only in an included config, or only in a worktree's `config.worktree` when `extensions.worktreeConfig` is set: git reports that remote, and `init.py` names the rules as waiting all the same. It does not turn on the protection of `main`: it names the jobs to require. In adopt mode it does not read the instruction file for what it prints, so it does not see whether the file states a rule, whether it is UTF-8 with LF line endings, or whether a marker the project adds stands by the wording of its rule: the check sees a marker, not the words. It does not add the step to a job, or see whether the job it goes into is required. It looks for instruction files only at the paths on its fixed list, not at any depth; `inventory.py` lists every one.

## run_pinned.py

```sh
python3 -I .github/ratchet/run_pinned.py <commit> -- register.json
python3 -I .github/ratchet/run_pinned.py <commit> --store .ratchet --repository <url> -- register.json --markdown REGISTER.md
```

This one checks no rule either. It runs `check_register.py` from the commit a project pins, for the step that adopt mode in `init.py` prints, and for a local check script that CI runs. It is new in 0.12, from the adoption report of a real project on 0.11: the step printed before cloned Ratchet at the pinned commit and ran `.ratchet/checks/check_register.py` from the clone's working tree, and a review from another model family showed that `git update-index --assume-unchanged` hides an edited `check_register.py` from `git status`, so edited code ran while `HEAD` matched the pin, and that an ignored `checks/argparse.py` beside the check was imported the same way.

**How it is run.** The project copies the one file into its own repo, once, from the pinned commit's objects, and commits it. Adopt mode in `init.py` prints the two commands, built by `copy_command` and `run_command` in `run_pinned.py`, with the name of the file's blob in the pinned tree, which `init.py` reads through the commit and each tree on the way, every object hashed and with no git config. The copy command runs every git under `env -i`, so no `GIT_` variable of the environment, `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_CONFIG_COUNT` among them, is in effect, and reads the blob through a new, empty git directory with the store's object directory, with no config of the store's, the user's or the system's and no lazy fetch. It writes it beside the target, and keeps it only when `git hash-object --no-filters` gives it that name; otherwise it leaves nothing at the target and fails. The step, or the line for a local check script, hashes the copy the same way before it runs it, and fails when the copy is missing, empty, cut short or not that blob. That check is an `if` that ends in `exit 1`, not the left side of `&&`, which `set -e` does not stop on. The line for a local check script, built by `local_line`, is the step in a subshell followed by `|| exit 1`, so a script ends there in `sh`, `bash` and `dash`, with `set -e` or without it, both when the copy is not the blob and when the check fails: an adoption report on 0.12 found that a script without `set -e` went on after a failing check to the end. `upgrade.py` prints the same copy command and lines, with the new commit, to a register with rows by reference in a project with no `.github/workflows/ratchet.yml`. The step is printed as a YAML block scalar, `run: |`. It runs with `python3 -I`, which leaves the script's directory out of `sys.path`, and it imports nothing from beside it, so a module planted beside the copy is not imported. Its first lines refuse, exit 2, when the file does not end with its own last line, so a copy cut short after them refuses even without the step's hash. Before it runs the check it compares its own bytes with `checks/run_pinned.py` of the commit, read and hashed as below, and refuses to go on when they differ, naming the command that copies it again: a copy left stale by an upgrade, or edited, does not run the check.

**What it claims.** The check that runs is `checks/check_register.py` of the pinned commit, beside the commit's own files and no other. It uses the store, `.ratchet` unless `--store` names another, only as a store of git objects: when the store is missing it makes one, empty and with no checkout, and fetches the pinned commit alone into it, shallow and by its id, from GitHub unless `--repository` names another, so no other commit and no history is fetched and indexed; when the repository does not give a commit by its id, it fetches the repository's branches and tags into the store it made, what a clone fetches, as 0.12 did; when the commit is not in a store that was there, it fetches the commit; it never reads the store's working tree. When none of these gives the commit, because the repository cannot be reached or does not hold it, it refuses, exit 2: it never passes without the pinned commit. It removes nothing, so a store it made stays, empty, and the next run fetches into it. It refuses a store that is not a git repo of its own, so a plain folder at `.ratchet` is never taken for the project's repo. git never reads a config of the store's, the user's or the system's, and never fetches while it reads: it runs in a new, empty git directory of its own, with the store's object directory as `GIT_OBJECT_DIRECTORY`, so the store's config, hooks, refs and attributes are never read, with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG` an empty file, `HOME` and `XDG_CONFIG_HOME` a new directory, every `GIT_` variable of the environment dropped, `GIT_CONFIG_PARAMETERS` included, and `GIT_CEILING_DIRECTORIES` above the directory it runs in. With no config there is no promisor remote, so a missing object is never fetched lazily, and `GIT_NO_LAZY_FETCH=1` and `--no-lazy-fetch`, where the installed git knows it, say so again. Replace objects, hooks, `core.fsmonitor`, automatic gc and maintenance are off. The fetches into a missing store and the fetch of a missing commit are the only steps that reach the network: each explicit, from the repository named alone, and with the same isolation, the fetch writing into the store's object directory through the empty git directory, so not even the store's remotes or url rewrites are read. Objects that the store's alternates name are read too, which is harmless, since every object is hashed. It reads the commit, its tree and every blob under it with `git cat-file --batch`, and no other object of the store: the trees one level at a time, each level in one read, and then the blobs in one read, so the number of reads follows the depth of the tree and not its count of directories. It hashes each object itself, so an object whose bytes do not give its name, corrupt or swapped, is refused, and a replace ref is never followed. It reads raw objects and not the output of `git archive`, which applies the attributes and the filters that the store's own config names. It writes the tree into a new directory from `tempfile`, refusing a name that is `.`, `..` or `.git` or holds a `/`, writing no link and no submodule, and removes the directory at the end. It runs the check there with `python3 -E -s -B`, from the directory it was started in, with the arguments after `--`, and exits with the check's code. Exit 2: it could not run, and the check did not run.

**What it does not claim.** The shared threat model holds. The copy, the step and the script that runs it are files of the project, so it does not stand against someone who edits them: a change to them is in the project's diff, for the owner's required review of the owner's paths to catch, where that lock is built. Its self-check catches a copy that is not the pinned commit's, not a copy edited to skip the self-check. A copy cut short before its first lines, or empty, exits 0 when run on its own, with no step around it: the hash in the printed step and the printed line is what refuses it, and a step or a script that drops that hash is the project's edit. It does not stand against a `git`, a `python3` or a `PATH` that is not what it says, or against the repository it clones from, which is GitHub's `fabian-von-tiedemann/ratchet` unless `--repository` names another. The step and the line use `git hash-object` in the project's own repo, with its config and the environment's `GIT_` variables. It runs no `git fsck` of the whole store: every object it uses is hashed by itself, and an object it does not use does not change what runs. It does not see whether the commit is a release, or whether the job it runs in is required. It runs `check_register.py` only. The workflow that `init.py` writes for a start still runs the check from a fresh `actions/checkout` of the pinned commit, not through `run_pinned.py`.

**The cases.** Each is a test in [test_run_pinned.py](test_run_pinned.py), on a project of its own with a copy of `run_pinned.py` taken from the commit, and a store cloned from a copy of this checkout with one commit.

## python3 -I

Every script in `checks/` runs under `python3 -I`, new in 0.12. `-I` leaves the script's directory out of `sys.path`, so before, `check_register.py` failed there with `ModuleNotFoundError: No module named 'registry'`. Each script that imports a module beside it now puts its own directory first on `sys.path`, named explicitly, before it does. That brings back what a plain run has, and no more: a module planted beside a check in a working tree is still imported, which is why `run_pinned.py` runs the check from a directory that holds only the pinned commit's files. `run_pinned.py` imports nothing from beside it. The cases are in `Isolated` in [test_run_pinned.py](test_run_pinned.py): every script that imports one beside it puts its directory on the path before the first such import, every script with a command line starts with `--help` under `-I`, and `check_register.py` passes on this repo's register under `-I`.

## inventory.py

```sh
python3 .ratchet/checks/inventory.py                          # the repo in the folder it runs in
python3 .ratchet/checks/inventory.py --uses claude,codex      # and the files no harness in use loads
python3 .ratchet/checks/inventory.py --ruleset main.json      # and the jobs that run and are not required
python3 .ratchet/checks/inventory.py --global --json          # with the user's own layer, as JSON
```

This one checks no rule in a register. It is the inventory of [D-2026-11-21-inventory-and-easy-upgrade](../decisions/D-2026-11-21-inventory-and-easy-upgrade.md), with the three additions of [D-2026-11-22-second-redraw](../decisions/D-2026-11-22-second-redraw.md): a repo that already has an agent layer runs it first, to see what it has before it chooses. It is new in 0.11.

**What it claims.** It lists, as names and short facts, the files that make up a repo's agent layer as it stands, and with `--global` the user's own layer under the home folder (`--home` names another folder). It reports facts and does not interpret Markdown (D-2026-11-16-strict-forms). Judging what each part means, and which principle it answers to, is the agent's job on its output, and the result is a proposal to the owner, never a change.

- **The files.** Instruction files at any depth (`CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `AGENTS.override.md`, `GEMINI.md`) and in the places a harness reads them, skills, commands, agents, hooks, settings, MCP config, workflows, pull request and issue templates, the code owners file and the register, each with its kind and the harnesses that load it. Which harness loads which file is the table `KINDS` in the script, as of 2026-11: Claude Code, Codex, Gemini CLI, Cursor, GitHub Copilot, Windsurf and Cline. Every file in a harness's own folder, such as `.claude/`, is listed, of a kind the table knows or not. From settings and MCP config it gives only the names of hook events, with a count, and of servers.
- **Same content and same name.** Files with the same bytes, by sha256, and skills, commands and agents with the same name, in the repo, across harnesses and, with `--global`, across the two layers, each group marked as the same or a different content.
- **Not loaded by a harness in use** (addition 2). With `--uses`, the files that no harness named there loads, such as a session prompt for a harness the project left, each with the instruction files that name it. Without `--uses` it does not guess which harnesses are in use, and says to give them.
- **Look unused.** A hook under `.claude/hooks/` that no settings file of its layer names, a skill folder without `SKILL.md`, an empty file, and a file in a harness's folder of a kind the table does not know.
- **Paths named that do not exist.** In each instruction file, by line: the target of a Markdown link, read from the file's folder; an import, a word of its own that starts with `@` and has a `/` or a known extension, such as `@AGENTS.md` or `@docs/notes.md`, with punctuation at its end left off; and a span in backticks with a `/` in it, read from the file's folder or from the root. A span with no `/`, such as `` `generate.py` ``, is a name and is not looked at, and so is one with a space in it, such as `` `python3 checks/generate.py --check` ``, which is a command, and one with no known extension whose first part does not exist, such as `owner/repo`. A word such as `@alice` or `@pytest.mark.skip` is not an import. A URL and an anchor are not looked at. Three kinds of path that does not exist are listed under "Paths named and not looked for" instead, each with a count, since an instruction file names them on purpose: a path that the `.gitignore` at the root ignores, such as a generated file that is not committed; a span in a row of a table, a line that starts with `|`, whose last part has no known extension, such as `` `feature/` `` or `` `feature/login` `` in a table of branch conventions; and a path outside the root, absolute, from `/` or `~/`, or relative and leaving the root, such as a file in another repo, named as outside the root and not checked. An absolute path inside the root is looked at as any other, and one with a single part and no known extension, such as `` `/review` ``, is a command and not a path. Every other path that does not exist is still named.
- **Workflows and the host's rules** (addition 1). For each workflow, the events it runs on and its jobs, each with its name. Given with `--ruleset` the ruleset, branch protection or rules for a branch exported from the host as JSON, once or more: whether each job is required, the jobs that run on a pull request and are not required, under the heading "they look like a gate and are not", the required checks no job here names, and what the export says of required review and bypass: the number of approvals, code owner review, stale reviews dismissed, approval of the last push, the actors that may bypass, and administrators when branch protection does not apply to them. A ruleset that is not `active`, or not on branches, requires nothing. A job reports its check under its `name:` when it has a name written out, and under its id only when it has no name or a name that is an expression, which is known only when the job runs. A job is required when a required check is that one name, alone, with a matrix `(...)` after it, or with ` / ` and a called job: a job `checks` with `name: Run Checks` is not required by a ruleset that requires `checks`. A type of rule, or a parameter of the review, that it does not read is named. A field the export leaves out is shown as not in the export, never filled in: the bypass actors, which GitHub shows only to an account with admin rights, are "not shown in the export" when they are left out and "none" when the list is empty.
- **Code owners beside the register** (addition 3). The lines of the code owners file that GitHub reads, `.github/CODEOWNERS`, `CODEOWNERS` or `docs/CODEOWNERS`, first found, with their numbers, beside the files `register.json` names: its `instructions`, a row's `stands_in`, and the paths in backticks in a row's `where`, read as in an instruction file, each marked when it does not exist. A code owners file that is not UTF-8, and a register whose `adopted` or `own` is not a list, are named as not read, and the rest is listed. It does not match one against the other: the owner compares them.

It writes nothing, reaches no network and runs no program. It reads only under the root, the home folder with `--global`, and the files given with `--ruleset`. In the home folder it looks only at the names at the top of `.claude`, `.codex`, `.gemini` and `.agents`, at `.claude.json`, and in the folders of `GLOBAL_WALKED`, and reads only the files of `GLOBAL_KINDS`. It follows no link: each one in the layer is named with its target and whether the target is inside the root, and nothing behind it is read. In the home folder it looks at every part of a path from the home folder down before it walks or reads under it, so a link at `~/.claude` or `~/.agents` is named there and nothing under it, such as `~/.claude/skills`, is read. It does not read a file whose name looks like a credential (`CREDENTIAL_NAMES`: `.env`, `*.pem`, `*token*`, `*secret*`, `*credential*`, `auth.json`, `.claude.json` and others), and names it as skipped. One exception: a Markdown file of a kind a harness loads into the session as text, an instruction file, a skill, a command, an agent or an output style, whose name matches only the words `*secret*`, `*token*` or `*credential*`, such as `.claude/rules/no-secrets.md`, is read. Such a name names a rule, and the harness already puts the file's text in front of the agent, so the inventory reading its paths shows nothing new; a name like `.env.md`, and every other kind of file, is still skipped. It does not read a file over 1,000,000 bytes, and names it. It reads every file, the repo's, the home folder's and the export alike, through one guarded reader, the functions named `guarded_` in the script: from its starting point, the root, the home folder, or for `--ruleset` the folder of the file given, it looks at each part of the path without following it and refuses at the first that is a link; it opens each folder under the one before it, and the file last, with `O_NOFOLLOW` and `O_NONBLOCK`, and reads it only if it is a regular file. The starting point itself may be reached through a link, as `/tmp` and `/var` are on macOS; nothing below it is. For `--ruleset` the starting point is the folder of the path the user typed, resolved through its links once, since the path given on the command line is the user's own choice of input: a file under a folder from `mktemp -d`, which is under `/var` on macOS, is read. No other function opens, lists, walks or looks at a path, and a test sweeps the script for any that does. Every name it prints is on one line, with a line break, a control character and a backslash escaped. It does not walk `.git` or `node_modules`, nor, at the root, `.claude/worktrees` or `.ratchet`, Ratchet's own copy in a repo that adopted it, and names the last two as skipped. The export is read through the same reader as every other file, from its folder: a link above it, such as `linked-directory/export.json`, is followed, and the file itself is refused when it is a link, read only if it is a regular file, and not at all if its name looks like a credential: the name is the last part of the path that names something, so `secret-token.json/` and `secret-token.json/.` are refused as `secret-token.json` is, and a path that ends in `/`, `/.` or `/..` names a folder and is refused. A refusal for an export that is a link says to give the file the link points to. Then the export is read with the strict reader, `registry.parse_json`. Each field it reads must be of its kind, `true` and `false` are not numbers, and a field is taken as left out only when it is absent or `null`. Exit code 0 when it ran, 2 when it could not: a root that is not a folder, a harness it does not know, `--uses` that names none, `--home` without `--global`, `--home` empty, an export that is a link, a path of an export that ends in `/`, `/.` or `/..`, not a regular file, named like a credential, cannot be read, is not JSON or not UTF-8, has a field twice, holds no ruleset, is a ruleset without `target` or `enforcement`, has a field of the wrong kind, a rule without a type, a rule for a branch without the ruleset it comes from, a list that mixes the rules for a branch with a ruleset or a branch protection, or is none of the three forms.

**The exports it reads.** Three, as GitHub's REST API returns them, saved as JSON:

| Export | Endpoint | Who can get it |
|---|---|---|
| A ruleset | `GET /repos/{owner}/{repo}/rulesets/{id}` | An account that can read the repo; `bypass_actors` is shown only to one with admin rights, and is "not shown in the export" otherwise. The list `GET /repos/{owner}/{repo}/rulesets` holds no rules, and is not read: fetch each ruleset by its id |
| The rules for a branch | `GET /repos/{owner}/{repo}/rules/branches/{branch}` | An account that can read the repo. A list of rules, each with its `type`, its `parameters` and the ruleset it comes from (`ruleset_source_type`, `ruleset_source`, `ruleset_id`), from the repo and the organization, of rulesets that are active only. It is listed as one entry for each ruleset, with no bypass, which this export never shows. An empty list, no rule on the branch, cannot be told from an empty export and is refused, with a line that says what it means |
| Branch protection | `GET /repos/{owner}/{repo}/branches/{branch}/protection` | Only an account with admin rights on the repo |

Each rule of the rules for a branch must have its `type`, `ruleset_source_type` and `ruleset_source` as text and `ruleset_id` as a number; its parameters are read as those of a rule in a ruleset, and a field it does not know is named as not read.

**Against which threat.** Not knowing what governs a repo: instruction files and skills that grew over time, collide with each other or with the user's global ones, that no harness in use reads any longer, or that name files that are gone; and a job that runs on every pull request and looks like a gate, when the host does not require it, which is how a check is taken to be "built" when it cannot refuse (#78). It is read only, so that a repo can be looked at before anything in it is chosen or changed. As [the threat model](#the-threat-model) says of every check, it catches mistakes and drift, not someone who means to hide a file from it.

**What it does not claim.**

- It does not read what a file says, or judge whether a rule is good, a duplicate in meaning, or in force. Two files that say the same thing in other words are not the same content.
- The table of harnesses and their files is as of 2026-11 and is not complete. It does not see a harness's own configuration that changes what it loads, such as Gemini CLI's `contextFileName` (named as a fact, not followed), an import beyond the one line `@path`, a rule set in an application's settings, or a plugin.
- It does not see whether a harness is in use. `--uses` is the owner's word.
- A path in an instruction file may be meant as something else, and a path written in another way is not seen. A name in backticks with no `/` is not looked at.
- It reads only the `.gitignore` at the root, not one below it, `.git/info/exclude` or a global excludes file, and of it only the simplest lines: a plain path of letters, digits, `.`, `-` and `_`, its parts separated by single slashes, with no part `.` or `..`, and at most one `/` at its start and one at its end. Such a line is read as git reads it: a `/` at the end makes it a folder, everything under it ignored; a `/` at the start or before the end reads it from the root; a name alone matches at any depth. Every other line is not read and is counted, and the count is printed: a line with `*`, `?`, `[`, `]`, `!` or a backslash, `//` anywhere, a space or a tab, a character outside that list, a CR at the end, or a byte that is not ASCII. A blank line and one that starts with `#` are no pattern, as in git, and are not counted. A path under a line that is not read is named as missing, as before this reader: two reviews found that a reader of git's wildcards and `!` hid a path that was missing (`docs/**` with `!docs/keep.md`, and `docs//`, which git does not match), so the reader subtracts and fails closed, and a missing path is never hidden by a guess at git's rules. It reads names as they are written, where git on a file system that ignores case may not, so at worst it names a path as missing. A test compares each line it reads with `git check-ignore --no-index` on a table of paths. A path that a line ignores is not named as missing even when it was meant to be committed.
- A span in a row of a table that looks like a branch name is not looked for, so a folder that is gone, named in a table with a `/` at its end, is counted there and not named as missing. A branch name written in another way, or outside a table, is still named as missing when its first part exists.
- It reads workflows as far as their top-level keys, their events, their jobs and each job's `name`, with a reader of a subset of YAML that fails closed. The subset: block mappings indented with spaces, keys that are plain or quoted without an escape, comments, and block scalars, whose text it skips. Under `on:` it reads one event name, a list of names on one line, a block sequence of names at any indent, column 0 among them as PyYAML writes it, or a block mapping of names. Anything else is named as not read: a line that leaves a quote or a bracket open, an anchor, alias, tag or merge key on `on:` itself, as an event or an item of its list, or as a job's key, a job's `name` that is not a scalar on one line, a key given twice, a second document, a tab in the indent, a missing `on:` or `jobs:`, and any line it cannot place. A workflow whose events or jobs are not read is never left out: its jobs are listed under the heading "Jobs of workflows this reader could not read: it cannot tell whether they run on a pull request", or the file is, when its jobs were not read either, and so is a workflow too large or not UTF-8. What stands under an event, such as its `branches`, is not read, so an anchor or an alias there is taken as it is and changes nothing it reports. It does not see a job's `if`, the branches or paths a trigger is limited to, or what a reusable workflow runs.
- It does not reach the host. The export is what the owner gives it: it does not see whether the file is current, or a rule the export leaves out, such as one set at the organization. A required check from an app that is not a job here is listed, not judged. A job whose name is an expression is matched by its id, which may not be what GitHub reports.
- It does not match the code owners file against the files the register names, and does not see whether the owner's review is required. The register's `where` says where a check is enforced and when that was read back (D-2026-11-22-second-redraw).
- A credential under a name not on the list is read like any other file of its kind, though it prints only names and short facts from it. A credential outside the layer is not looked at.
- It does not stand against a repo set up to mislead it: a file can be named or placed so that it looks like another kind.

**Its scope, by [the threat model](#the-threat-model).** Two lines bound what it claims, and a finding outside them is a question of scope for the owner, not a defect. The workflow reader is a subset of YAML, and it names everything outside that subset as not read: a form it names as not read is the reader working as it should, and reading one more form is a change of scope. The inventory reads no file through a link anywhere on its path below the starting point, which for `--ruleset` is the folder of the path the user typed: a link is named, with its target, and nothing behind it is read, listed or looked at, and a path an instruction file or the register names through a link is shown as not looked at, neither present nor missing.

A fixture's name cannot start with a dot, so a part that starts with `dot-` is renamed to start with `.` in the copy the test makes. ## tripwire.py

```sh
python3 checks/tripwire.py < call.json   # exit 0: the call goes ahead; exit 2: it is denied, with the reason on stderr
```

The reference check for `ratchet.irreversible-waits`. It is a `PreToolUse` hook for Claude Code ([Anthropic's hooks reference](https://code.claude.com/docs/en/hooks)): Claude Code runs it before every Bash command and every write to a file, and gives it the call as JSON on stdin. This repo runs it from [.claude/settings.json](../.claude/settings.json), and a project copies it as [CONTROL-ROOM.md](../CONTROL-ROOM.md#what-cannot-be-undone) says.

**It is a tripwire, not a lock.** It reads a command line well enough to catch the usual spellings of the five steps, and no better. It does not claim every spelling: another spelling of the same step gets past it, and a hook that reads the shell can always be shown one (D-2026-11-19-locks-not-parsing). Its claim is exactly the cases listed below. Where each step is locked, and where nothing locks it, is in [CONTROL-ROOM.md](../CONTROL-ROOM.md#what-cannot-be-undone).

**What it claims.** For a Bash command, it exits 2 and names each step on a line of its own, `tripwire: <step>`, when the command is one of the cases below and the approvals file has no entry for each step it takes with that exact command. For `Write`, `Edit`, `MultiEdit` and `NotebookEdit`, it exits 2 when the path is the approvals file. Every other tool exits 0. Input it cannot read, an empty call, a call that is not JSON or not UTF-8, has a field twice, names no tool or lacks the command or the path, exits 2. Any failure of its own exits 2 as well: it never exits other than 0 or 2, and its settings use `"onFailure": "block"`, so a hook that cannot start or times out blocks the call too.

**Against which threat.** An agent's mistake: a force push it takes to be harmless, a tag or a release nobody asked for, `rm -rf` on the wrong directory, a change to the settings, written in the way agents usually write these commands. It does not stand against an agent that means to get past it: such an agent writes the step another way, from a script, from another language, or edits the hook and its settings, which are files the maintainer reads before a merge (`ratchet.owner-paths`).

**How it reads a line.** It splits the line into simple commands at `;`, `&`, `|`, `&&`, `||`, newlines and parentheses, and also reads every `$(...)`, backtick and `<(...)` as commands of their own. It takes quotes and backslashes away as the shell does, skips the body of a here-document, and skips assignments, `if`, `then`, `do` and the like. It looks past `env`, `command`, `builtin`, `exec`, `nohup`, `nice`, `timeout`, `sudo`, `xargs`, `stdbuf` and `time`, and past a path before the program, such as `/usr/bin/git`. A `cd` to a literal path is followed for the commands after it in the same line, and a `cd` to anything else makes every later path unknown. It does not expand a variable, a pattern or a tilde other than a leading `~`.

**The steps, as it reads them.**

- `force-push`: `git push` with an option that starts `--force`, with `-f` alone or in a cluster such as `-uf`, `--mirror`, `--prune`, `--delete` or `-d`, a refspec that starts with `+`, or one with no source, `:ref`; `gh api` deleting `git/refs/heads/...`, or changing one with `force=true` or with a body from `--input`.
- `tag`: `git tag` with a name, `-a`, `-s`, `-f`, `-m`, `-F` or `-u`, and no listing option, or with `-d` or `--delete`; `git push` with `--tags`, `--follow-tags` or `--mirror`, the word `tag`, a refspec under `refs/tags/`, or a name that is a tag in the local repository, also with `--delete` or as `:ref`; `git update-ref` and `git symbolic-ref` on `refs/tags/`; `gh api` changing `git/refs/tags/...` or `git/tags`, or creating `git/refs` with `ref=refs/tags/...` or with a body from `--input`.
- `release`: `gh release create`, `edit`, `delete`, `upload` and `delete-asset`; `gh api` with any method but `GET` under `repos/{owner}/{repo}/releases`.
- `delete-outside`: `rm` with `-r`, `-R` or `--recursive`, alone or in a cluster, when an operand resolves to the working tree itself or to a path outside it, after links are resolved, or holds a variable or a substitution. The one exception is the temporary directory of the same line: `d=$(mktemp -d)`, or `$(mktemp -d -t <name>)`, followed in the same line by `rm -r "$d"` or `"${d}"`, quoted and with nothing after it, when nothing else in the line assigns `d` or names it as a word. And since the shell's state does not last from one Bash call to the next, a later call may delete such a directory by its path, or a path inside it, written from the directory where `mktemp -d` writes or from `/tmp`. On macOS that directory is the per-user temporary directory the system gives, `confstr(_CS_DARWIN_USER_TEMP_DIR)`, which `mktemp -d` uses whatever `TMPDIR` says, so `TMPDIR` does not move the exception there. When the system gives no absolute path of an existing directory, or the call fails, that root is not trusted at all and nothing takes its place, not `TMPDIR` and not a default; `/tmp` stays. Elsewhere it is the temporary directory that `TMPDIR` names, as GNU `mktemp` reads it. The entry directly in it is a real directory, named `tmp.` and six or more letters or digits as `mktemp -d` names it, and owned by the user the hook runs as. That entry and every part of the path after it are read as written, with `lstat` and before any link is followed, so none may be a link, `.` or `..`, with or without a `/` at the end. A part that does not exist ends the walk, since nothing below it exists. Another session of the same user may have a directory of that form, which this does not tell apart. The tests put a fresh directory from `mktemp -d` in the place of `/tmp`, so that they need no write to `/tmp`. They do it through a constant in the hook, which nothing in a call, its JSON or its environment, can change.
- `settings`: `gh repo edit`, `delete`, `rename`, `archive`, `unarchive` and `deploy-key`; `gh secret` and `gh variable` with `set`, `delete` or `remove`; `gh workflow enable` and `disable`; `gh api` with any method but `GET` on `repos/{owner}/{repo}` itself, or under one of its settings paths: `rulesets`, `branches`, `collaborators`, `invitations`, `hooks`, `keys`, `actions`, `environments`, `pages`, `secrets`, `variables`, `topics`, `vulnerability-alerts`, `automated-security-fixes`, `autolinks`, `properties`, `private-vulnerability-reporting`, `transfer`, `tags`, `dependabot`, `codespaces`, `interaction-limits` and `teams`. Labels are not on the list: they count as harmless and can be undone. Of these, the role Write may change Actions secrets and variables, of the repository and of an environment, and GitHub's docs do not reserve Dependabot and Codespaces secrets or enabling a workflow to an admin, so for these the tripwire is the only guard ([CONTROL-ROOM.md](../CONTROL-ROOM.md#what-cannot-be-undone)). Their usual spellings, with `gh secret`, `gh variable` and `gh api`, are cases below.
- `approvals-file`: any word or redirection in the command that names the approvals file, from the directory the command runs in. No approval covers it.

`gh api` takes its method from `-X`, `-XMETHOD`, `--method` or `--method=METHOD`, and without one, from GitHub CLI's own default: `POST` when a field (`-f`, `-F`, `--field`, `--raw-field`) or `--input` is given, `GET` otherwise.

**The approvals.** They are in `.claude/ratchet-approvals.json` in the project, which git ignores, so an approval stays on the machine where the owner wrote it and is never published. The owner writes it; [templates/ratchet-approvals.json](../templates/ratchet-approvals.json) is the empty file to start from.

```json
{"approvals": [{"step": "tag", "command": "git tag v0.7", "until": "2026-11-30"}]}
```

- It is read strictly: strict UTF-8, valid JSON, no field twice, exactly the field `approvals` at the top and exactly `step`, `command` and `until` in each entry. One defect anywhere, and the file approves nothing, and the denial names the defect.
- `step` is one of the five steps. A command that takes two, such as `git push --mirror origin`, needs an entry for each.
- `command` is the whole command, character for character, and one plain command: printable ASCII, no space at either end and none of `;`, `&`, `|`, `<`, `>`, `(`, `)`, `$`, a backtick or a backslash. So an approval never covers a chain or a substitution. A command that is not plain cannot be approved, and the denial says to run the step on its own line.
- `until` is a real date, `YYYY-MM-DD`, and the approval holds through that day, by the machine's own date.

**The cases.** Each is a test in [test_tripwire.py](test_tripwire.py), which runs the hook in a child process, as Claude Code does, in a scratch git work tree with a tag `v1` and a branch `feature`. The cases are in [fixtures/tripwire/](fixtures/tripwire/). In a command, `{tree}` stands for the scratch work tree.

With an entry for each of its steps and that exact command, a case in the third column passes, and the same command with a space after it, with `true && ` before it or with `; true` after it is still denied. A case in the fourth column stays denied with such entries.

## The tag ruleset

[templates/tag-ruleset.json](../templates/tag-ruleset.json) is the lock on moving and deleting a tag (`repo.tags-stay`, D-2026-11-19-tag-ruleset-scope). It is a repository ruleset in the form of GitHub's REST API, [Create a repository ruleset](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset):

- `target` `tag`, and `conditions.ref_name.include` `~ALL`, every tag.
- `enforcement` `active`.
- `rules`: `deletion` ("Only allow users with bypass permissions to delete matching refs"), `update` ("Only allow users with bypass permission to update matching refs") and `non_fast_forward` ("Prevent users with push access from force pushing to refs"). Not `creation`.
- `bypass_actors`: one, `actor_type` `RepositoryRole` with `actor_id` 5 and `bypass_mode` `always`. Observation (O): the documentation does not list the ids of the repository roles. Public reports and rulesets made in GitHub's settings page show the repository admin role as id 5. The read-back below shows what GitHub stored.

Creation is left open because the release workflow creates each tag with the built-in token of GitHub Actions, and a block on creation would stop it (O: GitHub's documentation does not say whether that token can be a bypass actor, and public reports say it cannot; see the decision). [release.py](release.py) only creates a tag, with one `POST` to `/repos/{owner}/{repo}/git/refs`, and never moves, deletes or edits one, so the ruleset does not touch a release.

**Applying it is the maintainer's.** Settings are the maintainer's, and the agents' account, with the role Write, cannot create a ruleset. The maintainer runs, under the maintainer's own login and from the root of a checkout:

```sh
gh api -X POST repos/fabian-von-tiedemann/ratchet/rulesets --input templates/tag-ruleset.json
```

or makes the same ruleset on the settings page: Rules, Rulesets, New tag ruleset, enforcement Active, target all tags, the rules "Restrict updates", "Restrict deletions" and "Block force pushes", and "Repository admin" on the bypass list.

**Reading it back.** The answer to the `POST` holds the ruleset's `id`. Then:

```sh
gh api repos/fabian-von-tiedemann/ratchet/rulesets/<id>
```

Under the maintainer's login, it shows `target` `tag`, `enforcement` `active`, `conditions` `~ALL`, the three rules and no `creation`, and the one bypass actor. Under the agents' account, `bypass_actors` is not shown, and `current_user_can_bypass` must be `never`.

**Applied and read back in this repo.** The maintainer applied the ruleset on 2026-11-19, as `tags-stay`. The answer to the maintainer's `POST` showed the one bypass actor, `[{"actor_id": 5, "actor_type": "RepositoryRole", "bypass_mode": "always"}]`. The control room read it back the same day with the agents' account: target `tag`, enforcement `active`, `conditions.ref_name.include` `["~ALL"]`, the rules `deletion`, `update` and `non_fast_forward` and no `creation`, `current_user_can_bypass` `never`, and `bypass_actors` null, because the role Write is not shown it. Not tried: deleting or moving a tag with the agents' account, which would put a published tag at risk if the rule did not apply. Tried: 0.7 is the first release under the ruleset, and the release workflow created the tag `v0.7` and its release with the built-in token, about two and a half hours after the ruleset was made. With the read-back recorded, `ratchet.irreversible-waits` was "built" in [REGISTER.md](../REGISTER.md) ([D-2026-11-19-tripwire-and-settings](../decisions/D-2026-11-19-tripwire-and-settings.md)), until [D-2026-11-22-second-redraw](../decisions/D-2026-11-22-second-redraw.md) defined "built" by where a check is enforced: a hook is built only when it runs in every harness the project uses, and the tripwire runs only in Claude Code. It is "text only for now" since step 3 of that migration.

**The case.** `TagRuleset` in [test_tripwire.py](test_tripwire.py) reads the file strictly and pins exactly these fields, these three rules in this order and no `creation`, and the one bypass actor. It also reads `release.py` and fails if it holds a `PATCH`, `DELETE` or `PUT`, or no longer creates a tag with its one `POST`.

**What it does not claim.** The test reads the file and `release.py`, not GitHub. It does not see whether the ruleset on GitHub is still the one in the file, or still active: that was read back once, on 2026-11-19. Deleting or moving a tag has not been tried.

## Why JSON

The rules are data that the checks and a project's CI must read. The format was chosen so that the checks need nothing but a Python interpreter:

- Python's standard library reads JSON in every supported version. It reads TOML only from 3.11, and it does not read YAML at all.
- The Python that ships with a common developer operating system is older than 3.11. A check that needs a newer interpreter, or a package, is a check that does not get run.

The cost is that JSON has no comments and escapes quotation marks. The rules are one sentence per field, so it stays readable, and anything that needs explaining belongs in the changelog or in a decision.
