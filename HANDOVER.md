# Handover

What a new session needs that GitHub does not show: who waits on whom, who acts next, and the next step (`ratchet.work-in-issues`). It does not copy what GitHub already shows: which PRs are open, their reviews and checks, which issues are open, or the settings. Read those there, after [AGENTS.md](AGENTS.md) and [REGISTER.md](REGISTER.md):

- the open pull requests, with their descriptions and review verdicts in the comments
- the open issues, and among them the open questions for the maintainer, which have the label `question`
- the decisions in [decisions/](decisions/).

Replaced, not appended to, after every important event. The [decision](decisions/D-2026-11-17-workflows-checks-handover.md) that gave it this form is from 2026-11-17.

## Who waits on whom

- **Rules that lean on code ownership** wait on the protection of `main`. This is `ratchet.owner-paths`, which stays "text only for now" in [REGISTER.md](REGISTER.md), and this repo's own rule `repo.maintainer-approves`, whose ratchet says "Text only for now". They become "built", and the own rule's ratchet a check, in a PR of their own, after four steps:
  1. The protection on `main` shows one required approval, the code owner's review required, approvals dismissed on a new push, and the job `checks` as a required status check. The ruleset that protects `main` is listed by `gh api repos/fabian-von-tiedemann/ratchet/rulesets`, and its rules are read from `gh api repos/fabian-von-tiedemann/ratchet/rulesets/<id>`.
  2. The agents' account has the role Write and no more.
  3. A pull request from the agents' account, with its checks green and an approval from that account, cannot be merged before the code owner approves.
  4. After the code owner approves, a new push from the agents' account removes the approval.
- **The agents' account merges, and waits on two approvals of the same head.** By [D-2026-11-17-agent-merges-after-approval](decisions/D-2026-11-17-agent-merges-after-approval.md) it merges a pull request with a squash, and with that head as the expected head, after the code owner has approved the head and a reviewer from another model family has passed it. The code owner's approval is the maintainer's click on GitHub, or the control room submits it with a token of the maintainer's own account on the maintainer's word in the control room's chat, only at a head that has passed that review or falls under the exception below ([D-2026-11-18-approve-on-word](decisions/D-2026-11-18-approve-on-word.md)). A word may name a pull request in advance, "yes #N when the review passes", and then covers the next head that review approves, if nothing was pushed after it, until that head is merged ([D-2026-11-19-review-by-risk](decisions/D-2026-11-19-review-by-risk.md)). A decision may give a standing approval for a named set of pull requests, and [D-2026-11-22-standing-approval](decisions/D-2026-11-22-standing-approval.md) gives one for the migration of the redraw, until it is done or the maintainer stops it. A PR that changes only files in `decisions/` and this file, and changes no rule, check or register, needs no such reviewer ([D-2026-11-17-improvement-loop](decisions/D-2026-11-17-improvement-loop.md)). Auto-merge is not used. The ruleset on `main` refuses the merge without the code owner's approval of the latest push and `checks` green. Nothing stops the account from merging before the other review has passed, or the control room from approving without the maintainer's word, so `repo.agents-own-account` stays text only.
- **A new version waits on a release pull request and the maintainer's word.** By [D-2026-11-19-batched-releases](decisions/D-2026-11-19-batched-releases.md), the next version is collected under the first entry of the changelog, headed `(unreleased)`, and no merge publishes it. The release is a pull request of its own that gives the entry its date and moves the tag that the README fetches. It is merged on the maintainer's word, at most once a week or when the maintainer asks, and a fix for a security fault is released at once. Its merge publishes the version through the release workflow, and a daily scheduled run turns red while any version dated on `main` lacks its tag or its release. 0.9 was the first version released this way, on 2026-11-19, and 0.10 followed on 2026-11-21. A pin of a source moves in `sources.json` with no new version.
- **The redraw is decided, and its migration waits on one pull request at a time.** [D-2026-11-22-second-redraw](decisions/D-2026-11-22-second-redraw.md) takes ten principles (seven for every project and three for an app in production), 54 rules to 29 with a core of 19, a product module of seven experimental rules under a cap of 17, adoption by reference as a weaker mode, "built" defined by where a check is enforced, and one threat model for every check. It names every loss and authorizes the seven new clauses in the core; any other loss still blocks its pull request. The migration runs in the order of its steps, smallest and most subtractive first, each a pull request of its own, reviewed by risk. It runs under the standing approval of [D-2026-11-22-standing-approval](decisions/D-2026-11-22-standing-approval.md): the control room submits the code owner's approval and merges once the review has passed the exact head and `checks` is green, writes one line in the maintainer's chat after each merge, and stops on the maintainer's word. Steps 5 to 11 are reviewed by Codex and Gemini 4 Neon in parallel, and steps 2 to 4, 12 and 13, which only move text, by Codex alone. That step 1 is reviewed by Codex alone is a proposal (P) of that decision. A release is not covered. Each core batch carries the table of coverage of [D-2026-11-20-principles-and-obligations](decisions/D-2026-11-20-principles-and-obligations.md). #78 is settled as a convention, and closes when the inventory exists.
- **A pull request that the base branch's checks cannot judge waits on the maintainer.** The job `base` of `.github/workflows/checks.yml` runs `checks/from_base.py` from the base commit: the base's scripts on the pull request's data, and the base's tests and runner on the pull request's checks. A pull request that changes the workflow, or a check or the form of a data file in a way the base rejects, keeps the required job `checks` red, and only the maintainer can merge it, as an administrator. So it is for the pull request that adds the job, since its base has no `checks/from_base.py`. Six entries of the register are "built" by it: `ratchet.register-on-top`, `ratchet.expected-tests-ran`, `repo.rules-as-data`, `repo.checks-fail-on-fixtures`, `repo.version` and `repo.new-rule-used`.
- **A rule whose check is not built** stays "text only for now" in [REGISTER.md](REGISTER.md), and the register says what is missing.

## Who acts next

- **The maintainer** approves the exact head of each PR outside the migration, on GitHub or by a word in the control room's chat, gives the word for a release, renews the token for approvals, changes settings, and answers the open issues with the label `question`.
- **The control room** starts a workspace for each open PR or issue with work left, has every head reviewed by a model from another family (except a PR that changes only files in `decisions/` and this file, and changes no rule, check or register, [D-2026-11-17-improvement-loop](decisions/D-2026-11-17-improvement-loop.md)), posts the verdict on the PR, submits the code owner's approval of that head when the maintainer gives the word in the control room's chat or the standing approval covers it, and merges the PR once the code owner has approved that same head. It never starts a third round after two rejections of the same kind: it takes a different approach to the maintainer as a decision.
