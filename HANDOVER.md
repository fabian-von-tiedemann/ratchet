# Handover

What a new session needs that GitHub does not show: who waits on whom, who acts next, and the next step (`ratchet.work-in-issues`). It does not copy what GitHub already shows: which PRs are open, their reviews and checks, which issues are open, or the settings. Read those there, after [AGENTS.md](AGENTS.md) and [REGISTER.md](REGISTER.md):

- the open pull requests, with their descriptions and review verdicts in the comments
- the open issues, and among them the open questions for the maintainer, which have the label `question`
- the decisions in [decisions/](decisions/).

Replaced, not appended to, after every important event. The [decision](decisions/D-2026-11-17-workflows-checks-handover.md) that gave it this form is from 2026-11-17.

## Who waits on whom

- **Rules that lean on code ownership** wait on the protection of `main`. These are `ratchet.one-approver` and `ratchet.checks-owner-read`, which stay "text only for now" in [REGISTER.md](REGISTER.md), and this repo's own rule `repo.maintainer-approves`, whose ratchet says "Text only for now". They become "built", and the own rule's ratchet a check, in a PR of their own, after four steps:
  1. The protection on `main` shows one required approval, the code owner's review required, approvals dismissed on a new push, and the job `checks` as a required status check. The ruleset that protects `main` is listed by `gh api repos/fabian-von-tiedemann/ratchet/rulesets`, and its rules are read from `gh api repos/fabian-von-tiedemann/ratchet/rulesets/<id>`.
  2. The agents' account has the role Write and no more.
  3. A pull request from the agents' account, with its checks green and an approval from that account, cannot be merged before the code owner approves.
  4. After the code owner approves, a new push from the agents' account removes the approval.
- **The agents' account merges, and waits on two approvals of the same head.** By [D-2026-11-17-agent-merges-after-approval](decisions/D-2026-11-17-agent-merges-after-approval.md) it merges a pull request with a squash, and with that head as the expected head, after the code owner has approved the head and a reviewer from another model family has passed it. The code owner's approval is the maintainer's click on GitHub, or the control room submits it with a token of the maintainer's own account on the maintainer's word in the control room's chat, only at a head that has passed that review or falls under the exception below ([D-2026-11-18-approve-on-word](decisions/D-2026-11-18-approve-on-word.md)). A word may name a pull request in advance, "yes #N when the review passes", and then covers the next head that review approves, if nothing was pushed after it, until that head is merged ([D-2026-11-19-review-by-risk](decisions/D-2026-11-19-review-by-risk.md)). A PR that changes only files in `decisions/` and this file, and changes no rule, check or register, needs no such reviewer ([D-2026-11-17-improvement-loop](decisions/D-2026-11-17-improvement-loop.md)). Auto-merge is not used. The ruleset on `main` refuses the merge without the code owner's approval of the latest push and `checks` green. Nothing stops the account from merging before the other review has passed, or the control room from approving without the maintainer's word, so `repo.agents-own-account` stays text only.
- **A new version waits on a release pull request and the maintainer's word.** By [D-2026-11-19-batched-releases](decisions/D-2026-11-19-batched-releases.md), the next version is collected under the first entry of the changelog, headed `(unreleased)`, and no merge publishes it. The release is a pull request of its own that gives the entry its date and moves the tag that the README fetches. It is merged on the maintainer's word, at most once a week or when the maintainer asks, and a fix for a security fault is released at once. Its merge publishes the version through the release workflow, and a daily scheduled run turns red while any version dated on `main` lacks its tag or its release. 0.9 was the first version released this way, on 2026-11-19. A pin of a source moves in `sources.json` with no new version.
- **The change of form in 0.10 is done, and #78 waits on the redraw.** Choice 2 of [D-2026-11-20-proposal-triage](decisions/D-2026-11-20-proposal-triage.md) accepts the change of form from #60, #76, #77 and #78, with #3. The answer on #89 is [D-2026-11-20-generated-block](decisions/D-2026-11-20-generated-block.md): the rules a project adopts are generated into a marked block of its own instruction file. #100 did the block, the translations bound by hash and the status of a project's own rules, and is merged. By [D-2026-11-21-release-and-redraw](decisions/D-2026-11-21-release-and-redraw.md), 0.10 is released without #78, which, with #3, would count a check as built only when it is required for the merge and reads its rules from the base branch. The redraw of the principles decides whether it is still needed.
- **The redraw waits on 0.10.** By [D-2026-11-21-release-and-redraw](decisions/D-2026-11-21-release-and-redraw.md), a fresh session of another model redraws the principles after 0.10, starting from the findings of a second model from another family: six or seven principles, the missing production principles as questions with obligations under them, and the rules whose friction outweighs their value removed or narrowed. Each change carries the table of coverage before and after from [D-2026-11-20-principles-and-obligations](decisions/D-2026-11-20-principles-and-obligations.md). A model from another family reviews it, and the maintainer decides.
- **A rule whose check is not built** stays "text only for now" in [REGISTER.md](REGISTER.md), and the register says what is missing.

## Who acts next

- **The maintainer** approves the exact head of each PR, on GitHub or by a word in the control room's chat, renews the token for approvals, changes settings, and answers the open issues with the label `question`.
- **The control room** starts a workspace for each open PR or issue with work left, has every head reviewed by a model from another family (except a PR that changes only files in `decisions/` and this file, and changes no rule, check or register, [D-2026-11-17-improvement-loop](decisions/D-2026-11-17-improvement-loop.md)), posts the verdict on the PR, submits the code owner's approval of that head when the maintainer gives the word in the control room's chat, and merges the PR once the code owner has approved that same head. It never starts a third round after two rejections of the same kind: it takes a different approach to the maintainer as a decision.
