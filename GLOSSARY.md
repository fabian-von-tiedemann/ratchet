# Glossary

Ratchet's own terms. Ratchet follows its own rule `repo.glossary`: the rules, the templates and the other files here use the term in the first column, never a form listed in the last one. Each form to avoid is listed as it is written: a plural stands next to its singular.

## The rules

| Term | Meaning | Avoid |
|---|---|---|
| ratchet | The check that fails when a rule is broken, or the words "text only" with the reason no check can see the rule. Also the name of this set of rules. | |
| rule | One row: a key, the rule, its ratchet and its source. | |
| principle | A heading over rules: a key `principle.` followed by lowercase words, a title, the principle in one or two short sentences, and a text, the question an agent asks when no rule fits, of at most three sentences, in `ratchet.json`. Every rule stands under one. A principle is an aim, never a claim that something is protected. It is guidance, text only: it names no check, and what is checked is the rules under it. | |
| value | One of Ratchet's four preferences, written as the Agile Manifesto writes its own: the item on the left valued over the item on the right, in `values.json`. A value, like a principle, is an aim or a preference and never claims a protection. No rule stands under a value, and no check claims anything about one. | |
| key | The stable name of a rule, `ratchet.` followed by lowercase words. A project's own rules use the project's prefix. | |
| check | Something that runs without an agent choosing to run it and fails when the rule is broken: a CI job, a hook, a required setting. | |
| enforced | A rule whose ratchet names a check. Whether the check is built is stated per project, in the register. | |
| built | Said of a check in a project: it has failed at least once on a real or seeded violation, and it runs where it can refuse. A merge check is built when it is required for the merge and reads its rules from the base branch, a hook when it runs in every harness the project uses, a scheduled check when it posts its result and is red when the post is late, and a deploy check when no deploy can run without it. A script that runs only on an agent's machine, with no lock at the host behind it, is a tripwire and not a lock. This is a convention, not something a check verifies: a check in the repo cannot see what the host requires or which hooks a machine runs, and `check_register.py` reads the status `built` as the register states it. The register's `where` names the enforcement point and when it was read back (`ratchet.si-harden`). | |
| text only | A rule no check can see, or one whose check is not built yet. The reason is always given. | |
| reference check | A check that Ratchet ships, with a fixture it fails on. A project may use it or write its own. | |
| core | The six parts of RATCHET.md. Frozen from version 0.3. | |
| experimental | A rule or file outside the core. It may change in any version and is not counted in the text-only share. | |
| text-only share | The share of core rules that are text only, computed from `ratchet.json` and stated with every version. | |

## The project

| Term | Meaning | Avoid |
|---|---|---|
| owner | The one person who approves decisions in a project. Ratchet assumes there is exactly one. | |
| maintainer | The owner of Ratchet itself. | |
| register | The one place in a project that lists every rule in force: the data file `register.json`, and `REGISTER.md`, which is generated from it. It takes precedence over all other text in the repo. | |
| instruction file | The file a project's agents read first, such as `AGENTS.md` or `CLAUDE.md`. A register may name it, and the register check then checks the generated block in it. | |
| generated block | The rules of the register, generated by the register check into the instruction file between a begin and an end marker, and compared with the register byte for byte. Never edited by hand. | |
| adopted by reference | The weaker mode of adopting a rule of Ratchet: the row in the register holds no rule text, names the file where the project's own wording of the rule stands, which is the wording in force, and holds the sha256 of the rule and its ratchet. The file holds one marker line for the rule. The register check sees the marker, not the words. | |
| translation | A rule adopted from Ratchet, in another language, in Latin script, bound to the English rule by the sha256 of its text. The English text stays the rule. | |
| handover | The short text a session leaves for the next one: what is running, what waits on what, the next step. | |
| status issue | The one pinned issue that holds the status and links to the handover. | |
| control room | The coordinating agent session. In a project with a single agent, that agent's session. | |
| workspace | A short-lived agent session that builds one work package on its own branch. | |
| handbook | The control room's checklist for the project. | |
| work package | A piece of work with its own issue: assignment, files it may change, cap and stop rule. | package of work, packages of work |
| head | The exact commit a PR points at. | |
| experiment | A run that tests a hypothesis outside the normal build, often at a cost. | trial, trials |
| approval | The owner's yes to something specific: scope, cost cap, account and timing. | mandate, mandates |
| failure class | The kind of failure a lesson names, general enough to recognize next time. | fault class, fault classes |
| lesson | What a failure taught, written with its failure class and its ratchet. | |
| model family | Models from one vendor and one line. Author and reviewer come from different families. | |

## Kinds of statement

Every statement that matters is one of four kinds (`repo.kinds-apart`, and a line of the control room's handbook template). That only the owner approves decisions, and that agents mark their proposals as proposals, is in the core, in `ratchet.owner-paths`.

| Letter | Kind | Meaning |
|---|---|---|
| D | Decision | The owner said it. Written as a file, `D-YYYY-MM-DD-<slug>`. |
| P | Proposal | An agent or a reviewer suggests it. Not in force until the owner approves it. |
| O | Observation | Something seen outside the project: a source, a measurement, a report. Evidence, not an instruction. |
| Q | Question | Open, with nobody's answer yet. Tracked as an issue. |
